# 알림 팬아웃·발송 측정

100만 명에게 알림 하나를 보내는 데 무엇이 얼마나 걸리는지 잰 기록. 그래프는
`bench/run-monitored.sh`가 돌린 실행을 Grafana에서 뜬 것이다.

## 결론

발송은 건당 암호화(ECDH + HKDF + AES-GCM + VAPID 서명) 때문에 CPU를 많이 쓴다. 공유 자원인
Postgres는 발송 중에 26%만 쓰이므로 **머신을 늘린 만큼 처리량이 늘어난다.** 그래서 발송을 별도
머신에서 돌리는 구조로 간다.

늘리는 단위는 머신이다. 같은 머신의 물리 코어를 쪼개 노드를 둘로 만들면 3,299 → 2,770건/s로
**16%를 잃는다.** 노드마다 붙는 배경 작업을 다 꺼도 1% 남짓이고 메모리 압력은 0.002%라, 그
손실이 "노드마다 JVM이 하나 더 붙는 값"은 아니다. **무엇이 그 16%를 먹는지는 가르지 못했다** —
앱과 Postgres의 건당 비용이 함께 33~34% 오른다는 관측까지가 확인한 것이다(ADR-0138).

구간을 나눠 재고 코어 배분도 구간에 맞게 바꿨다. 팬아웃은 DB가, 발송은 앱이 병목이라 같은
배분으로 둘 다 재면 어느 쪽도 제 실력이 아니다.

| 구간 | 코어 배분 | 소요 | 그때 CPU |
|---|---|---|---|
| 팬아웃 | Postgres 2물리 · 앱 1물리 · 브로커 1물리 | **15.00초** | pg가 병목 |
| 발송 | 앱 2물리 · Postgres 1물리 · 브로커 1물리 | **332.71초** | 앱 323% · pg 26% |

목 수신 1,097,488건 전부 성공, 429·5xx 0건. **공급자 응답 지연 230ms**로 잰 값이다 —
`application.yml`의 `notification.web-push`에 남은 FCM 왕복 실측값이고, 순진한 구조와 같은
조건에서 비교하려면 양쪽이 같아야 한다.

### 공급자 지연이 처리량을 얼마나 깎나

```
공급자  50ms   4,078건/s   코어당 2,039건/s   전체 269.11초   앱 399%
공급자 230ms   3,299건/s   코어당 1,650건/s   전체 332.71초   앱 323%
                                              −19%
```

같은 스크립트로 지연만 바꿔 잰 짝이다. 230ms 쪽은 같은 조건을 다시 잰 회차에서 332.26초가 나왔다.

**두 회차는 막히는 지점이 다르다.** 50ms에서는 앱이 배정 400% 중 399%를 써서 CPU가 상한이다.
230ms에서는 앱에 여유가 있는데도 안 오른다 — 동시 800건이면 지연만으로 상한이
800 ÷ 0.23 = 3,478건/s이고, 실측 3,299가 그 95%다. 여기서는 동시 상한이 먼저 막는다.

동시 상한을 800에서 2,400으로 올리면 230ms에서도 20%쯤 더 간다(ADR-0136). 기본값은 안 올렸다 —
실제 공급자는 목 서버와 달리 연결 수와 속도를 제한하므로 그 조건에서 다시 볼 일이다.

팬아웃은 공급자와 무관해 그대로다.

### 1분 예산

```
발송 실측         1,097,488건 ÷ 332.71초 = 3,299건/s  (물리 2코어 · 공급자 230ms)
코어당                                      1,650건/s

겹침 무시 (팬아웃 20초 + 발송 40초로 가정)
  필요 27,437건/s → 16.6 물리코어

겹침 반영 (발송이 팬아웃 도중 1.40초부터 시작 → 창이 58.6초)
  필요 18,729건/s → 11.4 물리코어

몇 대로 잡을지는 아래에서 정한다 — 코어를 대수로 바꾸는 데 실측 아닌 가정이 하나 들어간다.
```

겹침은 실측에서 나왔다. 한 대에서 둘을 같이 돌린 실행에서 **첫 발송이 1.40초**에 찍혔고, 팬아웃이
도는 시간의 **92.0%**가 발송과 겹쳤다. 머신을 나누면 그 지연은 그대로고 팬아웃이 끝나기를 기다릴
이유가 없으므로, 발송이 쓸 수 있는 창은 40초가 아니라 60 − 1.40 = 58.6초다.

11.4 물리코어는 8코어 서버 두 대(16코어)에 40% 여유를 두고 들어간다. **그래도 3대로 잡는다.**
두 대는 두 가정 위에 서기 때문이다 — 코어당 1,650건/s가 머신을 나눠도 유지된다는 것, 그리고
회차가 전부 n=1이라는 것. 앞쪽은 한 머신 안에서 코어를 쪼갤 때 16%를 잃는다는 실측의 반대편이고,
머신이 다르면 L3도 스케줄러도 공유하지 않는다는 구조에서 나온 예상이지 실측이 아니다
(ADR-0138의 "남은 것"). 서버 두 대에서 재고 나면 2대로 내린다.

예전에 적힌 첫 발송 5.88초는 벤치가 아웃박스 행을 psql로 넣어 릴레이 폴링을 기다린 값이었다
(ADR-0135).

코어당 1,650건/s는 암호화만 돌렸을 때의 물리 코어 한계 2,796건/s의 59%다. 나머지는 공급자 응답
대기, HTTP/2 클라이언트, JSON, 발송 진행 기록에 간다.

## 순진한 구조로 처리하면

같은 100만 건을 순진하게 처리하는 데 걸리는 시간을 표본으로 재고 환산했다(`bench/run-serial.sh`).
발송 쪽 공급자 지연은 위와 같은 230ms다.

| 구간 | 방식 | 표본 | 초당 | 100만 건 |
|---|---|---|---|---|
| 알림 만들기 | 행마다 왕복·커밋 + N+1 조회 | 20,000건 · 25.90초 | 772 | **21분 34초** |
| | 행마다 왕복·커밋 | 20,000건 · 14.23초 | 1,405 | 11분 51초 |
| | 집합 삽입 (지금 구조) | 1,000,000건 · 18.16초 | 55,063 | **18.16초** (실측) |
| 푸시 발송 | 한 건씩 순차 | 868건 · 205.91초 | 4.2 | **65시간 53분** |
| | 동시 800건 (지금 구조) | 1,097,488건 · 332.71초 | 3,299 | **5분 33초** (실측) |

```
완전히 순진한 구조      21분 34초 + 65시간 53분 = 66시간 14분
지금 구조 · 구간 분리 합  15.00초  + 5분 33초      =  5분 48초     686배
지금 구조 · 한 대 실측    팬아웃과 발송을 같이       = 11분 53초     335배
지금 구조 · 발송 3대                                 1분 이내    3,974배
```

구간 분리 합은 구간마다 코어를 몰아준 값을 더한 것이고, 한 대 실측은 앱 하나가 물리 1코어에서
둘을 같이 한 실행이다. 운영은 노드를 나누므로 앞쪽에 가깝다.

읽어 둘 것.

- **N+1 조회란 수신자마다 왕복이 네 번이라는 뜻이다** — 사용자 조회, 중복 확인, 알림 삽입,
  구독 조회. 단순 순차(11분 51초)보다 82% 더 걸린다.
- **집합 삽입은 100만 건을 직접 쟀다.** 10만 이상에서 처리율이 55,000건/s 근처로 평평하다
  (2만 35,714 · 10만 51,256 · 50만 55,885 · 100만 55,063). 규모가 커져도 느려지지 않는다.
- **그 18.16초는 체인 하나로 돌린 팬아웃의 DB 총합 20.3초와 같은 자리다.** 두 경로가 독립적으로
  같은 값에 닿았고, 팬아웃 소요를 DB 삽입이 지배한다는 뜻이다(체인 1 소요 22.19초 중 91%).
- 순진한 판의 두 값(21분 34초·65시간 53분)은 표본 환산이다. 100만 건을 실제로 순차 발송하면
  이틀 반이라 재는 것 자체가 성립하지 않는다.

## 설정을 바꾸면

조각 크기와 체인 수만 바꿔 다시 쟀다(`bench/run-chains.sh`). 조건마다 3회, 반복을 바깥 루프로 돌려
드리프트를 조건에 균등 분산했고 관측 컨테이너는 내렸다. 소요는 알림 행에 박힌 시각의 최소~최대다
([ADR-0135](../decisions/songjeongki/0135-the-fanout-elapsed-comes-from-the-row-timestamps.md)).
소비자 수는 체인 수 × 2(ADR-0134). 배분은 pg 물리 2코어 · 브로커 1코어 · 앱 1코어.

| 조각 | 체인 | 소비자 | 소요 | 조각당 DB | DB 총 | pg CPU |
|---|---|---|---|---|---|---|
| 1,000 | 1 | 2 | 26.46초 | 22.4ms | 22.4초 | 101% |
| 5,000 | 1 | 2 | 22.19초 | 100.9ms | 20.3초 | 107% |
| 5,000 | 2 | 4 | **14.42초** | 126.6ms | 25.4초 | 144% |
| 5,000 | 4 | 8 | 11.74초 | 213.0ms | 42.8초 | 280% |

- **조각 1,000 → 5,000은 16% 준다.** 조각당 DB 시간이 4.5배가 되지만 횟수가 5배 줄어 남는다.
- **체인 1 → 2는 35% 준다.** 체인 1에서 DB가 소요의 91%를 차지하니 그것을 둘로 가른 값이 그대로 나온다.
- **체인 2 → 4는 19% 더 주는데 DB 시간을 1.68배 쓴다.** 그래서 안 쓴다(ADR-0134).
- FK 제거·파티셔닝 제거·다음 조각 선발행은 이미 이 값 안에 들어 있다. 각각의 몫은 그때의 코드에서만
  잴 수 있고 전부 하네스 시계라, 총 소요가 아니라 DB 작업량으로 적는다.

## 파티셔닝을 걷어낸 뒤

알림을 시스템이 지우지 않기로 하면서 월 파티셔닝의 근거가 사라졌다(ADR-0132). 걷어낸 값이다.

| | 걷기 전 | 걷은 뒤 | |
|---|---|---|---|
| 알림 1건당 힙 행 | 2 | **1** | 중복 제거 표를 컬럼으로 흡수 |
| 알림 1건당 인덱스 | 4벌 | **3벌** | |
| 저장 | 334MB | 306MB | −8% |
| WAL | 657.6MB | 581.6MB | −12% |
| 슬라이스 SQL 총 실행 | 42,435ms | 39,353ms | −7% |

팬아웃 총 소요도 20.26 → 19.00초로 6% 줄었는데, 두 값 모두 하네스 시계라
[ADR-0135](../decisions/songjeongki/0135-the-fanout-elapsed-comes-from-the-row-timestamps.md) 이후의
표와 나란히 놓지 않는다. 차이만 본다.

파티션이 있는 동안 정리 비용은 이랬다.

```
DELETE 100만 행 + VACUUM   1,232ms · WAL 54MB · 인덱스 139MB 그대로 남음
파티션 DROP                   46ms · 전부 즉시 반환
```

27배 차이지만 지우지 않으면 치를 일이 없는 값이다. 반대편에서 매번 치르던 것이 알림 1건당 힙
행 하나와 인덱스 한 벌이었다.

## 노드를 늘리면

둘 다 큐 컨슈머라 증설이 가능하다. 배율이 다른 것은 병목이 달라서이고, **무엇을 늘리느냐에 따라
방향까지 바뀐다.**

| 늘린 것 | 1 | 2 | 배율 | 그때 CPU |
|---|---|---|---|---|
| 팬아웃 노드 (체인 2 고정 · pg 물리 2코어 고정) | 23.2초 | 20.5초 | **1.13배** | 앱 30→62% · pg 155→204% |
| 발송 물리 코어 (한 노드 안에서) | 1,574건/s | 3,299건/s | **2.10배** | 앱이 병목 |
| 발송 노드 (같은 물리 2코어를 쪼개서) | 3,299건/s | 2,770건/s | **0.84배** | 앱 323→347% |

팬아웃은 증설분이 Postgres CPU로 옮겨간다. 그래서 팬아웃은 단일 노드로 두고 증설 여력을 발송에
배정한다.

발송은 코어를 늘리면 선형보다 조금 낫게 늘어난다. 반면 **같은 코어를 두 노드로 쪼개면 16% 준다** —
두 JVM이 L3와 메모리 대역폭을 나눠 쓰고, 코어가 노드에 못 박히고, PG 커넥션이 곱해진다. 늘릴
단위는 코어와 머신이다(ADR-0138). 발송 두 줄은 공급자 230ms에서 잰 값이다.

팬아웃 쪽 23.2초·20.5초는 하네스 시계라 위 표들과 나란히 놓지 않고 **배율 1.13배만** 쓴다(ADR-0135).

## 일괄 조회하면 Postgres가 먼저 넘어간다

1회 처리 인원만 바꿔 같은 100만 건을 넣었다(`bench/run-naive.sh`).

| 조각 | 결과 | 만든 알림 | 아웃박스 한 행 | 벽시계 | WAL |
|---|---|---|---|---|---|
| 1,100,000 (안 나눔) | **Postgres OOMKilled → 크래시 복구 → 전량 롤백** | **0건** | — | — | 615.9MB 버려짐 |
| 800,000 | 완료 | 100만 | 30.5MB | 29.76초 | 657.3MB |
| 500,000 | 완료 | 100만 | 19.1MB | 29.82초 | 657.1MB |
| 300,000 | 완료 | 100만 | 11.4MB | 29.86초 | 657.4MB |
| 200,000 | 완료 | 100만 | 7.6MB | 29.81초 | 657.1MB |
| 5,000 (지금 기본값) | 완료 | 100만 | 196KB | 29.88초 | 657.1MB |

100만 행 INSERT 한 문장과 uuid 100만 개짜리 `array_agg`가 Postgres 컨테이너 1.5GB를 넘겼다.
`docker inspect`가 `OOMKilled=true`를 달고, 로그에는 크래시 복구가 남는다.

```
FATAL:  the database system is not yet accepting connections
DETAIL:  Consistent recovery state has not been yet reached.
LOG:  database system was not properly shut down; automatic recovery in progress
```

**615.9MB를 쓰고 아무도 알림을 못 받는다.** 두 번 돌려 두 번 같았다.

읽어 둘 것 셋.

- **앱이 아니라 DB가 먼저 넘어갔다.** 앱 힙은 변형끼리 차이가 없었다(683~819MB). 앱은 100만
  개짜리 명단을 받아 보지도 못했다.
- **벽시계는 전부 29.7~29.9초로 같다.** 조각은 속도가 아니라 터지지 않으려고 나누는 것이다.
  (이 29.8초는 릴레이 폴링 대기와 완료 확인 주기가 얹힌 하네스 시계라 아래 진행표와 나란히 놓을 수
  없다. 조각끼리만 비교한다 — ADR-0135.)
- **아웃박스 한 행 크기는 조각에 정확히 비례한다.** 그 행은 RabbitMQ 메시지 하나가 되고 푸시
  워커가 통째로 역직렬화한다 — 30.5MB짜리 메시지가 브로커와 워커 힙을 함께 지난다.

pg 메모리 열은 `memory.current`라 페이지 캐시가 섞여 신호가 지저분하다(50만이 1,497MB, 80만이
1,112MB). 근거로 쓰는 것은 `OOMKilled` 플래그와 알림 0건이고 메모리 열은 참고로만 둔다.

## 한 대에서 둘을 같이 돌리면

앱 컨테이너 하나가 물리 1코어에서 팬아웃과 발송을 다 돌리면, 팬아웃 도중에 큐로 들어온 푸시
명령이 곧바로 같은 코어를 쓰기 시작한다.

```
발송 리스너 끔    18.812초
발송 리스너 켬    23.612초   +26%
```

이 26%가 노드를 나눠야 하는 이유다. 이 짝은 prefetch를 1로 내리기 전에 잰 값이라(ADR-0136)
훔쳐 가는 쪽의 비용이 지금과 다르다. 방향은 그대로지만 크기는 다시 잴 일이다.

| 하드웨어 | i7-6700HQ 4물리코어(8논리) |
| 설정 | 체인 2 · 슬라이스 5,000명 · 팬아웃 소비자 4 (체인 x 2, ADR-0134) |
| 푸시 소비 | prefetch 1 · 소비자 2 · 동시 상한 800 (ADR-0136) |
| 노드 역할 | 발송 회차는 발송 전용 — 스케줄링·자막 consumer 끔 (ADR-0127) |
| 커넥션 풀 | 노드당 10 (ADR-0138) |
| 공급자 지연 | 230ms (목 서버) — 순진한 판과 지금 구조에 같이 건다 |
| 앱 힙 | 1GB 고정 · 컨테이너 1.5GB |
| Postgres | 컨테이너 1.5GB |

구간을 나눠 잴 때 인프라 컨테이너는 **재시작하지 않는다.** cpuset을 compose로 바꾸면 컨테이너가
다시 만들어지고, 그러면 RabbitMQ가 새 호스트명으로 빈 노드를 띄워 구간 A가 쌓아 둔 푸시 명령
201건을 잃는다(볼륨을 붙여도 그렇다 — 데이터 디렉터리가 `rabbit@<hostname>`이라서다). 호스트명을
고정하고, cpuset은 `docker update`로 도는 컨테이너에서 제자리에 바꾼다.

## 관측 위치

Prometheus·Grafana·렌더러는 **측정 머신 밖에서** 돌린다. 같은 머신에서 돌렸을 때 팬아웃이
18.3초에서 20.976초로 늘어(+15%) 노이즈가 수치에 남았다. 옮긴 뒤는 18.786초다.

`cAdvisor`는 cgroup과 `/var/lib/docker`를 읽어야 해서 옮길 수 없다. 그래서 측정은 관측을 완전히 끈
상태에서 하고, 여기 그래프는 그 값이 어떤 모양으로 흘러가는지를 보여 준다. 위 18.3·20.976초는
하네스 시계라 차이(+15%)만 쓴다.

폴링도 측정에 얹힌다. 0.5초마다 `docker compose exec`를 두 번씩 부르니 팬아웃이 18.8초에서
22.3초로 늘었다. 지금은 2초마다 "끝났는지"만 보고, 정확한 시각은 이미 기록된 곳에서 읽는다 —
팬아웃 완료는 `max(created_at)`, 첫·마지막 발송은 목 서버의 타임스탬프다.
