# 알림 팬아웃·발송 측정

100만 명에게 알림 하나를 보내는 데 무엇이 얼마나 걸리는지 잰 기록. 그래프는
`bench/run-monitored.sh`가 돌린 실행을 Grafana에서 뜬 것이다.

## 결론

발송은 건당 암호화(ECDH + HKDF + AES-GCM + VAPID 서명) 때문에 CPU를 많이 쓴다. 공유 자원인
Postgres는 발송 중에 23%만 쓰이므로 **노드를 늘린 만큼 처리량이 늘어난다.** 그래서 발송을 별도
머신에서 돌리는 구조로 간다.

구간을 나눠 재면 이렇다. 코어 배분도 구간에 맞게 바꿨다 — 팬아웃은 DB가, 발송은 앱이 병목이라
같은 배분으로 둘 다 재면 어느 쪽도 제 실력이 아니다.

| 구간 | 코어 배분 | 소요 | 그때 CPU |
|---|---|---|---|
| 팬아웃 | Postgres 2물리 · 앱 1물리 · 브로커 1물리 | **20.35초** | pg가 병목 |
| 발송 | 앱 2물리 · Postgres 1물리 · 브로커 1물리 | **359.91초** | 앱 305% · pg 23% · 목 52% |

목 수신 1,097,488건 전부 성공, 429·5xx 0건.

### 1분 예산

```
발송 실측         1,097,488건 ÷ 359.91초 = 3,049건/s  (물리 2코어)
코어당                                     1,525건/s

겹침 무시 (팬아웃 20초 + 발송 40초)
  필요 27,437건/s → 18.0 물리코어 → 8코어 서버 3대

겹침 반영 (발송이 팬아웃 도중 5.88초부터 시작 → 창이 54.1초)
  필요 20,279건/s → 13.3 물리코어 → 8코어 서버 2대
```

겹침은 실측에서 나왔다. 한 대에서 둘을 같이 돌린 실행에서 **첫 발송이 5.88초**에 찍혔다 —
아웃박스 릴레이가 첫 조각의 푸시 명령을 그때 큐로 올린다. 머신을 나누면 그 릴레이 지연은 그대로고
팬아웃이 끝나기를 기다릴 이유가 없으므로, 발송이 쓸 수 있는 창은 40초가 아니라 60 − 5.88 = 54.1초다.

코어당 1,525건/s는 암호화만 돌렸을 때의 물리 코어 한계 2,796건/s의 55%다. 나머지는 HTTP/2
클라이언트, JSON, 발송 진행 기록에 간다.

## 순진한 구조에서 먼저 넘어가는 쪽

"자료를 올렸으니 그 강좌 수강생 전원에게 알림을 만든다" — 처음 떠올리는 구조다. 그러면 100만
명이 한 덩어리가 된다. 조각 크기만 바꿔 같은 100만 건을 넣었다(`bench/run-naive.sh`).

| 조각 | 결과 | 만든 알림 | 아웃박스 한 행 | 벽시계 | WAL |
|---|---|---|---|---|---|
| 1,100,000 (안 나눔) | **Postgres OOMKilled → 크래시 복구 → 전량 롤백** | **0건** | — | — | 615.9MB 버려짐 |
| 800,000 | 완료 | 100만 | 30.5MB | 29.76초 | 657.3MB |
| 500,000 | 완료 | 100만 | 19.1MB | 29.82초 | 657.1MB |
| 300,000 | 완료 | 100만 | 11.4MB | 29.86초 | 657.4MB |
| 200,000 | 완료 | 100만 | 7.6MB | 29.81초 | 657.1MB |
| 5,000 (지금 기본값) | 완료 | 100만 | 196KB | 29.88초 | 657.1MB |

100만 행 INSERT 한 문장과 uuid 100만 개짜리 `array_agg`가 Postgres 컨테이너 1.5GB를 넘겼다.
`docker inspect`가 `OOMKilled=true`를 달고, 로그에는 크래시 복구가 남는다.

```
FATAL:  the database system is not yet accepting connections
DETAIL:  Consistent recovery state has not been yet reached.
LOG:  database system was not properly shut down; automatic recovery in progress
```

**615.9MB를 쓰고 아무도 알림을 못 받는다.** 두 번 돌려 두 번 같았다.

읽어 둘 것 셋.

- **앱이 아니라 DB가 먼저 넘어갔다.** 앱 힙은 변형끼리 차이가 없었다(683~819MB). 앱은 100만
  개짜리 명단을 받아 보지도 못했다.
- **벽시계는 전부 29.7~29.9초로 같다.** 조각은 속도가 아니라 터지지 않으려고 나누는 것이다.
  (이 29.8초는 폴링이 얹힌 값이라 위의 20.35초와 나란히 놓을 수 없다. 조각끼리만 비교한다.)
- **아웃박스 한 행 크기는 조각에 정확히 비례한다.** 그 행은 RabbitMQ 메시지 하나가 되고 푸시
  워커가 통째로 역직렬화한다 — 30.5MB짜리 메시지가 브로커와 워커 힙을 함께 지난다.

pg 메모리 열은 `memory.current`라 페이지 캐시가 섞여 신호가 지저분하다(50만이 1,497MB, 80만이
1,112MB). 근거로 쓰는 것은 `OOMKilled` 플래그와 알림 0건이고 메모리 열은 참고로만 둔다.

## 한 대에서 둘을 같이 돌리면

앱 컨테이너 하나가 물리 1코어에서 팬아웃과 발송을 다 돌리면, 팬아웃 도중에 큐로 들어온 푸시
명령이 곧바로 같은 코어를 쓰기 시작한다.

```
발송 리스너 끔    18.812초
발송 리스너 켬    23.612초   +26%
```

이 26%가 노드를 나눠야 하는 이유다.

## 이 실행의 조건

| | |
|---|---|
| 측정 대상 | 수강생 1,000,000명 · 푸시 구독 1,097,488건 |
| 하드웨어 | i7-6700HQ 4물리코어(8논리) |
| 설정 | 갈래 2 · 조각 5,000명 · 팬아웃 소비자 8 |
| 앱 힙 | 1GB 고정 · 컨테이너 1.5GB |
| Postgres | 컨테이너 1.5GB |

구간을 나눠 잴 때 인프라 컨테이너는 **재시작하지 않는다.** cpuset을 compose로 바꾸면 컨테이너가
다시 만들어지고, 그러면 RabbitMQ가 새 호스트명으로 빈 노드를 띄워 구간 A가 쌓아 둔 푸시 명령
201건을 잃는다(볼륨을 붙여도 그렇다 — 데이터 디렉터리가 `rabbit@<hostname>`이라서다). 호스트명을
고정하고, cpuset은 `docker update`로 도는 컨테이너에서 제자리에 바꾼다.

## 관측 위치

Prometheus·Grafana·렌더러는 **측정 머신 밖에서** 돌린다. 같은 머신에서 돌렸을 때 팬아웃이
18.3초에서 20.976초로 늘어(+15%) 노이즈가 수치에 남았다. 옮긴 뒤는 18.786초다.

`cAdvisor`는 cgroup과 `/var/lib/docker`를 읽어야 해서 옮길 수 없다. 그래서 관측을 완전히 끈
값(18.3초)이 대표 수치이고, 여기 그래프는 그 수치가 어떤 모양으로 흘러가는지를 보여 준다.

폴링도 측정에 얹힌다. 0.5초마다 `docker compose exec`를 두 번씩 부르니 팬아웃이 18.8초에서
22.3초로 늘었다. 지금은 2초마다 "끝났는지"만 보고, 정확한 시각은 이미 기록된 곳에서 읽는다 —
팬아웃 완료는 `max(created_at)`, 첫·마지막 발송은 목 서버의 타임스탬프다.

## 다시 뜨는 법

```bash
# 구간을 나눠 재기 (팬아웃·발송 각각에 코어를 몰아준다)
ssh lazy 'cd ~/apps/liveclass && MODE=split bash bench/run-timeline.sh'

# 조각을 안 나누면 어디가 터지는지
ssh lazy 'cd ~/apps/liveclass && bash bench/run-naive.sh'

# 그래프용 실행 (측정 머신에는 exporter만)
ssh lazy 'cd ~/apps/liveclass && PHASE=both bash bench/run-monitored.sh'

# 로컬: 터널 + 관측
ssh -N -L 18081:127.0.0.1:18081 -L 15692:127.0.0.1:15692 \
       -L 19187:127.0.0.1:19187 -L 18082:127.0.0.1:18082 lazy &
docker compose -f bench/monitoring/compose.remote.yml up -d

# 스크린샷 (창은 실행이 남긴 window.json)
curl -o graphs/01-container-cpu.png \
  "http://127.0.0.1:13000/render/d-solo/fanout-bench?panelId=2&from=<ms>&to=<ms>&width=1400&height=560&theme=light"
```
