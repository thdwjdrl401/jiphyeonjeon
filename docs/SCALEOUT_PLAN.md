# 스케일아웃 계획 — Kurento / 시그널링 / 채팅

> ⚠️ **대체됨 (SUPERSEDED)**: Kurento 기반 계획이다. 미디어는 **LiveKit self-host**로 변경됨 → **[architecture.md](architecture.md)** · [decisions/0004](decisions/0004-media-livekit-selfhost.md). 아래는 참고용(히스토리).

> 목표: 부하를 **측정 → 기준점(최대 방 인원·동시 방 수) 설정 → (고도화 단계) 트리거 기반 자동 확장**.
> 전제: 병목은 **미디어 처리(Kurento)**. 시그널링·채팅은 상대적으로 경량.
> **우선순위**: ①단일 인스턴스 캐파 측정 → 최대 방 인원 기준 결정(근시일) → ②멀티 인스턴스 오케스트레이션(고도화, 후순위).

---

## 0. 현재 아키텍처 (단일 노드)
```
[Vue SPA] ──REST/STOMP──> [Spring App] ──Kurento Client──> [Kurento MS]
                          (REST + 시그널링 + 채팅 SimpleBroker)   (미디어 라우팅)
                                    │
                                  [MySQL]     [Coturn STUN/TURN]
```

## 1. 부하 특성 분석 — 무엇이 먼저 터지는가

| 컴포넌트 | 부하 성격 | 병목 | 스케일 압력 |
|----------|----------|------|------------|
| **Kurento** | 방마다 미디어 인코딩/디코딩/라우팅 | **CPU, 대역폭(NIC)** | 🔴 가장 높음 |
| 시그널링(Spring `/webrtc`) | SDP/ICE는 진입/퇴장 순간만 | 소켓 수 | 🟡 낮음 |
| 채팅(STOMP) | 텍스트 브로드캐스트 | 소켓/브로커 | 🟢 매우 낮음 |
| MySQL | CRUD·이력, 화상 무관 | 커넥션/IO | 🟢 낮음 |

### "4명"과 부하의 관계 (중요 — 오해 방지)
- **방 최대 4명은 Kurento 한계가 아니라 명세(Sub Ⅲ)의 비즈니스 규칙**이다. Kurento 한 인스턴스는 서버 스펙(CPU/NIC)이 허용하는 만큼 수용 가능.
- group-call(SFU) 토폴로지에서 방 인원 N이면 각자 **송신 1 + 수신 N-1** → 라우팅 스트림 **N×(N-1)**, 엔드포인트 ≈ N². **인원이 늘면 부하가 제곱으로 폭증**.

| 인원 N | 스트림 N×(N-1) | 엔드포인트 ≈ N² |
|--------|---------------|----------------|
| 4 | 12 | 16 |
| 10 | 90 | 100 |
| 20 | 380 | 400 |
| 50 | 2,450 | 2,500 |

➡️ **따라서 "최대 방 인원"은 고정값이 아니라, 실제 서버에서 단일 인스턴스가 QoS를 유지하며 버티는 한계를 측정해 정하는 값이다.** (명세의 4명은 출발점/기본값)

### 핵심 설계 제약
- Kurento `MediaPipeline`은 **서버 로컬** → 한 방의 참여자는 같은 인스턴스에 있어야 함.
- 한 방의 부하가 단일 인스턴스를 넘어설 때만 인스턴스 간 브리징(캐스케이딩)이 필요 → **고도화·후순위**. 방 인원이 단일 인스턴스 캐파 이내라면 불필요.

## 2. 접근 전략 — 근시일 vs 고도화

| Tier | 범위 | 시점 |
|------|------|------|
| **Tier 1 (근시일·우선)** | 계측 + **단일 Kurento 부하 테스트** → 최대 방 인원·동시 방 수 기준 결정. 단일 인스턴스로 운영 | 지금 |
| **Tier 2 (중기)** | 채팅 외부 브로커(멀티 앱 인스턴스 대비), MySQL 분리(RDS) | 필요 시 |
| **Tier 3 (고도화·후순위)** | **멀티 Kurento 오케스트레이션**(풀+방 배치+오토스케일), 시그널링 수평 확장, (초대형 방이면) 크로스 인스턴스 브리징 | 트래픽 증가 후 |

> 사용자 결정 반영: **멀티 Kurento 오케스트레이션은 고도화(Tier 3)로 이동.** 우선은 단일 인스턴스 캐파 측정에 집중.

## 3. 성능 측정 계획 (Tier 1 핵심)

### 3.1 수집 지표
- **Kurento**: 시스템 CPU%·mem·**NIC in/out(Mbps)**; Kurento 레벨 활성 `MediaPipeline`/`WebRtcEndpoint` 수, 엔드포인트 `getStats()` — **outbound/inbound bitrate, packetsLost, jitter, RTT**.
- **QoS 저하 판정선**: packetLost율↑, jitter↑, RTT↑, 영상 프리즈/해상도 다운.

### 3.2 수집 스택
- Prometheus + Grafana **또는** CloudWatch 커스텀 메트릭. Kurento stats는 `KurentoClient`·엔드포인트 `getStats()`로 수집하는 익스포터를 시그널링 서버에 구현.

### 3.3 부하 테스트 하네스
- 가상 참여자: headless Chrome + `--use-fake-device-for-media-stream --use-fake-ui-for-media-stream` + 합성 영상(y4m).
- 오케스트레이션: Selenium Grid / [KITE](https://github.com/webrtc/KITE) / `webrtcperf` 로 방·참여자 램프업.
- 시나리오 A(**방 크기 한계**): 한 방의 인원을 늘리며 QoS 붕괴 지점 측정 → **최대 방 인원** 도출.
- 시나리오 B(**동시 방 한계**): 4명(또는 A에서 정한 인원) 방 개수를 늘리며 붕괴 지점 측정 → **인스턴스당 최대 동시 방 수** 도출.

---

## 4. 기준점 결정 (Tier 1 산출물)

측정한 캐파시티 곡선의 **knee(품질 붕괴 직전) 지점**을 기준으로:
- **최대 방 인원** = 단일 인스턴스가 한 방에서 QoS 유지하는 최대 N (명세 4명을 이 값으로 조정 가능).
- **인스턴스당 최대 동시 방 수** = 운영 정원. 이 값을 넘기려 할 때가 Tier 3(멀티 인스턴스) 도입 시점.
- 운영 여유치: 붕괴점의 **70~80%**에서 경고/차단.

> 즉 로드 테스트 결과가 곧 **앱의 방 정원 정책**과 **인스턴스 도입 기준**이 된다.

## 5. (Tier 2) 채팅 스케일 준비
- 앱 인스턴스를 여럿 두게 되면 인메모리 `SimpleBroker`로는 인스턴스 간 메시지 팬아웃 불가.
- → **외부 브로커 릴레이**: Spring `enableStompBrokerRelay` → RabbitMQ(STOMP) 또는 Redis pub/sub. WebSocket 세션 sticky.
- 채팅은 경량이라 급하지 않음 — 앱을 다중화하는 시점에 함께.

---

## 6. (Tier 3 · 고도화 · 후순위) 멀티 Kurento 오케스트레이션

> 트래픽이 단일 인스턴스 정원(§4)을 넘어설 때 착수. **지금은 설계만 남겨두고 보류.**

- **KMS 레지스트리(Redis)**: 각 Kurento의 `{id, host, 부하지표, 방개수, 상태}`.
- **방 배치**: 새 방 → least-loaded 인스턴스 선택 후 `room→KMS` 매핑; 기존 방 → 매핑된 인스턴스로 라우팅(같은 파이프라인 보장).
- **오토스케일**: 커스텀 메트릭(CPU/엔드포인트/bitrate) → CloudWatch Alarm+EC2 ASG 또는 K8s HPA. 쿨다운·min/max.
- **드레이닝 축소**: 미디어는 장수명 스테이트풀 연결 → 축소 대상은 `draining`으로 신규 방 차단 후 기존 방 종료 대기 후 종료(통화 강제 종료 방지).
- **시그널링 수평 확장**(더 후순위): `conferenceId` 어피니티(consistent hashing/ sticky) + Redis 공유 상태.
- **크로스 인스턴스 브리징**(최후): 한 방이 인스턴스 하나를 넘는 초대형 방을 원할 때만. RTP 캐스케이딩 — 고난도.

## 7. 단계별 로드맵 (재정렬)

| Phase | Tier | 내용 | 산출물 |
|-------|------|------|--------|
| **P0. 계측** | 1 | Kurento/시스템 메트릭 익스포터 + 대시보드 | 관측 가능성 |
| **P1. 단일 캐파 측정** | 1 | 부하 하네스로 방 크기·동시 방 한계 측정 | 캐파시티 곡선 |
| **P2. 기준 확정** | 1 | 최대 방 인원 + 인스턴스당 동시 방 수 + 여유치 결정 | **방 정원 정책**, 인스턴스 도입 기준 |
| P3. 채팅 브로커 | 2 | (앱 다중화 시) SimpleBroker→RabbitMQ Relay | 멀티 인스턴스 채팅 |
| P4. Kurento 풀+배치 | 3 | Redis 레지스트리 + room→KMS 배치/드레이닝 | 다중 Kurento 수동 |
| P5. Kurento 오토스케일 | 3 | 트리거 + 드레이닝 축소 | 자동 확장 |
| P6. 시그널링 스케일 | 3 | 어피니티 + 공유 상태 | 시그널링 수평 확장 |

**지금 할 것 = P0 → P1 → P2 (Tier 1).** P3 이후는 트래픽이 정원을 넘어설 때 착수.

---

## 8. 리스크 & 고려사항
- **측정 없는 기준값은 무의미** → P0/P1 선행이 원칙. 최대 방 인원도 측정으로 정함.
- **드레이닝 미흡 시**(Tier 3) 축소가 통화를 끊음 → 방 종료 대기 필수.
- **Coturn(TURN)** 도 relay 트래픽 병목 가능 → 필요 시 별도 스케일.
- **비용**: 미디어 인스턴스는 CPU/네트워크 비쌈 → 정원 산정·scale-in(드레이닝) 신중.
- 초대형 방(크로스 인스턴스)은 별도 설계 과제 — 현재 범위 밖.
