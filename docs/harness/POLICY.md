> 기능/변경마다 **"계약 테스트가 필요한가, 린트로 충분한가, 아무것도 불필요한가"**를 판단하는 기준.
> "항상 테스트"도 "테스트 없음"도 아닌, **필요한 곳에만** 자물쇠를 채우기 위한 것.

## 판단 기준

### camelCase 판단 기준

`camelCase`는 적용 대상에 따라 검증 방법이 다르다.

- **API JSON 요청/응답 필드명**: FE/BE 공유 계약이므로 계약 테스트 대상이다. 예: `thumbnailUrl`, `isActive`, `conferenceCategoryId`.
- **코드 내부 식별자**: 정적으로 잡을 수 있으므로 린트 대상이다. 예: 변수명, 함수명, import 순서, 미사용 변수.
- **DB 컬럼명**: DB 내부 구현 영역이므로 snake_case를 허용한다. 단, DTO/request/response로 노출되는 순간 camelCase 계약을 따른다.

| 상황 | 필요한 자물쇠 | 이유 |
|---|---|---|
| FE/BE가 공유하는 API JSON 요청·응답 **필드 계약** ([ROADMAP](../ROADMAP.md) "🟡 최대 함정") | **계약 테스트 필수** | 한쪽이 바꾸면 런타임에 깨짐 |
| **마일스톤 완료 게이트 핵심 경로** (로그인 성공/실패, 방 생성·종료) | **계약 테스트** | 회귀 시 서비스 핵심이 무너짐 |
| 상태코드·응답 규격 (201/401/409 등) | **계약 테스트** | FE 분기와 사용자 흐름이 의존 |
| 코드 내부 정적 규칙 (변수명 camelCase, import 순서, 미사용 변수) | **린트로 충분** | 테스트보다 저비용, 즉시 피드백 |
| 🟢 표준 CRUD·내부 헬퍼·UI 문구·스타일 | **불필요** | 공유 계약 없음. 근거만 한 줄 남김 |

> 판단이 애매하면 "공유 경계를 넘는가?"를 물어라 — FE↔BE, 방장↔참여자, 채팅↔시그널링처럼 **두 주체의 계약이 걸리면 테스트**, 한 모듈 내부면 린트/무.

## 마일스톤별 성장 (자물쇠는 착수 시점에 추가)

| 마일스톤 | 활성화할 계약 자물쇠 |
|---|---|
| **Sub Ⅰ** 인증/회원 | `/users`·`/auth` 응답 규격(201·401·404·409) 계약 테스트 |
| **Sub Ⅱ** 방 CRUD | 방 API JSON 필드명 camelCase 계약 테스트 + 코드 식별자 camelCase 린트 |
| **Sub Ⅲ** 화상콜/이력 | `/histories` 응답 필드 + `user_conference` 동기화 불변식(방장 종료 시 전원 exit·`isActive=false`) |

미리 다 깔지 않는다. **해당 마일스톤 착수 시** [ENFORCEMENT.md](ENFORCEMENT.md)로 그때 필요한 것만 켠다.

## 판단 후 할 일

1. **판단을 남긴다**: 테스트를 **채택하든 생략하든** 근거를 기록. 유의미한 판단이면 [../decisions/](../decisions/)에 ADR.
2. **자물쇠를 켠다**: 계약 테스트/린트가 필요하다고 판단했으면 [ENFORCEMENT.md](ENFORCEMENT.md)의 템플릿을 복사·활성화.
3. **완료 게이트**([AGENTS.md §4](../../AGENTS.md#4-완료-게이트-기능-완료-선언-전-필수))에서 증거·ADR 번호를 명시.

> Claude Code 사용자는 `/harness-check <기능>`으로 이 판단을 자동화할 수 있다(근거·ADR 초안 출력).
