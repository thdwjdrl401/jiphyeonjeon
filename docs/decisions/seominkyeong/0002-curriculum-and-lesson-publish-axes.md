# ADR-0002: 게시 축은 서버에서 분리하고, 공개는 화면의 버튼 하나로 완결한다

> 📍 하네스 개요: [../../harness/README.md](../../harness/README.md) · 판단 정책: [../../harness/POLICY.md](../../harness/POLICY.md)

- **상태**: 채택
- **일자**: 2026-07-28
- **관련**: Sub Ⅱ, 브랜치 `fix/fe/authoring-ux`, [songjeongki/0021](../songjeongki/0021-lesson-publish-mvp-direct.md)(유지), [seominkyeong/0001](0001-draft-only-curriculum-delete.md)

## 맥락 (Context)

공개 여부를 결정하는 상태가 **두 개**인데 서로 독립이다.

| 축 | 값 | 바꾸는 API |
|---|---|---|
| 커리큘럼 `lifecycleStatus` | DRAFT · PUBLISHED · ARCHIVED | `POST /instructor/curriculums/{id}/publish` |
| 강의 `status` | DRAFT · PUBLISHED (AI_NOT_READY·READY는 미사용, [0021](../songjeongki/0021-lesson-publish-mvp-direct.md)) | `POST /instructor/lessons/{id}/publish` |

수강생이 강의를 보려면 **둘 다 PUBLISHED여야 한다.** `CatalogService`가 커리큘럼을
`findByIdAndLifecycleStatus(id, PUBLISHED)`로 찾고(아니면 404), 그 안에서 `buildOutline`이
PUBLISHED 강의만 담기 때문이다. 실 API로 확인한 전이는 다음과 같다.

| 단계 | lifecycleStatus | publishedLessonCount | `GET /curriculums/{id}` |
|---|---|---|---|
| 생성 직후 | DRAFT | 0 | 404 |
| 강의만 게시 | DRAFT | 1 | **404** |
| 커리큘럼도 게시 | PUBLISHED | 1 | 200 (목차 강의 1개) |

서버 로직은 각 축에서 올바르게 동작한다. 문제는 **화면이 두 축을 따로 보여 준다**는 것이다.
강사는 "게시 강의 5/5"를 보고 공개됐다고 믿지만 커리큘럼이 DRAFT면 실제 공개는 0이다.
반대로 커리큘럼만 게시하면 목차가 빈 커리큘럼이 카탈로그에 올라간다. 두 실패 모두
"내가 방금 한 행동이 무엇을 공개했는가"를 알려 주는 지점이 없어서 생긴다.

## 결정 (Decision)

1. **서버의 두 축은 계속 독립으로 둔다.** [ADR-0021](../songjeongki/0021-lesson-publish-mvp-direct.md)의
   "강의 게시는 별도 command"를 유지하고, 서버의 커리큘럼 publish는 강의를 연쇄 게시하지 않는다.
2. **대신 화면은 주 버튼 하나로 "공개" 상태에 도달시킨다.** 관리 화면의 주 게시 버튼은 초안 강의를
   먼저 올리고 이어서 커리큘럼을 공개한다 — 두 축을 오케스트레이션하는 책임은 클라이언트가 진다.
   강사가 공개를 위해 버튼을 두 번 눌러야 하는 흐름은 만들지 않는다.
3. **화면은 두 축의 AND(= 실제 공개 여부)를 1차 정보로 표시한다.** 배지는 축 이름(DRAFT)이 아니라
   결과(`공개 중`/`비공개`)를 쓰고, '내 커리큘럼' 카드도 DRAFT 커리큘럼의 "게시 강의 N/N"이
   공개 신호로 읽히지 않게 한다.
4. **우회로는 남기되 안전할 때만 연다.** "커리큘럼만 게시"는 이미 게시된 강의가 있을 때만 노출한다 —
   게시된 강의가 0개면 목차가 빈 커리큘럼이 공개되기 때문이다. 같은 조건을 실행 경로에도 가드로 둔다.
5. **저장 실패 시 게시를 중단한다.** 자동 저장이 실패한 상태로 게시하면 화면에 보이는 내용과
   공개되는 내용이 갈린다.
6. **mock도 같은 두 축 모델을 지킨다.** mock은 시드 없는 강의의 기본 상태를 커리큘럼 lifecycle에서
   끌어와, 커리큘럼을 게시하면 강의까지 PUBLISHED로 딸려 올라갔다 — 실 서버와 어긋나 mock 검증이
   두 축 문제를 가렸다. `publishMockCurriculum`이 lifecycle을 바꾸기 전에 강의 상태를 고정한다.

## 근거 (Rationale)

- **서버 축을 합치지 않는 이유**: 커리큘럼 publish가 강의를 연쇄 게시하면 API 한 번으로 되돌릴 수
  없는 노출이 일어나고, 강의 단위로 공개를 준비하는 여지가 사라진다. CP2에서 AI 준비도 축이 살아나면
  강의 게시 전제만 조이면 되는데, 합쳐 놨다면 그때 되돌리는 비용이 커진다.
- **그럼에도 UI에서 한 번에 끝내는 이유**: 처음에는 서버 분리를 화면에도 그대로 노출해
  "강의 일괄 게시" + "커리큘럼 게시" 두 버튼으로 뒀는데, 실제로 써 보니 강의를 다 게시하고도
  공개되지 않는 막다른 상태(`게시 강의 5/5`인데 노출 0)가 반복해서 만들어졌다. 남은 단계를 경고
  문구로 안내해 봐도, 두 번 눌러야 한다는 사실 자체가 실패 원인이었다. **분리는 서버의 사정이지
  강사의 관심사가 아니다** — 오케스트레이션을 클라이언트로 내려 주 동선을 한 번의 클릭으로 만든다.
- **문제는 상태 모델이 아니라 경계 배치였다.** 서버 전이는 각 축에서 정확하다(위 표). 축을 합치는
  대신 화면이 두 축을 묶어 실행하고 AND를 말하게 하면, 서버 모델을 단순하게 유지한 채 혼란이 사라진다.
- **[ADR-0021](../songjeongki/0021-lesson-publish-mvp-direct.md)을 뒤집지 않는다.** 그 결정의 목적은
  "AI 준비도를 게시 전제로 걸지 않는 것"이었고 여전히 유효하다. CP2에서 준비도 축이 생기면
  강의 게시 전제만 다시 조이면 된다 — 축을 합쳐 놨다면 그때 되돌리는 비용이 커진다.

## 대안 (Alternatives)

| 대안 | 장점 | 단점 |
|---|---|---|
| **(선택) 서버 축 유지 + 클라이언트가 한 번에 오케스트레이션** | 클릭 1번으로 공개 도달, 서버 모델·ADR-0021 유지, 우회로도 남음 | 게시 시퀀스가 클라이언트에 있어 부분 실패 처리를 FE가 책임짐 |
| (기각) 축 유지 + 화면도 2단계 노출 | 구현이 가장 단순 | **실제로 시도했다가 되돌림** — 막다른 상태(강의 5/5인데 노출 0)가 반복 발생 |
| (기각) 서버에서 연쇄 게시 | 클릭 1번, FE 단순 | 미완성 강의 노출, API 한 번에 되돌릴 수 없음, ADR-0021 대체 필요 |
| (기각) 강의 축 제거(커리큘럼 상태만) | 가장 단순 | 강의 단위 비공개 준비 불가. CP2 AI 준비도 축과 충돌 |

## 영향·후속 (Consequences)

- **FE 변경**: `CurriculumManagePage`의 게시 동작을 `runPublish(includeLessons)` 하나로 합쳤다
  (저장 가드 → 강의 일괄 게시 → 빈 목차 가드 → 커리큘럼 게시 → 무효화 → 결과 토스트).
  `MyCurriculumsPage` 카드 문구도 공개 여부를 먼저 말한다.
- **mock 변경**: `publishMockCurriculum`이 lifecycle 전환 전에 강의 상태를 고정한다. 이 divergence는
  mock 검증에서 두 축 문제를 가리고 있었으므로, 회귀 테스트로 고정한다.
- **BE 변경 없음.** 상태 전이는 이미 올바르며, 이 ADR은 표현·오케스트레이션 계층의 결정이다.
- **계약 자물쇠**: 서버 계약이 바뀌지 않으므로 신규 계약 테스트는 불필요하다
  ([POLICY](../../harness/POLICY.md)의 🟢 "UI 문구·스타일"). 대신 두 축 조합과 게시 시퀀스는
  FE 통합 테스트(`CurriculumWorkspace.test.tsx`)로 고정한다 — 주 버튼 1회로 공개 도달,
  게시된 강의 0개면 우회로 미노출, 이미 전부 공개면 비활성, mock이 강의를 딸려 올리지 않음.
- **CP2 후속**: AI 준비도(`AI_NOT_READY`/`READY`)가 살아나면 강의 게시 전제가 바뀐다. 그때
  이 화면의 "잔여 단계" 문구에 준비도 조건을 한 줄 더 얹으면 된다.
