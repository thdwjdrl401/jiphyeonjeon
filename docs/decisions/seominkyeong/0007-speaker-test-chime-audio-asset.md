# ADR-0007: 스피커 테스트음은 제공된 "bing–bong" 차임 음원을 쓰고, 다듬기는 코드에서 한다

> 📍 하네스 개요: [../../harness/README.md](../../harness/README.md) · 판단 정책: [../../harness/POLICY.md](../../harness/POLICY.md)

- **상태**: 채택
- **일자**: 2026-07-30
- **관련**: 브랜치 `feat/fe/speaker-test-coin-chime`, `frontend/src/features/live-session/speakerTest.ts`

## 맥락 (Context)

입장 전 점검(`StudentPrejoinPage`)의 스피커 테스트음이 **부저처럼 거칠게 들린다**는 요청을 받았다.

기존 구현은 사인파 하나를 구간 내내 일정 음량으로 끄는 방식이었다 —
`attack(30ms) → 일정 음량 유지 → release(120ms)`, C5·E5·G5. 이 화면은 학생이 입장할 때마다,
경우에 따라 "다시 듣기"로 여러 번 듣는다. 그래서 음색의 자극이 그대로 피로가 된다.

부저처럼 들린 원인은 음높이가 아니라 두 가지였다.

1. **사인파 하나** — 배음이 없어 기계음으로 들린다.
2. **유지 구간이 있는 엔벨로프** — 음량을 유지하는 구간이 있으면 "울리는 소리"가 아니라
   "켜져 있는 소리"가 된다.

처음에는 저작권 문제를 피하려고 Web Audio 가산 합성으로 금속 타격 차임을 직접 만들었다.
그 뒤 **요청자가 사용할 음원을 직접 지정**했다 — `bing-bong-subway-chime-jam-fx`
(제목 `Bing bong - subway chime`, 제작자 `Jam FX`, ID3 태그 기준). 합성음과 지정 음원 중
하나를 골라야 했다.

## 결정 (Decision)

1. **제공된 MP3를 그대로 재생한다.** Web Audio 합성은 폐기한다.
   파일은 `frontend/src/assets/audio/bing-bong-subway-chime-jam-fx.mp3`에 두고 Vite 에셋으로 번들한다.
2. **파일은 손대지 않는다.** 재인코딩·트리밍 없이 받은 그대로 커밋한다(MD5 `11fe0b20…`).
   출처를 추적할 수 있어야 하고, 재인코딩은 음질 손실만 남긴다.
3. **다듬기는 로드 시점에 코드에서 한다.** 원본을 실측해 나온 두 가지다.
   - **앞쪽 무음 632ms를 잘라낸다.** 그대로 재생하면 "왼쪽 재생 중" 표시가 소리보다 먼저 켜져
     학생이 "왼쪽은 안 들렸다"고 오해한다.
   - **모노로 합친다.** 원본은 좌우 상관계수 0.95의 스테레오다(R이 L보다 에너지가 크다).
4. **음량은 최고점 0.7로 정규화한다.** 음원을 바꿔도 음량이 들쭉날쭉하지 않게 한다.
5. **구간 길이는 1,550ms, 구간 사이 침묵은 200ms** — 전체 약 5.05초.
6. **구간 끝은 120ms 페이드아웃으로 닫는다.**
7. **재생 순서와 pan은 그대로다.** 좌(-1) → 우(+1) → 양쪽(0).
8. **표시 타이머는 음원이 준비된 뒤에 시작한다.**
9. **음원은 화면 진입 시 미리 받아 둔다**(`prefetchSpeakerTestChime`). Web Audio가 없는
   환경에서는 받지 않는다.

## 근거 (Rationale)

- **합성보다 제공 음원을 택한 이유**: 요청자가 파일을 직접 지정했다. 음색은 최종적으로 사람이
  귀로 판단하는 항목이고, 합성 파라미터를 반복 조정하는 것보다 원하는 소리를 직접 지정하는 쪽이
  빠르고 확실하다. 합성으로 두 차례 시도했지만 "부저 같다"·"연속음 같다"는 피드백이 이어졌다.
- **모노로 합치는 이유**(핵심): `StereoPannerNode`는 **입력 채널 수에 따라 다르게 동작한다.**
  스테레오 입력에서 `pan: ±1`은 두 채널을 한쪽으로 합쳐 보내지만, **`pan: 0`은 원본 스테레오를
  그대로 통과시킨다.** 즉 스테레오 원본을 그냥 쓰면 좌·우 구간은 L+R 합(더 큼)이고 양쪽 구간만
  원본 정위(스피커별로 자기 채널만)가 되어, **세 구간의 음색과 음량이 어긋난다.** 스피커 테스트는
  세 구간이 같은 소리여야 "한쪽이 안 들린다"를 판단할 수 있으므로 이 어긋남은 그대로 결함이다.
  모노로 합치면 모노 pan 법칙(`x=(pan+1)/2`, `L=cos(xπ/2)`, `R=sin(xπ/2)`)이 적용돼 세 구간이
  같은 소리가 되고 위치만 달라진다.
- **앞쪽 무음을 고정 상수로 자르지 않고 실행 시 탐색하는 이유**: 632ms는 이 파일의 값이다.
  음원을 교체하면 상수가 조용히 틀려지고, 그 증상은 "표시가 소리보다 먼저 켜진다"라서 알아채기
  어렵다. 최고점 대비 1% 임계값으로 첫 유효 샘플을 찾으면 파일이 바뀌어도 규칙이 유지된다.
- **구간 길이 1,550ms의 근거**: 원본 실측에서 "bing"과 "bong"의 타격 간격이 575ms이고, 두 번째
  음의 감쇠가 최고점 대비 -30dB까지 떨어지는 데 소리 시작부터 1,505ms가 걸린다. 그보다 짧게
  자르면 "bong"이 잘려 2음 차임이 아니라 토막난 소리가 된다. 전체가 2.95초에서 5.05초로
  길어지는 것은 이 음원(실제 소리 1.8초)을 쓰는 대가다.
- **인코딩된 바이트를 캐시하고 디코딩은 재생마다 하는 이유**: `AudioBuffer`는 만들어진
  `AudioContext`의 샘플레이트에 묶인다. 재생마다 새 컨텍스트를 만드는 구조에서 재사용하면
  샘플레이트가 다른 기기(44.1k vs 48k)에서 음이 빨라지거나 느려진다. `decodeAudioData`에
  매번 맡기면 컨텍스트 샘플레이트로 리샘플링해 준다.
- **`decodeAudioData`에 사본을 넘기는 이유**: 이 API는 넘긴 `ArrayBuffer`를 detach 한다.
  캐시한 원본을 그대로 넘기면 두 번째 재생부터 빈 버퍼가 되어 **"다시 듣기"가 조용히 실패한다.**
- **표시 타이머를 음원 준비 뒤에 시작하는 이유**: 로드·디코딩은 비동기다. 먼저 타이머를 걸면
  느린 회선에서 화면은 "양쪽 재생 중"인데 소리는 아직 왼쪽인 상태가 된다.
- **미리 받아 두는 이유**: 버튼을 누른 뒤 158KB를 받기 시작하면 느린 회선에서 "재생 중"인데
  소리가 안 나는 구간이 생긴다. Web Audio가 없으면 받지 않는다 — 재생할 수 없는 파일을
  내려받는 건 낭비다.
- **정규화 목표를 1.0이 아니라 0.7로 두는 이유**: 브라우저·기기 단계에서 더해지는 처리로
  클리핑이 나지 않게 헤드룸을 남긴다.

## 대안 (Alternatives)

| 대안 | 장점 | 단점 |
|---|---|---|
| **(선택) 제공 MP3 + 로드 시 모노·트리밍·정규화** | 원하는 음색이 확실함, 파일이 원본 그대로라 출처 추적 가능 | 번들 +158KB, 라이선스 확인 필요, 전체 길이 5.05초로 길어짐 |
| (기각) Web Audio 가산 합성 | 저작권·번들 문제 없음, 파라미터 조정 가능 | 두 차례 시도에서 원하는 음색에 도달하지 못했다 |
| (기각) MP3를 모노·트리밍해 재인코딩 후 번들 | 번들 크기 절감(약 1/3) | 음질 손실, 원본과 대조 불가(출처 추적 약화) |
| (기각) 원본 스테레오를 그대로 pan | 코드가 단순 | `pan: 0`만 원본 정위가 남아 세 구간의 음색·음량이 어긋난다 |
| (기각) 구간을 1초 이하로 줄여 전체 3초 유지 | 기존 길이 유지 | "bong"이 잘려 2음 차임이 토막난 소리가 된다 |

## 영향·후속 (Consequences)

- **FE**: `speakerTest.ts`를 오실레이터 합성에서 `AudioBufferSourceNode` 재생으로 교체.
  `SpeakerTestStep`에서 `frequency` 필드 제거(음원 재생에는 의미가 없다).
  `prefetchSpeakerTestChime` 신설 및 `StudentPrejoinPage`에서 진입 시 호출.
  `SPEAKER_TEST_DURATION_MS`가 2,950ms → 5,050ms로 늘었다.
- **에셋**: `frontend/src/assets/audio/bing-bong-subway-chime-jam-fx.mp3` 추가(158,817 bytes).
  Vite가 해시 파일명으로 별도 emit 한다(인라인되지 않음) — 확인: `bing-bong-subway-chime-jam-fx-CwRF6nXN.mp3`.
- **BE·계약**: 없음. API 요청/응답 필드·상태코드와 무관한 FE 내부 구현이라
  [POLICY](../../harness/POLICY.md) 기준 **계약 테스트 대상이 아니다.**
- **단위 테스트**: `speakerTest.test.ts`를 음원 재생 구조로 다시 썼다(18개). 화면만 봐서는
  회귀를 알 수 없는 항목을 못 박았다 — **앞쪽 무음 잘라내기**, **모노 다운믹스**, **좌우 pan
  `[-1, 1, 0]`**, **정규화 최고점**, **구간 초과 방지**, **페이드아웃**, **음원 준비 전 표시 금지**,
  **다시 듣기 시 재사용(detach 회귀 감지)**, **fetch·decode 실패 시에도 화면 흐름 유지**.
- **통합 테스트 영향**: 테스트음이 2.95초 → 5.05초로 길어져 `RouteSmoke`의 수강생 입장 흐름이
  기본 테스트 제한(5초)을 넘었다. 해당 테스트의 제한을 20초로, 버튼 대기를 9초로 늘렸다.
- **음원 검증 방법**: 단위 테스트는 소리를 듣지 못한다. 그래서 `speakerTest.ts`의 상수를 파싱해
  실제 MP3에 같은 파이프라인을 적용하고 WAV로 렌더링해 실측했다 — 앞쪽 무음 632ms 제거,
  클립 1,550ms, 최고점 0.700(클리핑 없음), 좌/우 구간 **반대 채널 누출 0.000**,
  구간 사이 침묵 0.000000, 클립 안 타격 2개(5ms·575ms → bing–bong 온전).
  이 스크립트는 일회성 검증 도구이므로 저장소에 커밋하지 않는다.
- **후속(라이선스 확인 필요)**: 음원은 요청자가 지정한 파일이며 ID3 태그의 제작자는 `Jam FX`다.
  **제품에 번들해 배포하는 것이 허용되는 라이선스인지 확인이 필요하다.** 확인 결과 재배포가
  불가하면 (1) 사용 가능한 유사 음원으로 교체하거나 (2) 폐기한 합성 방식으로 되돌린다 —
  다듬기 코드(모노·트리밍·정규화)는 음원이 바뀌어도 그대로 쓸 수 있다.
- **후속(번들 크기)**: 158KB 중 약 1/3이 뒤쪽 무음(1.18초)이고 11KB가 ID3 태그다. 크기가
  문제되면 무손실 프레임 절단으로 줄일 수 있다. 지금은 출처 추적을 우선해 원본을 유지한다.
