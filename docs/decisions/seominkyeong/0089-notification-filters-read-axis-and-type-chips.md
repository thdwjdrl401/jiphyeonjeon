# ADR-0089: 알림 필터는 읽음 탭 하나와 역할별 종류 칩으로 간다

> 📍 하네스 개요: [../../harness/README.md](../../harness/README.md) · 판단 정책: [../../harness/POLICY.md](../../harness/POLICY.md)

- **상태**: 채택
- **일자**: 2026-08-06
- **관련**: Sub Ⅱ · [ADR-0012](0012-notification-center-two-status-axes.md)를 **부분 대체**(업무 처리 축을 화면에서 뺀다) · [ADR-0085](../songjeongki/0085-notification-target-gates-by-type.md)(종류별 대상 게이트)

## 맥락 (Context)

알림 페이지의 분류가 `전체`(강사는 `처리 대기`까지)뿐이었다. 알림은 열두 종류인데 목록에서 종류를
고를 수 없어, 라이브 임박만 보거나 학습 자료만 훑는 일이 안 됐다.

종류 필터를 넣으려니 제약이 둘이었다.

1. **서버가 종류로 걸러 주지 않는다.** `GET /api/me/notifications`는 `scope`·`readState`·`page`·`size`만
   받는다(`NotificationController`).
2. **필터 줄이 세 개가 된다.** 기존 1차 탭(전체·처리 대기) + 2차 탭(읽지 않음·읽음) 위에 종류를 얹으면
   무엇이 상위인지 읽히지 않는다 — ADR-0012가 두 축을 두 줄로 나눈 이유가 그것인데, 세 줄이 되면
   그 근거가 자기를 무너뜨린다.

## 결정 (Decision)

**탭은 읽음 축 하나로 줄이고, 그 아래 종류 칩 줄을 둔다.**

| 줄 | 무엇 | 모양 |
|---|---|---|
| 탭 | 읽지 않음 · 읽음 | 밑줄 |
| 칩 | 종류(역할별) | 테두리 pill |

- **`전체 · 처리 대기` 탭을 걷는다.** 처리 대기는 목록의 배지로 계속 보이고, 강사가 처리할 알림은
  대개 `수강 신청` 칩으로 좁혀 찾는다. 업무 처리 축이 데이터에서 사라지는 것은 아니다 — 화면에서
  고르는 축에서만 빠진다.
- **칩은 그 역할이 받는 모든 종류를 늘 보여 준다.** 0건인 종류도 남겨 흐리게 그린다.
- **역할마다 칩 구성이 다르다.** 표(`NOTIFICATION_AUDIENCE`)는 서버 규칙에서 옮겨 왔다 —
  `NotificationFanoutWorker.INSTRUCTOR_TYPES`(녹화 둘은 강사에게만), `NotificationAccessRule`(수강
  판정은 학생), mock 발행 함수(수강 신청은 커리큘럼 소유 강사). 라이브 임박은 양쪽이 받는다.
- **종류 필터는 화면에서 걸고, 칩을 고른 동안 다음 페이지를 자동으로 당긴다**(상한 5페이지).

## 근거 (Rationale)

- **0건 칩을 지우지 않는 이유**: 지우면 "이 화면에 어떤 알림이 오는가"를 알 수 없고, 새 종류가 처음
  도착하는 순간 칩이 불쑥 생겨 줄이 흔들린다. 흐리게 두면 목록이 비어도 화면의 뼈대가 유지된다.
- **0건 칩을 막지 않는 이유**: 건수는 <b>지금까지 불러온</b> 목록에서 센 값이다. 다음 페이지에 있는
  종류가 0으로 보이는데 `disabled`로 막으면 실제로 있는 알림을 고를 수 없다.
- **자동 페이지 당김**: 8건만 받아 둔 상태에서 "라이브 임박 없음"이라고 말하면 다음 페이지에 있는
  것을 없다고 하는 거짓이 된다. 상한을 두는 이유는 오래 쓴 계정에서 수백 건을 전부 받게 되기 때문이다.
- **역할 표를 화면에 두는 것의 위험을 인정한다.** 서버 규칙을 베낀 표라 언제든 어긋날 수 있어,
  **표에 없어도 실제로 받은 종류는 칩으로 만든다** — 목록에 보이는데 좁힐 방법이 없는 상태를 막는다.

## 대안 (Alternatives)

| 대안 | 장점 | 단점 |
|---|---|---|
| (선택) 읽음 탭 + 역할별 종류 칩 | 줄이 둘로 유지되고 종류로 좁혀진다 | 처리 대기만 모아 보는 길이 없어진다 |
| 세 줄 유지(전체·처리 대기 + 읽음 + 종류) | 기존 축을 하나도 잃지 않는다 | 무엇이 상위인지 읽히지 않는다(ADR-0012가 경계한 상태) |
| 서버에 `type` 파라미터 추가 | 페이지네이션·건수가 정확해진다 | Controller·Service·Repository 순업 + 계약 테스트. 백엔드 변경 |
| 받은 종류만 칩으로 | 칩이 적다 | 새 종류가 올 때 줄이 흔들리고, 이 화면에 어떤 알림이 오는지 알 수 없다 |
| 0건 칩을 `disabled` | 누를 이유가 없다는 게 분명하다 | 다음 페이지에 있는 알림을 고를 수 없다 |

## 영향·후속 (Consequences)

- **ADR-0012의 두 축 중 업무 처리 축이 화면에서 빠졌다.** 그 ADR의 나머지(읽음과 처리를 한 값으로
  합치지 않는다, 처리 상태는 배지로 남긴다)는 그대로 유효하다 — 읽어도 `처리 대기`가 유지되는 성질을
  통합 테스트가 계속 지킨다.
- 서버가 `type` 필터를 갖게 되면 자동 페이지 당김과 상한을 지우고 쿼리로 옮긴다. 그때 칩 건수도
  정확해진다(지금은 불러온 범위의 값이다).
- 알림 종류가 늘어나면 `NOTIFICATION_AUDIENCE`에 역할을 함께 적어야 한다. 빠뜨리면 칩이 조용히
  사라지는 대신, 실제로 받은 종류는 칩으로 남으므로 화면이 먹통이 되지는 않는다.
- 하네스: **계약 테스트 불필요**(POLICY 🟢). 요청은 그대로(`scope=ALL`로 고정), 응답·필드명·상태코드를
  바꾸지 않았다. 칩 규칙과 빈 문구는 순수 함수로 빼 단위 테스트 12건, 화면 동작은 통합 테스트로 고정했다.
