# ADR-0008: 라우트 이동 시 스크롤은 라우팅 계층에서 일괄 초기화하고, 위치 복원은 도입하지 않는다

> 📍 하네스 개요: [../../harness/README.md](../../harness/README.md) · 판단 정책: [../../harness/POLICY.md](../../harness/POLICY.md)

- **상태**: 채택
- **일자**: 2026-07-31
- **관련**: 브랜치 `feat/fe/route-scroll-reset`, `frontend/src/app/router/ScrollToTop.tsx`

## 맥락 (Context)

버튼·링크로 화면을 옮기거나 저장·삭제 후 자동 이동했을 때 새 화면이 맨 위가 아니라 **이전 화면의
스크롤 위치에서 시작**하는 문제가 있었다. SPA는 라우트가 바뀌어도 문서 스크롤이 그대로 남기 때문이다.
목록을 한참 내려보다 상세로 들어가면 상세가 중간부터 보이고, 자동 이동한 화면도 엉뚱한 곳에서 뜬다.

구현 전에 확인한 현재 구조:

- 라우터는 `BrowserRouter` 하나이고 라우트 정의는 `AppRouter`에 모여 있다.
- 레이아웃은 `PublicLayout`·`WorkspaceLayout`·`LessonLayout` 셋이며 각각 `main`을 하나 갖는다.
- **페이지 스크롤 주체는 문서(window)다.** 세 셸 모두 `min-height: 100vh`만 있고 `overflow`가 없다.
  `overflow-y: auto`를 가진 요소는 채팅 로그·자막 독·강의 목차 사이드바 같은 **내부 위젯**뿐이다.
- 커리큘럼 탐색은 검색·필터 조건을 **쿼리스트링에 보존**한다.

## 결정 (Decision)

1. **`ScrollToTop` 컴포넌트를 `AppRouter`에 한 번만 둔다.** 페이지마다 `useEffect`로 스크롤을
   초기화하지 않는다.
2. **`pathname`이 바뀔 때만 초기화한다. `search`는 보지 않는다.**
3. **`useLayoutEffect`로 처리한다** — 브라우저가 그리기 전에 옮긴다.
4. **`window.scrollTo({ top: 0, left: 0, behavior: 'auto' })`** — 부드러운 스크롤을 쓰지 않는다.
5. **`history.scrollRestoration`을 `'manual'`로 바꾼다.** 언마운트 시 원래 값으로 되돌린다.
   API가 없는 브라우저에서는 이 단계만 건너뛰고 초기화는 그대로 한다.
6. **현재 떠 있는 `main`의 `scrollTop`도 0으로 되돌린다.** 채팅 로그·자막 독처럼 내부에 따로
   스크롤되는 위젯은 건드리지 않는다.
7. **스크롤 위치 복원(목록 → 상세 → 목록)은 이번에 도입하지 않는다.** 모든 이동을 맨 위로 통일한다.

## 근거 (Rationale)

- **한 곳에서 처리하는 이유**: 페이지별로 넣으면 새 페이지가 생길 때마다 빠뜨리고, 빠뜨린 것을
  화면만 봐서는 알기 어렵다("이 화면만 위로 안 가네"를 사용자가 신고해야 발견된다).
- **`search`를 보지 않는 이유**: 커리큘럼 탐색은 필터를 쿼리에 보존한다. 쿼리가 바뀔 때마다 맨 위로
  튀면 **결과를 내려보며 조건을 바꾸는 흐름이 끊긴다.** 필터 변경은 "같은 화면의 내용 갱신"이지
  페이지 이동이 아니다.
- **`useLayoutEffect`인 이유**: `useEffect`로 두면 새 화면이 이전 스크롤 위치에서 한 프레임 그려진
  뒤 위로 튀어 깜빡임이 보인다. 레이아웃 단계에서 옮기면 그 프레임이 없다.
- **`scrollRestoration = 'manual'`이 반드시 필요한 이유**: 뒤로 가기에서 브라우저는 저장해 둔 위치를
  되살리는데, 그 복원은 **우리 초기화보다 늦게** 일어나 초기화를 덮어쓴다. 즉 이 설정 없이는
  "뒤로 가기도 맨 위" 요구가 지켜지지 않는다. 끄기 때문에 나중에 복원을 도입하려면 이 값을 되돌리고
  복원 대상을 명시해야 한다.
- **`behavior: 'auto'`인 이유**: 화면이 바뀌는 순간에 애니메이션이 겹치면 이동이 끝나기 전에 다음
  조작이 들어와 위치가 어긋난다. 페이지 전환은 "이동"이 아니라 "새 화면 표시"다.
- **`main`까지 되돌리는 이유(보험)**: 지금은 문서가 스크롤되므로 이 줄은 동작하지 않는다. 다만
  레이아웃을 `height: 100vh` + 내부 스크롤 구조로 바꾸면 `window.scrollTo`가 무력해지고, 그때
  증상은 "특정 레이아웃에서만 스크롤이 안 올라감"이라 원인을 찾기 어렵다. 미리 덮어 둔다.
- **내부 위젯을 건드리지 않는 이유**: 채팅 로그는 "맨 위"가 아니라 **"최신"** 이 기준이고
  (`CaptionDock`은 의도적으로 `scrollTop = scrollHeight`로 맨 아래를 본다), 라우트가 바뀌면
  어차피 다시 마운트된다. 일괄 초기화 대상에 넣으면 이 의도를 깬다.
- **위치 복원을 미루는 이유**: 복원이 유용한 화면(목록 → 상세 → 목록)이 있지만, **어떤 화면이 복원
  대상인지에 대한 정책이 아직 없다.** 정책 없이 복원을 넣으면 "어떤 화면은 복원되고 어떤 화면은
  안 되는" 예측 불가한 동작이 되고, 복원 실패 시 사용자는 원인을 알 수 없다. 전부 맨 위로 통일하는
  쪽이 예측 가능하다. 복원이 필요해지면 그때 대상 화면과 저장 키를 명시적으로 정한다.

## 대안 (Alternatives)

| 대안 | 장점 | 단점 |
|---|---|---|
| **(선택) 라우팅 계층 `ScrollToTop` + 복원 없음** | 한 곳에서 처리, 동작이 예측 가능, 새 페이지가 자동 적용 | 목록 복귀 시 위치가 사라짐(향후 과제) |
| (기각) 페이지별 `useEffect(() => window.scrollTo(0, 0))` | 페이지마다 예외를 두기 쉬움 | 새 페이지에서 빠뜨리기 쉽고, 누락을 화면만 봐서는 알 수 없다 |
| (기각) `ScrollRestoration`(React Router) 사용 | 프레임워크 제공 | 데이터 라우터(`createBrowserRouter`)가 필요해 라우터 구성을 바꿔야 한다. 이번 범위를 넘는다 |
| (기각) `pathname + search` 모두 감시 | 규칙이 단순 | 커리큘럼 탐색에서 필터를 만질 때마다 맨 위로 튀어 탐색 흐름이 깨진다 |
| (기각) 목록 화면만 위치 복원 | 사용성이 좋음 | 복원 대상 정책이 없어 절반만 동작하는 로직이 된다. 별도 판단 뒤에 도입 |

## 영향·후속 (Consequences)

- **FE**: `app/router/ScrollToTop.tsx` 신설, `AppRouter`가 `<Routes>` 위에서 한 번 렌더한다.
  기존 페이지는 변경하지 않았다(스크롤 초기화 코드가 애초에 없었다).
- **BE·계약**: 없음. FE 라우팅 동작이라 [POLICY](../../harness/POLICY.md) 기준 계약 테스트 대상이 아니다.
- **테스트**: `test/integration/ScrollReset.test.tsx`(8개). 링크 이동·`replace` 자동 이동·브라우저
  뒤로 가기·`scrollRestoration` 전환과 복구·`main` 초기화·**쿼리만 바뀔 때 유지**·실제 `App`에
  연결됨을 고정했다. jsdom은 `history.scrollRestoration`을 구현하지 않아 그 테스트에서만 직접 심는다.
- **후속(위치 복원)**: 목록 화면 위치 복원이 필요해지면 (1) 복원 대상 라우트, (2) 저장 위치
  (`sessionStorage` 키), (3) `scrollRestoration` 되돌림 여부를 정해 별도 ADR로 남긴다.
- **후속(실제 확인)**: 이 환경에 헤드리스 브라우저가 없어 **실제로 스크롤되는 화면에서 눈으로 확인하지는
  못했다.** jsdom은 레이아웃을 계산하지 않아 `window.scrollTo` 호출 여부까지만 검증할 수 있다.
  최종 확인(긴 목록을 내려보다 상세로 들어가기, 뒤로 가기)은 사람이 브라우저에서 해야 한다.
