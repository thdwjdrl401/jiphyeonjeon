# ADR-0010: 탈퇴 안내는 실제 동작에 맞추고, 비밀번호 재설정은 FE 먼저 만든다

> 📍 하네스 개요: [../../harness/README.md](../../harness/README.md) · 판단 정책: [../../harness/POLICY.md](../../harness/POLICY.md) · 계약: [../../CONTRACT.md](../../CONTRACT.md)

- **상태**: 채택
- **일자**: 2026-07-31
- **관련**: [0009](0009-profile-identity-card-consolidation.md)(프로필 카드 통합), [0008](0008-route-scroll-reset-policy.md)(라우트 스크롤 초기화), [songjeongki/0031](../songjeongki/0031-account-profile-security.md)(계정·프로필·보안 API), [songjeongki/0030](../songjeongki/0030-frontend-unimplemented-api-and-partial-writes.md)(FE 선행 구현 선례)

## 맥락 (Context)

내 프로필 화면(`ProfilePage`, 학생·강사 공용)의 "계정 보안" 카드에 비밀번호 변경과 회원 탈퇴가
한 덩어리로 들어 있었다. 세 가지를 함께 요청받았다 — ① 상단 카드의 "프로필 수정" 버튼이 어디로
가야 하는가, ② "비밀번호를 잊으셨나요?" 구현, ③ 회원 탈퇴 안내·동의 절차 보강.

조사에서 드러난 사실 세 가지가 결정을 갈랐다.

1. **"프로필 수정"은 이미 모달을 열고 있었다**(`setIsEditOpen(true)` → `ProfileEditModal`).
   그리고 계정 보안 카드에는 프로필 편집 기능이 아예 없었다 — 비밀번호 변경과 탈퇴뿐이다.
   그래서 "수정 버튼을 계정 보안 카드로 스크롤" 안은 엉뚱한 곳에 착지한다.
2. **비밀번호 재설정은 서버 인프라가 0이다.** `JavaMailSender`·`spring-boot-starter-mail`·
   `smtp`·`passwordReset`·`tempPassword` 모두 저장소 전체에서 0건이다.
3. **요청받은 탈퇴 안내 문구 4개가 실제 동작과 전부 어긋났다.** 일반 커머스 서비스의 문구로
   보이는데, 이 제품의 탈퇴는 [0031]에 따라 **소프트 삭제**다.

| 요청 문구 | 실제 동작 |
|---|---|
| 수강권·구매 강의·찜한 콘텐츠 즉시 삭제, 복구 불가 | 삭제하지 않는다. `status=WITHDRAWN` + `withdrawn_at`뿐. `curriculum.instructor_id`·`enrollment.user_id`가 CASCADE 없는 FK라 하드 삭제가 **불가능**하고, 강사 커리큘럼·수강 기록은 남아야 한다 |
| 수강평·Q&A·포인트·쿠폰 영구 삭제 | 그런 기능이 없다. 쿠폰·찜·구매·결제·수강권·수강평·환불 = 코드 0건. `포인트` 검색 결과는 전부 "엔드**포인트**"이고, `Bookmark`는 엔티티만 있고 배선되지 않았다 |
| 개인정보 지체 없이 파기 | 파기하지 않는다. WITHDRAWN 행을 보존하고 이메일만 `withdrawn_<userId>_<원본>`으로 변형한다 |
| 동일 아이디 재가입 제한될 수 있음 | 정반대다. tombstone을 도입한 목적이 **같은 이메일 재가입 허용**이다 |

## 결정 (Decision)

### 1. "프로필 수정"은 지금의 편집 모달을 그대로 쓴다

위 §1대로 이 버튼은 이미 편집 모달을 열고 있고, 그게 옳은 착지점이다. 옮기지 않는다.
모달을 닫으면 포커스를 버튼으로 되돌린다(`editButtonRef`) — 키보드 사용자가 원래 자리로 온다.

**화면 레이아웃은 이 ADR의 범위가 아니다.** 카드 배치·정보 밀도를 어떻게 바꿀지는 별도 작업으로
남긴다. 여기서는 안내 문구와 절차의 정확성만 다룬다.

### 2. 비밀번호 변경·회원 탈퇴를 각자의 패널 컴포넌트로 뗀다

`PasswordChangePanel` · `AccountWithdrawPanel`. 둘 다 예전처럼 "계정 보안" 카드 한 장 안에 있고,
그 사이에 구분선(`.settings-section`)을 둔다 — 탈퇴 안내가 항목 여러 개로 길어져 두 기능이 한
덩어리로 읽히면 어디까지가 무엇인지 흐려진다.

> **갱신**: 카드 이름과 구분선은 [0011](0011-profile-page-compaction.md)이 바꿨다 — "계정 보안"
> → **"계정 설정"** 한 장에 둘을 함께 두는 것은 그대로이고, 구분선(`.settings-section`) 대신
> 탈퇴 진입 행 자체의 경계선을 쓴다. 컴포넌트를 둘로 뗀 결정과 그 이유는 그대로다.

떼어 낸 이유는 상태다. 탈퇴는 동의 체크와 409 인라인 오류를, 비밀번호 변경은 확인 필드 대조를
각자 들고 있어야 하는데, 페이지가 그 상태를 전부 소유하면 한 화면이 서로 무관한 폼 두 개의
상태 기계가 된다.

### 3. 회원 탈퇴 안내는 실제 동작만 쓴다

```
회원 탈퇴 시 계정이 비활성화되어 더 이상 로그인할 수 없습니다.
· 강의, 커리큘럼 및 학습 기록은 서비스 운영을 위해 보존됩니다.
· 동일한 이메일로 언제든지 다시 회원가입할 수 있습니다.
· (강사만) 진행 중인 라이브 강의가 있으면 탈퇴할 수 없습니다. 먼저 강의를 종료해 주세요.
탈퇴를 진행하시겠습니까?
[ ] 위 안내 사항을 모두 확인하였으며, 이에 동의합니다.
```

> **갱신**: 이 문구가 놓이는 자리는 [0011](0011-profile-page-compaction.md)이 카드에서 **확인
> 모달**로 옮겼다. 문장은 그대로이고, 위 블록에서 `탈퇴를 진행하시겠습니까?` 한 줄만 지웠다 —
> 바로 아래 동의 체크박스가 같은 질문이다.

**개인정보 파기 항목은 넣지 않는다.** 실제 보존 정책·기간이 정해지기 전에는 어떤 문구도 거짓이
되고, 이건 UI 문구가 아니라 법적 고지 영역이다. 개인정보처리방침이 확정되면 그 문구를 인용한다.

**비밀번호 재확인도 넣지 않는다.** `DELETE /me`는 본문을 받지 않아(`withdrawAccount()` 무인자)
FE가 비밀번호를 받아도 검증할 곳이 없다 — 거짓 보안 인상만 준다.

### 4. 진행 중 라이브 차단은 서버 권위 + 인라인 표시

FE가 미리 판정하지 않는다. "이 강사에게 켜져 있는 라이브가 있는가"를 한 번에 묻는 API가 없어
커리큘럼을 전부 훑어야 하고, 훑는 사이 상태가 바뀌면 화면과 서버가 어긋난다. 대신 강사에게는
조건을 미리 안내하고, 409 `AUTH_WITHDRAWAL_BLOCKED`을 **폼 안 `InlineNotice`로** 띄운다.

### 5. 비밀번호 재설정은 임시 비밀번호가 아니라 1회용 링크, FE 먼저

- **주 진입점은 로그인 화면**(`/login` 비밀번호 라벨 옆). 이 기능이 필요한 사람은 로그인을 못 해
  프로필 화면에 오지 못한다. 계정 보안 카드의 링크는 보조 — 현재 비밀번호를 기억하지 못해 변경
  폼을 채울 수 없는 경우다.
- 라우트 `/password-reset`(요청) · `/password-reset/confirm?token=`(설정). **`GuestOnlyRoute`에
  넣지 않는다** — 로그인한 사용자가 보조 링크로 와야 하므로 게스트 전용이면 홈으로 튕긴다.
- **계정 존재 여부를 드러내지 않는다.** 가입 여부와 무관하게 같은 안내를 낸다.
- 인터페이스·화면·mock만 만들고 서버는 별도 요청으로 남긴다([0030] 선례). `httpAuthService`는
  실제 경로를 그대로 호출하고, 엔드포인트가 없는 동안의 404/405/501만 "준비 중"으로 번역한다 —
  서버가 생기면 이 파일은 손대지 않아도 붙는다.

## 근거 (Rationale)

- **거짓 고지를 쓸 수 없는 이유**: "모든 데이터가 즉시 삭제되며 복구할 수 없습니다"는 사실이
  아니다. 개인정보 파기에 관한 허위 고지는 UI 문구 실수와 다른 범주의 문제다.
- **임시 비밀번호보다 1회용 링크인 이유**: 임시 비밀번호는 메일 본문에 계속 남아 메일함이 뚫리면
  그대로 쓸 수 있고, 사용자가 바꾸지 않으면 영구 비밀번호가 된다. 토큰 링크는 TTL·1회용 관리가
  쉽다.
- **계정 존재 여부를 감추는 이유**: 이 제품은 **이메일이 곧 로그인 식별자**다(CONTRACT.md —
  "인증 식별자는 `email`"). "그런 계정이 없습니다"를 보여 주면 임의 이메일로 가입자인지 확인하는
  수단이 된다.
- **확인 필드를 화면에서만 대조하는 이유**: 서버는 새 비밀번호 하나만 받는다
  (`PUT /me/password` — currentPassword·newPassword). 오타로 바꾼 비밀번호는 로그인 실패로만
  드러나고 되돌릴 방법이 없어서, 입력 단계에서 잡는 것이 유일한 방어다.
- **접근성 이름을 `aria-labelledby`로 고정한 이유**: `.workspace-form`은 `label`이 도움말
  `small`까지 감싸는 구조라, 감싸는 label을 그대로 쓰면 필드 이름이 "새 비밀번호 8자 이상으로…"가
  된다. 이름은 라벨 텍스트로 고정하고 도움말은 `aria-describedby`로만 연결한다.

## 대안 (Alternatives)

| 주제 | 대안 | 기각 이유 |
|---|---|---|
| 수정 버튼 | 계정 보안 카드로 스크롤 | 그 카드에 프로필 편집이 없다. 스크롤 초기화 동작([0008])과도 충돌 |
| 레이아웃 | 계정 설정을 좌측 세로 탭으로 가르기 | 요청 범위 밖이다. 화면 구성 변경은 별도 작업으로 다룬다 |
| 탈퇴 문구 | 원문 유지 + 하드 삭제로 정책 변경 | FK CASCADE·마이그레이션·[0031] 반전이 필요한 BE 대공사 — 이번 범위 밖 |
| 탈퇴 재확인 | 비밀번호 재확인 | `DELETE /me`가 본문을 받지 않아 검증 불가 — 보안 연극 |
| 탈퇴 재확인 | 이메일 타이핑 확인(GitHub 방식) | 요청자가 최종 문구에서 재확인 절차를 뺐다 — 동의 체크박스만 유지 |
| 라이브 차단 | FE가 미리 조회해 버튼 비활성 | 전용 API가 없어 커리큘럼 전수 조회 필요 + 조회 중 상태 변화로 화면·서버 불일치 |
| 재설정 | 임시 비밀번호 발송 | 비밀번호가 메일에 영구히 남는다 |
| 재설정 | 서버까지 지금 구현 | `backend/` 변경은 별도 요청 사항 — 메일 인프라 신설 + 계약 테스트가 따라온다 |

## 영향·후속 (Consequences)

- **FE 신규**: `PasswordChangePanel` · `AccountWithdrawPanel` · `PasswordResetRequestPage` ·
  `PasswordResetConfirmPage`.
- **FE 변경**: `ProfilePage`(계정 보안 카드가 두 패널을 조립) · `LoginPage`(재설정 링크) ·
  `AppRouter`·`paths`(라우트 2개) · `authService.interface`·`httpAuthService`·`mockAuthService`
  (재설정 3종).
- **비밀번호 변경에 `새 비밀번호 확인` 필드 추가.** 서버는 새 비밀번호 하나만 받으므로 전송하지
  않고 화면에서만 대조한다.
- **BE·계약**: 변경 없음. 기존 `PUT /me/password`·`DELETE /me`를 그대로 쓰고 요청/응답 필드와
  상태코드를 바꾸지 않았다. [POLICY](../../harness/POLICY.md) 기준 **계약 테스트 대상이 아니다.**
- **테스트**: 552개 전체 통과. `AccountWithdrawPanel.test.tsx`(4개)·`passwordReset.test.tsx`(8개)를
  신설하고 `ProfilePage.test.tsx`에 3개를 보탰다. 화면만 봐서는 회귀를 알 수 없는 항목을 못
  박았다 — **409 시 폼 안 표시**, **동의 전 호출 금지**, **라이브 안내는 강사만**, **거짓 문구
  재발 방지**(`복구할 수 없습니다`·`영구적으로 사라집니다`·`재가입이 제한` 부재 단정),
  **계정 유무 비노출**, **토큰 없으면 폼 미출력**, **토큰 1회용**.
- **후속(BE 요청 필요)**: 비밀번호 재설정 서버 구현 — 메일 발송 인프라, `POST /auth/password-reset`
  (계정 유무와 무관하게 **항상 202**), `POST /auth/password-reset/confirm`(1회용 토큰 + 짧은 TTL),
  변경 시 전 세션 무효화, rate limit. **이 제품은 이메일을 검증하지 않으므로**(요청자 결정) 오타
  이메일 계정은 영구 복구 불가이고, 타인 이메일로 가입한 계정은 그 타인이 탈취할 수 있다 —
  이 위험을 감수하는 전제로 위 완화책이 필수다.
- **후속(선택)**: 탈퇴 시 다른 기기 세션은 즉시 파기되지 않는다([0031] §4의 기존 한계, indexed
  세션 전환이 선행). 안내에 넣지 않았다 — 불안만 키우고 사용자가 할 수 있는 일이 없다.
- **후속(별도 작업)**: 내 프로필 화면의 정보 밀도·레이아웃 개편. 이 ADR은 손대지 않았다.
  → [0011](0011-profile-page-compaction.md)에서 다뤘다.
