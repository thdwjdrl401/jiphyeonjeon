# ADR-0010: 프론트 fixture = 통합 도메인 상태를 단일 원본으로 사용

> 통합 저장소: [mockDatabase.ts](../../../frontend/src/features/demo/mockDatabase.ts) · 화면 어댑터: [demoData.ts](../../../frontend/src/features/demo/demoData.ts) · 데이터 소스 결정: [ADR-0008](0008-frontend-runtime-and-data-source-boundary.md)

- **상태**: 채택
- **일자**: 2026-07-21
- **적용 범위**: 프론트 fixture, 목록·상세·학생/강사 대시보드 테스트 시나리오

## 맥락

커리큘럼 목록은 배열 index 규칙으로 수강 상태를 만들고, 학생 내 커리큘럼은 특정 제목을 수강 중으로 고정해 사용했다. 그 결과 학생 대시보드에서 선택한 커리큘럼이 공개 상세에서는 미수강으로 표시되는 등 같은 사용자의 관계가 화면마다 달라졌다.

라이브 예정, 이어 학습하기, 승인 대기 같은 기능도 각 화면의 별도 상수에서 계산하면 상태 전이와 라우팅 결과가 서로 어긋난다.

## 결정

1. `mockDatabase.ts`를 커리큘럼·수강 관계·소유권·레슨·라이브 세션·진행 상태 fixture의 단일 원본으로 사용한다.
2. `demoData.ts`와 feature별 mock 함수는 단일 원본을 화면 모델로 변환하는 어댑터로만 사용한다.
3. 수강 상태는 제목이나 배열 index가 아니라 `userId + curriculumId + enrollment.status`로 판정한다.
4. `ACTIVE` 수강은 나의 학습 목록, `PENDING` 수강 신청은 승인 대기 목록으로 분리한다.
5. 승인 대기 카드에는 진행률과 학습 계속하기 행동을 제공하지 않는다.
6. 공개 목록·상세·내 커리큘럼은 같은 커리큘럼 ID와 수강 관계를 사용한다.
7. 레슨 목적지는 레슨·세션·replay 상태를 해석하는 공통 함수에서 계산한다.
8. 다음 라이브와 이어 학습하기도 통합 구조에서 파생하며 화면에 별도 고정값을 두지 않는다.
9. 테스트 사이에는 변경 가능한 fixture를 초기 상태로 복원한다.

## 근거

- 사용자와 리소스의 관계가 모든 화면에서 동일하게 보인다.
- 상태별 테스트 데이터를 한곳에서 조정할 수 있어 라이브·VOD·승인 대기 시나리오를 재현하기 쉽다.
- 화면 모델과 도메인 상태를 분리하면 UI 요구가 바뀌어도 관계 판정의 원본은 유지할 수 있다.
- 실제 API로 전환할 때 화면별 상수가 아니라 어댑터 경계만 교체할 수 있다.

## 대안

| 대안 | 장점 | 단점 |
|---|---|---|
| 페이지별 독립 fixture | 작성이 빠름 | ID·관계·상태 불일치 |
| 제목 또는 index 기반 시나리오 | 코드가 짧음 | 정렬·문구 변경에 따라 의미 변경 |
| 모든 페이지가 거대한 객체 직접 사용 | 변환 코드 감소 | 화면과 저장 모델 강결합 |
| **통합 원본 + 화면 어댑터(선택)** | 일관성, 전환 가능성 | 초기 도메인 모델 설계 필요 |

## 영향·후속

- 새 fixture는 기존 커리큘럼·수강·레슨 ID를 우선 재사용한다.
- 화면에 도달할 수 없는 상태를 만들지 않도록 버튼 경로와 fixture 상태를 함께 테스트한다.
- 실제 API 연결 뒤에도 fixture는 계약 모델의 예제이자 회귀 테스트 데이터로 유지한다.
- 서버 계산값이 확정되면 진행률·다음 라이브·이어 학습 알고리즘을 HTTP 응답 기준으로 교체한다.
