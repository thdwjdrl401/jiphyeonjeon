## 1. 현재 조율이 필요한 충돌

### 1.1 레슨 발행 상태: 제품 목표와 CP0 MVP 편차

- **제품 목표**: 자료·AI 준비를 반영한 `DRAFT → AI_NOT_READY → READY → PUBLISHED`, `READY`에서 강사 게시.
- **현재 채택 MVP**: [ADR-0021](../songjeongki/0021-lesson-publish-mvp-direct.md)의 `DRAFT ↔ PUBLISHED` 직행, AI 준비도 게이트 없음.
- **원인**: CP0에는 AI ingestion 파이프라인이 없는데 공개 목차는 `PUBLISHED`만 보여 발행 경로가 필요했다.
- **현재 처리**: 구현은 ADR-0021을 우선한다. 프론트 문서의 `READY→PUBLISHED`를 현재 CP0 계약으로 사용하지 않는다.
- **후속**: CP2/CP3에서 AI 준비도를 발행 축과 합칠지 별도 readiness 축으로 둘지 ADR로 다시 확정한다.
- **우선순위**: P0, AI 파이프라인 착수 전

### 1.2 자료 귀속: 레슨 전용과 커리큘럼 공통 자료

- **이전 결정**: [ADR-0003](0003-lesson-pptx-incremental-processing.md)은 PPTX 자료를 레슨에 귀속했다.
- **변경된 결정**: [ADR-0011](0011-optional-curriculum-materials.md)에서 선택형 커리큘럼 공통 자료를 별도 귀속으로 추가했다. 프론트 UI와 fixture 권한은 채택됐지만 백엔드 계약과 AI 처리 정책은 미확정이다.
- **현재 권한**: 활성 수강생과 운영 강사만 자료 목록을 볼 수 있다. 승인 대기·미수강 사용자와 비운영 강사에게는 메타데이터도 노출하지 않는다.
- **위험**: 공통 자료가 AI 검색 범위에 포함되면 readiness가 레슨 자료와 공통 자료의 합성 상태가 되고 중복 embedding·삭제 영향 범위가 달라진다.
- **조치 필요**: 업로드·목록·삭제 API, 레슨 상속 방식, 중복 처리, 삭제 영향, 다운로드 URL 권한을 확정한다.
- **우선순위**: P0, PPTX schema·ingestion 구현 전

### 1.3 API 인덱스 이동 후 상대 링크

- **현상**
  - `API_MAP.md`가 `docs/frontend/api/`로 이동했지만 일부 링크가 이전 위치 기준이다.
  - `STATE_TRANSITIONS.md`가 `docs/`로 이동했지만 내부 링크 일부가 이전 `docs/frontend/` 위치를 기준으로 남아 있다.
- **API_MAP 예시**
  - `PAGES.md`는 `../PAGES.md`여야 함
  - `components/...`는 `../components/...`여야 함
  - 같은 `api/` 파일 링크는 `api/CATALOG.md`가 아니라 `CATALOG.md`여야 함
  - `CONTRACT.md`는 `../../CONTRACT.md`여야 함
- **원인**: 파일 이동과 링크 갱신이 같은 변경에서 완결되지 않았다.
- **현재 제약**: 이번 작업은 `docs/decisions/yoongwanghyeok`만 수정하도록 제한되어 있어 원본 문서를 고치지 않는다.
- **검증 결과**: `node docs/harness/templates/check-links.mjs` 실행 시 위 기존 링크들로 실패한다.
- **해결 절차**: 별도 문서 정리 변경에서 `API_MAP.md`, 하위 API·컴포넌트 문서, `STATE_TRANSITIONS.md`의 상대 링크를 함께 수정한 뒤 링크 검사를 다시 실행한다.
- **우선순위**: P1

### 1.4 커리큘럼 공통 자료는 실제 API에서 아직 저장되지 않음

- **현상**: mock 모드에서는 생성·관리·상세 자료 흐름이 이어지지만, 실제 API에는 공통 자료 필드와 업로드 endpoint가 없다.
- **현재 안전장치**
  - 실제 상세 응답의 `materials` 누락은 빈 배열로 정규화한다.
  - 실제 생성 요청에 미합의 자료 필드를 임의로 보내지 않는다.
  - 프론트 문서에서 fixture 우선 기능으로 표시한다.
- **위험**: `VITE_USE_MOCK_API=false`에서 UI 선택 내용을 실제 저장으로 오인할 수 있다.
- **조치 필요**: API 계약이 생길 때까지 UI에 실제 저장 완료를 의미하는 문구를 추가하지 않고, 계약 확정 후 FE·BE·`CONTRACT.md`·계약 테스트를 함께 변경한다.
- **우선순위**: P0, 실제 커리큘럼 자료 연동 전

### 1.5 URL 상위 가드와 리소스 권한을 혼동할 위험

- **현상**: `/student/*`, `/instructor/*` 상위 가드가 적용되어도 수강 관계나 커리큘럼 소유권까지 증명하지는 않는다.
- **위험**: 역할만 맞는 사용자가 다른 사용자의 보호 리소스에 접근할 수 있다.
- **현재 처리**: 프론트 상세는 `viewerContext.relationship`으로 조건부 표시하고, 실제 서버 권한을 최종 경계로 문서화했다.
- **조치 필요**: 모든 관리·자료·라이브 endpoint에서 서버가 역할과 관계를 함께 검사하고 `403/404` 정책을 확정한다.
- **우선순위**: P0

## 2. 해결된 결정 변경·트러블슈팅

### 2.1 master 브랜치에서 문서를 생성함

- **문제**: 초기 페이지 문서를 master에서 생성했다.
- **조치**: 해당 변경을 제거하고 사용자가 새 브랜치를 만든 뒤 같은 내용으로 다시 생성했다.
- **재발 방지**: 문서 생성 전 `git branch --show-current`와 `git status --short`를 확인한다.

### 2.2 단일 명세 파일이 지나치게 길어짐

- **문제**: 페이지·컴포넌트·API가 한 파일에 누적되어 검토 단위가 불명확해졌다.
- **조치**: `PAGES.md`, `components/`, `api/`로 분리하고 각 디렉토리에 인덱스를 두었다.
- **결과**: 공통 규칙과 페이지별 세부 내용을 독립적으로 검토할 수 있게 됐다.

### 2.3 콘텐츠 용어가 여러 번 변경됨

- **변경 이력**: 강의 단위 → 코스·커리큘럼·레슨 → 커리큘럼·섹션·레슨.
- **최종 제품 계층**: 커리큘럼 → 섹션 → 레슨.
- **해결**: 외부 API와 DTO 식별자는 `curriculum`·`curriculumId`로 통일했다. 역사적 ADR의 이전 표현은 당시 맥락으로만 유지한다.

### 2.4 자료 형식과 처리 전략이 변경됨

- **형식 이력**: Markdown → Markdown+PDF → PPTX 전용.
- **처리 이력**: 자료 변경 후 전체 AI 결과 재생성 → 파일별 chunk·embedding과 영향받은 AI 결과만 증분 처리.
- **최종 제품 목표**: PPTX 전용, 초기 복수 업로드, 이후 단일 추가·삭제, 관계없는 결과 유지.
- **교훈**: 폐기된 형식·처리 방식을 API enum이나 storage schema에 미리 고정하지 않는다.

### 2.5 LiveKit만으로 되감기가 가능한지 혼동

- **문제**: LiveKit 또는 Egress를 “가까운 구간 되감기 버퍼”로 이해할 여지가 있었다.
- **원인**: SFU, recorder, 재생 format의 역할이 섞였다.
- **정리**
  - LiveKit SFU: 현재 WebRTC 전달
  - Egress: LiveKit 미디어를 녹화하고 HLS 생성
  - HLS: 저장된 과거 구간 재생
  - MinIO+nginx: 세그먼트 저장과 전달
- **해결안**: 현재는 WebRTC, 과거는 recent/full DVR HLS, `LIVE` 버튼으로 복귀.
- **남은 검증**: 녹화 중 전체 DVR playlist 누적 제공과 session clock 보정.

### 2.6 API prefix 변경

- **초기 초안**: `/api/v1`
- **현재 정본**: [ADR-0016](../songjeongki/0016-drop-api-path-versioning.md)에 따라 `/api`
- **현재 처리**: 새 문서와 구현은 `/api`를 사용한다. 버전이 필요해지면 Spring 네이티브 API versioning을 별도 ADR로 도입한다.

### 2.7 목록과 내 커리큘럼의 mock 수강 상태가 달랐음

- **문제**: 공개 목록은 배열 index로 수강 여부를 만들고, 내 커리큘럼은 특정 제목을 수강 중으로 고정해 같은 상세에서 관계가 달라졌다.
- **원인**: 화면별 fixture가 동일한 사용자·커리큘럼·수강 관계를 공유하지 않았다.
- **조치**: [ADR-0010](0010-integrated-mock-domain-state.md)에 따라 `mockDatabase.ts`를 단일 원본으로 만들고 목록·상세·대시보드를 ID 기반 어댑터로 연결했다.
- **결과**: `ACTIVE`, `PENDING`, 진행률, 이어 학습, 다음 라이브가 같은 관계 데이터에서 파생된다.
- **재발 방지**: 제목·배열 index로 상태를 만들지 않고 관계 fixture와 라우팅 결과를 함께 테스트한다.

### 2.8 승인 대기 기능과 기존 다음 라이브 변경의 병합 충돌

- **문제**: `MyCurriculumsPage.tsx` import와 `demoData.ts` 함수 경계에서 두 브랜치의 추가 코드가 충돌했다.
- **원인**: 한 브랜치는 승인 대기 목록을, 다른 브랜치는 다음 라이브·이어 학습을 같은 인접 영역에 추가했다.
- **조치**
  1. upper/lower 중 하나를 고르지 않고 두 기능의 import와 export를 모두 보존했다.
  2. 깨진 중괄호와 중복 import를 정리했다.
  3. 통합 mock 원본을 기준으로 두 파생 함수가 함께 동작하게 했다.
  4. lint·typecheck·전체 테스트·build로 병합 결과를 검증했다.
- **교훈**: 추가형 충돌은 “둘 중 어느 쪽” 선택 문제가 아니라 최종 의미를 재구성하는 작업이다.

### 2.9 커밋하지 않은 변경 상태에서 브랜치를 생성함

- **확인 사항**: 추적 중인 파일의 커밋되지 않은 변경과 새 파일은 브랜치가 아니라 working tree에 있으므로, 충돌이 없으면 새 브랜치로 그대로 따라간다.
- **권장 절차**
  1. 이동 전 `git status --short`로 변경 범위를 확인한다.
  2. 새 브랜치를 만든 직후 다시 status를 확인한다.
  3. 다른 기준 브랜치로 이동해 충돌 위험이 있으면 먼저 커밋하거나 stash한다.
- **교훈**: “변경이 따라간다”와 “안전하게 분리됐다”는 같은 의미가 아니다. 브랜치별 작업 경계는 커밋으로 명확히 한다.

### 2.10 문서가 `git add .` 뒤 보이지 않는 것처럼 보임

- **점검 절차**
  1. `git status --short --untracked-files=all`로 새 파일까지 확인한다.
  2. `git check-ignore -v <path>`로 실제 ignore 규칙 적용 여부를 확인한다.
  3. 필요한 경우 대상 문서를 명시적으로 `git add <path>`한다.
- **교훈**: IDE 표시만으로 staging 여부를 판단하지 않고 Git의 status와 ignore 근거를 확인한다.

### 2.11 Vite 프로덕션 빌드가 샌드박스 권한으로 실패함

- **문제**: Vite가 설정을 로드하는 동안 상위 디렉토리 읽기가 차단되어 `Cannot read directory`와 config resolve 오류가 발생했다.
- **판단**: TypeScript나 Vite 설정 오류가 아니라 실행 환경의 filesystem 권한 문제였다.
- **조치**: 동일한 빌드 명령을 필요한 권한 범위에서 다시 실행했고 정상 완료를 확인했다.
- **교훈**: 빌드 실패 시 코드 오류와 실행 환경 오류를 로그 경로·권한 메시지로 먼저 구분한다.

### 2.12 프로필 입력이 서버 저장처럼 보였음

- **문제**: 닉네임·강사 공개 프로필 입력이 로컬 상태만 바꾸면서 저장 성공 안내를 표시했다.
- **조치**: [ADR-0013](0013-profile-image-edit-modal.md)에 따라 실제 구현된 프로필 이미지만 수정 모달에서 저장하고, 미구현 필드는 읽기 전용·준비 중으로 전환했다.
- **결과**: 프로필 이미지 응답이 인증 캐시와 전역 아바타에 즉시 반영되고 새로고침 후 사라지는 가짜 저장 행동이 없어졌다.

## 3. 구현 전 검증이 필요한 기술 이슈

| 우선순위 | 항목 | 확인할 내용 | 완료 기준 |
|---|---|---|---|
| P0 | 실제 Egress 호출 | LiveKit room·발행 참가자·MinIO로 녹화 시작/종료 | HLS manifest와 segment가 생성되고 자산 상태가 webhook으로 `READY` 도달 |
| P0 | 누적 DVR HLS | 라이브 중 세션 시작부터 playlist 재생 | 늦은 입장·새로고침 후 `0ms~현재` 탐색 가능 |
| P0 | session clock | WebRTC, HLS, 자막, 채팅의 offset | source 전환 후 동일 `sessionMs` 오차가 허용 범위 이내 |
| P0 | LiveKit token 권한 | 학생 `canPublish=false` | UI 조작과 무관하게 학생 publish가 서버에서 거부됨 |
| P1 | WS 재연결 | STOMP 끊김 뒤 REST 누락 복구 | 중복 없이 메시지·자막 연속성 유지 |
| P1 | HLS URL 만료 | 재생 중 URL 갱신 | 현재 위치를 유지한 채 URL 재발급·재생 지속 |
| P1 | 자료 증분 처리 | 추가·삭제의 영향 범위 | 관계없는 embedding·게시 결과가 유지됨 |
| P1 | AI 검수 동시성 | draft·published version 충돌 | 오래된 초안 게시가 `409`로 차단되고 기존 게시본 유지 |
| P1 | 진행률 | watched range 병합·90% 기준 | seek만으로 완료되지 않고 중복 재생이 과대 계산되지 않음 |

## 4. 정책 협의가 남은 항목

### 인증·프로필

- CSRF token 전달 방식과 재발급 시점
- 회원가입 후 자동 로그인 여부
- 현재 사용자 endpoint와 공통 오류 DTO
- 비밀번호 변경·다른 세션 종료·회원 탈퇴 데이터 처리

### 커리큘럼·수강

- `IMMEDIATE` 강사 선택·저장 API와 `INVITATION_ONLY` 지원 범위 (`IMMEDIATE` 학생 신청·조회는 지원)
- 강사 계정의 타 커리큘럼 수강 허용
- lifecycle·학습 완료 상태 enum
- 목록의 page/cursor 방식과 `viewerContext` 포함 여부

## 6. 이번 구현에서 얻은 배운 점

1. **계정 역할과 리소스 관계는 다르다.** 학생이라고 항상 수강생은 아니고, 강사라고 모든 커리큘럼의 운영자는 아니다.
2. **일대일 MVP도 수명주기가 다르면 리소스를 분리한다.** lesson과 live session을 분리해 일정·실행·재시도·녹화를 콘텐츠 상태와 독립시켰다.
3. **fixture도 데이터 모델이다.** 화면별 상수보다 ID와 관계를 공유하는 단일 원본이 상태 전이 테스트에 유리하다.
4. **환경 변수는 기능별 분기가 아니라 시스템 경계여야 한다.** 하나의 스위치로 모든 서비스가 mock 또는 HTTP를 선택해야 혼합 상태를 막을 수 있다.
5. **프론트 조건부 렌더링은 보안 경계가 아니다.** 자료 목록과 다운로드 URL은 서버가 소유권·수강 상태를 검사해야 한다.
6. **선택 파일은 빈 상태도 정상 모델이다.** 응답 누락을 빈 배열로 정규화하고 자료 없이 생성·저장이 가능한지 테스트해야 한다.
7. **상태 라벨은 행동과 함께 설계한다.** 라이브 예정·입장 준비·다시보기 준비 중·다시보기 가능이 사용자를 올바른 다음 경로로 안내해야 한다.
8. **입장 전 점검은 화면 링크가 아니라 라우트 규칙이어야 한다.** 직접 URL 접근에서도 prejoin을 우회할 수 없어야 한다.
9. **병합 충돌은 문법보다 의미를 검증한다.** 양쪽 변경이 독립 기능이면 둘 다 보존하고 전체 회귀 검증으로 확인한다.
10. **문서와 코드는 확정 수준을 구분한다.** fixture UI, 제안 API, 공유 계약을 같은 완료 상태로 표현하지 않는다.
