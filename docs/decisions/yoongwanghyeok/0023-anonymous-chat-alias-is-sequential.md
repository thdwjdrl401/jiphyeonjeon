# ADR-0023: 익명 채팅 가명은 해시 코드가 아니라 세션별 순번이다

> 📍 하네스 개요: [../../harness/README.md](../../harness/README.md) · 아키텍처: [../../ARCHITECTURE.md](../../ARCHITECTURE.md) · 계약: [../../CONTRACT.md](../../CONTRACT.md)

- **상태**: 채택 (BE + FE 구현)
- **일자**: 2026-08-06
- **관련**: [songjeongki/0050](../songjeongki/0050-chat-anonymity-is-sender-choice.md)(익명은 발신자 선택), 공유 계약 [../../CONTRACT.md](../../CONTRACT.md) §2 채팅
- **부분 supersede**: [songjeongki/0050](../songjeongki/0050-chat-anonymity-is-sender-choice.md) §근거의 "가명 형식은 `수강생-XXXX`(`hash(sessionId + userId)`)" 부분만. 그 ADR의 다른 결정(익명은 메시지마다 발신자 선택, 기본값은 익명 아님, 강사는 익명 불가, `mine` 우측 정렬)은 **그대로 유지**한다.

## 맥락

`ChatService.studentAlias`는 `(sessionId + userId)`의 해시값을 4자리 숫자로 접어 `수강생-0473` 같은
가명을 만들었다. 코드에는 처음부터 이런 주석이 있었다:

```java
// 순차 "수강생 N"(1,2,3…) 부여는 세션별 카운터가 필요해 후속(정책 확정).
```

해시 방식은 세션별 카운터 없이 결정론(같은 학생 → 같은 가명)을 얻는 손쉬운 수단이었지만, 사람이
읽기엔 무의미한 4자리 숫자라 "지금 이 강의실에 익명이 몇 명이나 있는지"조차 가늠할 수 없었다.
디자인 리뷰에서 이 부분을 "익명1", "익명2"처럼 등장 순서로 세면 더 읽기 쉽다는 요청이 나왔다 —
바로 위 주석이 가리키던 그 "후속"이다.

## 결정

1. **가명은 `"익명" + 세션 내 순번`이다**(`익명1`, `익명2`, …). 순번은 그 세션에서 **익명으로 처음
   메시지를 보낸 순서**로 매기고, 이후 같은 학생이 다시 익명으로 보내도 같은 순번을 재사용한다 —
   ADR-0050이 요구하는 "세션 내내 같은 가명" 결정론은 그대로 지킨다.
2. **세션별 카운터 + (세션,사용자)→순번 매핑을 애플리케이션 메모리에 둔다**
   (`ConcurrentHashMap`). 단일 인스턴스 전제([songjeongki/0019](../songjeongki/0019-ws-realtime-chat-stomp.md)의
   SimpleBroker·`session.presence` 참여자 수 카운트와 같은 전제) — 다중 인스턴스로 가면 Redis 등
   공유 저장소로 옮겨야 한다.
3. **세션 종료 시점에 비우지 않는다.** 채팅은 `ENDED` 뒤에도 후속 토론을 위해 이어진다(공유 계약
   §2 채팅, [choinhoo/0004](../choinhoo/0004-ended-session-conversation.md)) — 종료 때 지우면 같은
   학생이 종료 후 새 번호를 받아 결정론이 깨진다. 세션이 끝나도 메모리에 남는 것은 이미 이 앱이
   받아들인 단일 인스턴스 트레이드오프(위 참조)와 같은 성격이라 별도 정리 작업을 추가하지 않는다.

## 근거

- **읽을 수 있는 숫자가 더 유용하다.** `수강생-0473`은 해시값이라 순서·인원 어느 것도 말해 주지
  않는다. `익명1`·`익명2`는 등장 순서를 그대로 드러내 진행자·참가자 모두 지금 몇 명이 익명으로
  말하고 있는지 짐작할 수 있다.
- **결정론은 순번 매핑으로도 그대로 성립한다.** 해시가 결정론을 준 것은 입력이 같으면 출력이 같기
  때문이었는데, `(세션,사용자)→순번` 맵의 `computeIfAbsent`도 같은 성질(처음 한 번만 계산하고
  이후 재사용)을 준다 — 카운터 자체가 필요했던 이유(위 코드 주석)는 동시 요청에서도 번호가
  겹치지 않게 하는 것뿐이고, `AtomicInteger.incrementAndGet()`이 그 동시성만 책임진다.
- **세션 간 추적 불가는 그대로다.** 순번은 세션마다 1부터 다시 시작하므로(카운터도 세션별),
  다른 세션의 "익명1"과 이 세션의 "익명1"을 연결할 수 없다 — ADR-0050이 지키려던 "세션 밖으로
  추적되지 않는다" 불변식은 그대로 유지된다.

## 대안

| 대안 | 장점 | 단점 |
|---|---|---|
| **세션별 순번(선택안)** | 사람이 읽기 쉽고, 인원 감을 준다 | 세션별 상태(카운터+맵)가 필요 |
| 기존 해시 코드(`수강생-XXXX`) | 상태 없이 순수 함수로 계산 | 숫자에 의미가 없고, 서로 다른 두 코드가 얼마나 다른 사람인지 짐작할 수 없다 |
| DB에 순번 컬럼 추가 | 다중 인스턴스에서도 정확 | 이 앱은 이미 SimpleBroker·참여자 수 등 여러 곳에서 단일 인스턴스를 전제하고 있어, 이 하나만 DB로 옮기는 것은 일관성이 떨어지고 지금 필요 이상 |

## 영향·후속

- **변경**: `ChatService.studentAlias`(BE), `ChatMessageResponse` 주석, FE `LearningSidebar`의
  익명 판별 정규식(`/^수강생-\d{4}$/` → `/^익명\d+$/`, 채팅 아바타 "?" 대체 표시에 씀),
  `mockLiveSessionService`·`DevLivePanel`의 예시 가명.
- **문서**: 공유 계약 §2 채팅 행의 가명 예시, `docs/frontend/api/LIVE.md` §9, `ChatContractTest`·
  `LiveChatWebSocketTest`의 `startsWith("수강생-")` → `startsWith("익명")`.
- **과거 메시지는 그대로다**(ADR-0050과 같은 이유) — `sender_name`은 저장 시점에 확정되므로 이
  변경 이전에 쌓인 익명 메시지는 계속 `수강생-XXXX` 형태로 보인다. 소급 전환은 하지 않는다.
