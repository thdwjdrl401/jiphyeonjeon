# ADR-0001: 프론트 명세 = 페이지 → 컴포넌트 → API 순서로 분리

> 프론트 페이지: [PAGES.md](../../frontend/PAGES.md) · 컴포넌트 인덱스: [components/README.md](../../frontend/components/README.md) · API 인덱스: [api/API_MAP.md](../../frontend/api/API_MAP.md)

- **상태**: 채택
- **일자**: 2026-07-21
- **적용 범위**: 프론트엔드 기획·명세 문서

## 맥락

처음에는 페이지 분리, 컴포넌트 구성, API 명세를 하나의 `FRONTEND_API_MAP.md`에서 순서대로 작성했다. 접근 권한·라이브·VOD 상태가 추가되면서 공통 컴포넌트만으로도 문서가 길어졌고, 페이지 구조와 상세 API 협의 내용이 서로 다른 변경 주기를 갖기 시작했다.

코드를 작성하기 전에 모든 컴포넌트의 props까지 고정하면 구현 피드백을 반영하기 어렵지만, 페이지 책임과 필요한 데이터 경계 없이 바로 구현하면 FE·BE 협의 누락이 생긴다.

## 결정

1. 명세 작성 순서를 **페이지 분리 → 컴포넌트 책임 → API 계약 초안**으로 유지한다.
2. 페이지·라우트·접근 원칙은 `docs/frontend/PAGES.md`에서 관리한다.
3. 컴포넌트는 `docs/frontend/components/`에 다음처럼 분리한다.
   - 공통 레이아웃·공통 컴포넌트
   - 단순 공개 페이지 묶음
   - 복잡한 페이지 또는 기능 흐름별 문서
4. API는 `docs/frontend/api/API_MAP.md`에 공통 계약·인덱스를 두고, 도메인별 문서로 분리한다.
5. 컴포넌트 명세는 책임·상태·필요 데이터·접근성까지 정의하되 실제 props, hook, 폴더의 세부 구현은 코드 작성 시 확정한다.
6. React 구조는 혼합형을 전제로 한다.
   - `app`: 전역 라우팅·provider·layout
   - `pages`: 라우트 단위 조합
   - `features`: curriculum, lesson, live, learning, AI 같은 기능 소유
   - `shared`: 도메인 의미가 없는 재사용 UI·유틸리티

## 근거

- 페이지 구조를 먼저 고정하면 누락된 사용자 흐름과 접근 권한을 일찍 발견할 수 있다.
- 컴포넌트 책임을 API보다 먼저 정하면 백엔드에 화면별 전용 endpoint를 무분별하게 요구하지 않게 된다.
- 공통·페이지·도메인 API 문서를 분리하면 리뷰 주체와 변경 주기를 맞출 수 있다.
- props를 문서에서 과도하게 고정하지 않아 구현 과정의 자연스러운 리팩터링 여지를 남긴다.

## 대안

| 대안 | 장점 | 단점 |
|---|---|---|
| 단일 대형 문서 | 검색 위치가 하나 | 길이 증가, 책임 혼합, 동시 수정 충돌 |
| 페이지별 모든 내용을 한 파일에 작성 | 한 화면의 맥락 파악 용이 | 공통 계약 중복, API 형태 표류 |
| 코드 우선 후 문서화 | 초기 속도 | 접근 권한·상태·FE/BE 계약 누락 위험 |
| **3단계 분리(선택)** | 점진 검토, 책임과 계약 분리 | 인덱스와 링크를 함께 관리해야 함 |

## 영향·후속

- 묶음 문서를 추가·분리하면 `components/README.md` 또는 `api/API_MAP.md` 인덱스를 함께 갱신한다.
- 실제 요청·응답이 확정되면 `CONTRACT.md`와 계약 테스트를 같은 변경에서 갱신한다.
- 새 문서는 이미 확정된 내용을 복제하기보다 정본을 링크하고 화면별 추가 요구만 기록한다.
