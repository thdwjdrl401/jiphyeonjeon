# ADR-0012: 커리큘럼 중심 탐색 + 레슨 중심 라이브 관리

> 역할 라우팅: [ADR-0009](0009-role-prefixed-routing-and-entry-gates.md) · 통합 mock: [ADR-0010](0010-integrated-mock-domain-state.md) · 상태 전이: [STATE_TRANSITIONS.md](../../STATE_TRANSITIONS.md)

- **상태**: 채택·실제 API 연동 — 폼은 통합, 저장 endpoint는 순차 호출
- **일자**: 2026-07-22
- **적용 범위**: 로그인 후 이동, 공통 내비게이션, 학생·강사 마이페이지, 커리큘럼·레슨 탐색, 라이브 일정 생성·수정·상세 흐름

> **2026-08-06 현행 정합화**: 레슨 폼 안에서 일정을 함께 편집하는 UX는 유지하면서, 실제 저장은
> 레슨 생성·수정 뒤 `POST /instructor/lessons/{lessonId}/live-sessions` 또는
> `PATCH /instructor/live-sessions/{sessionId}`를 순차 호출하도록 구현됐다. 즉 하나의 화면 흐름이지
> 하나의 원자적 요청은 아니다. `GET /instructor/lessons/{id}`의 `liveSession`으로 저작 화면 문맥도
> 복원한다. 업로드 녹화강의(`deliveryType=RECORDED`)는 라이브 일정 없이 별도 생성 흐름을 사용한다.

## 맥락

역할별 prefix와 라이브 입장 전 점검은 ADR-0009에서 채택했지만, 실제 화면 이동에는 다음과 같은 중복과 단절이 남아 있었다.

- 로그인 후 웰컴 페이지를 다시 거쳐야 커리큘럼을 탐색할 수 있었다.
- 마이페이지, 내 커리큘럼, 내 프로필 이동이 여러 버튼과 사이드바에 분산되어 있었다.
- 레슨 상세·수정·입장 점검 화면에서 현재 커리큘럼의 다른 레슨으로 바로 이동할 수 없었다.
- 레슨과 일대일로 연결된 라이브 일정의 생성·수정·상세가 별도 세션 페이지에 있어 같은 정보를 여러 화면에서 확인해야 했다.
- 라이브가 종료되어 다시보기 산출물이 생성 중이거나 공개된 뒤에도 레슨 수정 화면에서 과거 라이브 일정을 변경할 수 있었다.

현재 실제 API에는 레슨 생성·수정과 라이브 일정 저장을 하나로 처리하는 합의된 요청 계약이 없다. 따라서 프론트 이동 구조를 단순화하더라도 새 API 필드나 endpoint를 임의로 정의해서는 안 된다.

## 결정

1. 로그인 성공 후 역할과 관계없이 공개 커리큘럼 탐색 페이지로 이동한다. 로그인 상태의 웰컴 페이지 버튼도 같은 탐색 페이지를 가리킨다.
2. 공통 헤더의 `내 커리큘럼` 진입점은 `마이페이지`로 바꾸고, hover 메뉴에서 `내 커리큘럼`과 `내 프로필`을 선택하게 한다.
3. 헤더 프로필 클릭은 프로필 페이지 이동이 아니라 기본 정보 popover를 열며, 외부 영역을 클릭하면 닫는다.
4. `/student/*`, `/instructor/*` 역할 prefix와 상위 가드는 ADR-0009대로 유지한다.
5. 학생 레슨 상세·입장 전 점검과 강사 커리큘럼 관리·레슨 상세·레슨 수정·최종 점검에는 현재 커리큘럼의 섹션·레슨 목록을 공통 사이드바로 표시한다.
6. 사이드바의 레슨 링크는 현재 역할의 레슨 상세로 이동한다. 최종 점검처럼 URL에 `sessionId`만 있는 화면은 통합 mock의 세션→레슨 관계를 통해 현재 커리큘럼 문맥을 복원한다.
7. 커리큘럼 상세와 관리 화면의 레슨 진입 버튼은 레슨 상세로 통일한다. 레슨 수정은 레슨 상세에서만 진입한다.
8. 라이브 일정 입력은 레슨 생성·수정 폼에 포함한다. 일정 유무, 예정 시작 시각, 예상 진행 시간, 입장 가능 시각과 운영 정책을 한 흐름에서 확인한다.
9. 라이브 일정 생성·수정 페이지와 일반 세션 상세 페이지는 제거한다. 라이브 일정, 현재 상태와 운영 정책은 레슨 상세의 `라이브 강의` 영역에서 표시한다.
10. `prejoin`, `preflight`, `classroom`, `processing`은 장치 점검·실시간 입장·녹화 처리처럼 세션 실행 상태가 필요하므로 `sessionId` 기반 경로를 유지한다. 레슨과 세션의 ID 또는 수명주기를 합치지 않는다.
11. `ENDING`, `ENDED`이거나 다시보기 상태가 `DRAFT`, `READY_FOR_REVIEW`, `PUBLISHED`인 레슨은 라이브 완료 단계로 본다. 이 단계의 레슨 수정 화면에서는 라이브 일정 입력과 변경 UI를 표시하지 않는다.
12. 학생 레슨 상세는 라이브 전에는 라이브 강의만, 라이브 종료 후에는 다시보기만 표시한다. 라이브 입장은 예정 시각 10분 전부터 허용하고 그 이전에는 입장 불가 안내를 표시한다.
13. 학생·강사 대시보드와 프로필은 중복 이동 버튼을 줄이고, 커리큘럼·레슨 상세를 실제 작업의 진입점으로 사용한다.
14. 커리큘럼 관리에서 레슨은 drag-and-drop으로 같은 섹션 안에서 순서를 바꾸거나 다른 섹션으로 이동할 수 있다.
15. 위 동작은 기존 통합 mock의 커리큘럼·섹션·레슨·라이브 상태를 사용한다. 실제 API 요청·응답 필드, 상태코드와 endpoint는 추가하지 않는다.

## 근거

- 사용자는 마이페이지와 별도 세션 상세를 반복해서 거치지 않고 커리큘럼→레슨 흐름 안에서 학습·관리를 이어갈 수 있다.
- 현재 커리큘럼 목차를 화면에 유지하면 강의 상세와 점검 단계에서도 인접 레슨으로 이동하기 쉽다.
- 레슨 상세를 관리 허브로 두면 레슨 정보, 자료, 라이브 일정과 다시보기 상태를 한 곳에서 파악할 수 있다.
- 실행 화면의 `sessionId`를 유지해 콘텐츠와 실시간 실행 상태의 분리 원칙 및 향후 재시도·녹화 처리 확장성을 보존한다.
- 완료된 라이브 일정을 수정하지 못하게 해 이미 생성 중이거나 공개된 다시보기의 시간 기준과 과거 일정이 달라지는 것을 방지한다.
- 합의되지 않은 API 계약을 만들지 않아 mock UI를 실제 저장 기능으로 오인하는 위험을 줄인다.

## 대안

| 대안 | 장점 | 단점 |
|---|---|---|
| 별도 라이브 일정·세션 상세 페이지 유지 | 세션 기능의 화면 경계가 명확함 | 레슨과 일대일인 현재 구조에서 이동과 정보가 중복됨 |
| 모든 화면에 마이페이지 공통 사이드바 유지 | 레이아웃 구현이 단순함 | 현재 커리큘럼과 인접 레슨 문맥이 사라짐 |
| 모든 라이브 경로를 `lessonId`로 변경 | URL과 화면 모델이 단순함 | 실행 상태·녹화 처리의 세션 식별자와 수명주기를 잃음 |
| 종료 후 일정도 계속 수정 허용 | 운영자 수정 자유도 | 다시보기 시간축·이력과 일정 정보가 불일치할 수 있음 |
| **레슨 관리 허브 + 실행 경로의 sessionId 유지(선택)** | 이동 단순화와 도메인 분리를 함께 유지 | 세션→레슨 문맥 복원 로직이 필요함 |

## 영향·후속

- 제거된 일반 세션 상세·일정 생성·수정 URL은 404로 처리하고 route smoke test로 고정한다.
- 레슨 상세, 레슨 수정, 커리큘럼 관리와 최종 점검은 공통 커리큘럼 레슨 내비게이션을 사용한다.
- 향후 한 레슨에 여러 라이브 일정이 허용되면 레슨 상세에서 일정 이력·회차 선택 UI와 현재 회차 판정 규칙을 별도로 설계해야 한다.
- 실제 일정 저장 API를 도입할 때 레슨 요청에 포함할지 라이브 일정 endpoint를 유지할지 FE·BE가 먼저 합의해야 한다.
- API 계약이 확정되면 `CONTRACT.md`, FE·BE 구현과 계약 테스트를 같은 변경에서 갱신한다.
- 서버는 역할 prefix나 프론트 노출 여부를 권한 경계로 신뢰하지 않고 커리큘럼 소유권·수강 관계·세션 입장 가능 시간을 다시 검사해야 한다.
