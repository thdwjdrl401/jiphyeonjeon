# ADR-0002: 콘텐츠 계층과 접근 UI = 커리큘럼→섹션→레슨 + 관계별 조합

> 페이지 명세: [PAGES.md](../../frontend/PAGES.md) · 상세 컴포넌트: [CURRICULUM_DETAIL.md](../../frontend/components/CURRICULUM_DETAIL.md) · 시스템 페이지: [SYSTEM_PAGES.md](../../frontend/components/SYSTEM_PAGES.md)

- **상태**: 채택
- **일자**: 2026-07-21
- **적용 범위**: 제품 용어, 프론트 라우팅·컴포넌트 조합, 접근 UX

## 맥락

초기에는 강의가 독립적으로 존재하거나 커리큘럼과 강의의 관계가 불명확했다. 이후 코스·커리큘럼·레슨, 커리큘럼·섹션·레슨 등 여러 용어 후보를 검토했고, 인프런·Udemy와 유사하게 하나의 학습 상품 아래 구간과 개별 수업을 두는 구조가 필요하다고 판단했다.

또한 같은 커리큘럼 상세에서도 비로그인, 미수강 학생, 승인 대기, 수강생, 운영 강사, 비운영 강사의 정보와 행동이 다르다. 이를 역할별 페이지로 복제하면 공개 정보·목차·오류 처리가 중복된다.

## 결정

1. 콘텐츠 계층은 **커리큘럼 → 섹션 → 레슨**으로 확정한다.
2. 계정 유형은 **강사(`INSTRUCTOR`)와 학생(`STUDENT`)**으로 구분한다. 관리자는 후속 범위다.
3. **수강생**은 별도 계정 역할이 아니라 특정 커리큘럼에 활성 수강 관계가 있는 사용자를 뜻한다.
4. 회원가입 시 강사·학생 유형을 선택하며, 프로필에서 임의 변경하지 않는다.
5. 커리큘럼 생성은 강사만, 관리는 해당 커리큘럼을 운영하는 강사만 가능하다.
6. 웰컴과 공개 커리큘럼 탐색은 별도 페이지로 유지한다.
7. 커리큘럼 상세는 비로그인을 포함해 공개하되, 실제 레슨 자료·라이브·VOD 접근은 관계와 게시 상태로 보호한다.
8. 권한별 페이지를 복제하지 않고 **공통 페이지 골격 + 관계별 조건부 컴포넌트**를 사용한다.
9. 프론트는 계정 역할이나 작성자 ID만으로 권한을 추론하지 않는다. 서버가 제공하는 `relationship`, `allowedActions`, 차단 `reasonCode`를 사용한다.
10. 비로그인 `401`은 안전한 내부 `returnTo`와 함께 로그인으로 이동하고, 인증 후 권한 부족 `403`은 접근 불가 페이지를 사용한다. 보호 리소스 존재 은닉이 필요하면 `404`를 허용한다.

## 근거

- 섹션은 긴 커리큘럼을 학습 단위로 묶고 순서를 관리하는 자연스러운 중간 계층이다.
- 수강생을 역할 enum으로 만들지 않으면 한 사용자의 커리큘럼별 관계를 정확히 표현할 수 있다.
- 공통 상세 골격은 공개 정보·목차·로딩·오류를 재사용하면서 관계별 CTA만 바꿀 수 있다.
- 서버 판정 사용은 다른 강사의 관리 UI 노출, 미수강자의 보호 콘텐츠 접근 같은 보안 오류를 줄인다.

## 대안

| 대안 | 장점 | 단점 |
|---|---|---|
| 강의 독립 존재 | 모델 단순 | 상품·목차·수강 관계 구성 어려움 |
| 커리큘럼→레슨 2계층 | 초기 CRUD 단순 | 긴 커리큘럼의 그룹·순서 관리 부족 |
| 역할별 상세 페이지 복제 | 조건문 감소 | 공개 정보·오류·목차 중복과 표류 |
| 프론트에서 역할로 권한 계산 | 요청 데이터 감소 | 소유권·수강 상태·상태 전이 누락 가능 |
| **3계층 + 관계별 조합(선택)** | 구조와 권한 확장에 유리 | 서버 관계 DTO 합의 필요 |

## 영향·후속

- 공개 목록·상세 응답은 최소 관계 정보와 허용 행동을 제공하는 방향으로 협의한다.
- 강사 계정이 다른 강사의 커리큘럼을 수강할 수 있는지는 별도 정책으로 남긴다.
- API 식별자를 `courseId`와 `curriculumId` 중 무엇으로 통일할지는 이 ADR 범위 밖이며 현재 공유 계약과 프론트 초안 사이 조율이 필요하다.
- 관리자, 초대 전용 수강, 역할 전환은 정책을 정의한 뒤 추가한다.
