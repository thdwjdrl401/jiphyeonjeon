# ADR-jinwoo-0001: Spring→ai-api RAG S2S 인증 — MR-A 착수를 위한 공백 정리와 승인 조건

> 📍 하네스 개요: [../../harness/README.md](../../harness/README.md) · 판단 정책: [../../harness/POLICY.md](../../harness/POLICY.md)

- **상태**: 채택 — §9(HMAC 공유 시크릿)로 결정됨(2026-07-28). `canola/0023` 자체의 상태 줄("Proposed... AI 합의 필요")은 유채은 소유 파일이라 여기서 대신 고치지 않음 — 반영은 본인 몫으로 남김.
- **일자**: 2026-07-28 (제안 작성) / 2026-07-28 (채택 확정)
- **관련**: [canola ADR-0023](../canola/0023-spring-to-ai-rag-jwt-contract.md), MR-A(`feat/common/rag-sse-bridge`)
- **주의**: `canola/0023-spring-to-ai-rag-jwt-contract.md`는 팀원(유채은) 소유 문서로, 이 ADR 작성 과정에서 읽기만 했고 수정하지 않았다. 아래 내용은 그 문서를 읽고 이 폴더(jinwoo)에 독립적으로 정리한 것이다.

## 쉽게 말하면 (요약)

Spring이 ai-api한테 "이 요청은 진짜 내가 보낸 것"이라고 증명하는 방법이 아직 안 정해져서, ai-api는
지금 안전하게 하려고 **누가 요청을 보내든 무조건 다 막아버리는 상태(503)**다.

방법은 두 가지가 있었다: JWT(안전하지만 키 관리가 복잡)와 HMAC(기존 콜백 방식 재사용, 훨씬 간단).
Spring 담당(송정기)이 이미 HMAC으로 하자고 제안해 코드까지 병합해놨지만, AI 담당(유채은)이 아직
"네, 그렇게 하겠습니다"라는 최종 확인을 안 해준 상태다. 게다가 HMAC 제안엔 JWT 제안에 있던 것들
(테스트는 어떻게 할지, 승인할 때 뭘 체크할지, 위험한 점은 없는지)이 빠져 있다.

그래서 이 문서에서 한 일:
1. HMAC으로 간다고 가정하고 빠진 부분(테스트 방법·체크리스트·위험 서술)을 미리 초안으로 채워놨다.
2. 인증과 무관한 문제 두 개(다시보기 시간 계산, 프론트가 이미 정해놓은 주소)도 미리 정리해놨다.
3. **(2026-07-28 갱신) HMAC(§9) 채택이 확정됨** — ai-api 쪽 구현(`app/adapters/hmac_internal_authenticator.py`
   등)을 완료해 MR(`feat/ai/rag-internal-auth`, `!154`)로 제출했고, 위 테스트 전략 초안 그대로 실제 테스트를
   작성해 148개 통과 확인함. `canola/0023` 자체의 문서 상태 갱신("Proposed" → "채택")은 유채은 소유 파일이라
   여기서 대신 하지 않았음 — 코드·문서 반영은 이 폴더와 `ai/ai-api/` 안에서만 완료.

## 맥락 (Context)

MR-A(`feat/common/rag-sse-bridge`)는 Spring→ai-api RAG 호출의 S2S 인증 방식이 확정되지 않아 블로킹돼 있다.
`canola/0023`은 §1~8에서 RS256 JWT를 제안했고, 이후 Spring 담당(송정기)이 §9에서 기존 `AiCallbackVerifier`
패턴을 재사용하는 HMAC 공유 시크릿 방식을 역제안했다(커밋 `312f5af`, master 병합 완료). 그러나 문서 상단과 §9
말미 모두 "AI 담당(유채은) 확인 필요"로 명시돼 있어, **§9는 아직 승인되지 않은 제안 상태**다.

또한 §9를 §1~8과 비교하면 두 가지가 빠져 있다:
- §5(테스트 전략)에 대응하는 절이 없음
- §8(최종 승인 체크리스트)에 대응하는 절이 없음
- HMAC 재사용 시의 잔여 위험(신선도 창 재사용 등)에 대한 명시적 서술이 없음

이와 별개로, ADR-0023 범위 밖에서 발견된 두 가지 gap도 MR-A/MR-D 착수 전 정리가 필요하다:
- replay 세션 시간축 변환 기준 없음 (`docs/ARCHITECTURE.md` §9-9)
- FE가 계약 확정 전에 `/lessons/{id}/ai/questions:stream` 경로를 이미 하드코딩(`docs/ARCHITECTURE.md` §9-11)

## 결정 (Decision)

§9(HMAC 공유 시크릿)를 MR-A 구현의 작업 기준으로 채택하고, 아래 "해결" 항목의 초안을 이 문서에서 직접
작성해 승인 심사를 준비한다. 단, **유채은·송정기의 서면 최종 승인 전에는 MR-A를 master로 병합하지 않는다**
— 구현·검증은 진행하되 완료 게이트(AGENTS.md §4)의 ADR 승인 요건은 그대로 유지한다.

## 근거 (Rationale)

- §9는 이미 master에 병합됐고 기존 `AiCallbackVerifier` 패턴을 재사용하는 방향이라 실질적으로 채택 가능성이
  높다 — 다만 "가능성이 높다"와 "승인됐다"는 다르므로 병합 자체는 승인 후로 미룬다.
- 구조적 공백(테스트 전략·체크리스트·잔여위험)을 미리 채워두면, 유채은·송정기가 검토할 때 §1~8과 동일한
  깊이로 비교할 수 있어 승인 절차가 빨라진다.
- replay 시간축·FE 경로 문제는 인증 방식 선택과 무관하게 어차피 풀어야 하므로, 승인 대기 중에도 먼저
  해결해 MR-A/MR-D 착수 시점을 앞당긴다.

## 대안 (Alternatives)

| 대안 | 장점 | 단점 |
|---|---|---|
| §1~8 RS256 JWT | 발급/검증 권한 완전 분리, claim 기반 세밀한 통제 | RSA 키 생성·PEM 2종 mount·`kid` 회전 등 운영 비용, 임베딩 콜백과 인증 모델 이원화 |
| **§9 HMAC 공유 시크릿 (선택)** | 기존 `AiCallbackVerifier` 패턴 재사용, 키 관리 단순, 인증 모델 일원화 | 대칭키라 발급/검증 권한 분리 없음(내부망 전제로 수용), §9 자체엔 테스트 전략·체크리스트 누락(본 문서에서 보완) |

세부 비교(알고리즘·claim·시간·binding 등)는 `canola/0023` §3, §9에 이미 상세히 기록돼 있어 재작성하지 않는다.

## 영향·후속 (Consequences)

### 해결한 것 (이 문서에서 직접 제안)

**1. §9 대응 테스트 전략 초안** (§5 대응)

| 계층 | 확인할 내용 |
|---|---|
| 서명 | 정상 서명 통과, 변조된 body 거부, 잘못된/누락된 `X-Internal-Signature` 거부 |
| 신선도 | `issuedAtMs` 정상 범위/경계값(60초) 통과, 60초+1ms 초과 거부, 5초 이내 미래는 허용·초과분은 거부 |
| binding | body 서명 특성상 `lessonId`/`sessionId`/`requestId` 위조 시 서명 자체가 깨짐 — 이를 명시적 회귀 케이스로 고정 |
| 설정 | `AI_INTERNAL_SECRET` 미설정 시 `503` (fail-closed) |
| 안전 | 인증 실패 시 RAG adapter 미호출, 원문·시크릿 미로그 |

**2. §9 대응 최종 승인 체크리스트 초안** (§8 대응)

| 질문 | 제안 답변 | 승인/수정 |
|---|---|---|
| 서명 대상은 무엇인가? | 요청 원시 body 전체 | ☐ |
| 신선도 창은 얼마인가? | 60초 (`issuedAtMs` 기준). 구현에서 미래 시각 허용치 5초도 추가함(§9 본문엔 없는 구현 세부사항 — 근거는 잔여 위험 표 참고) | ☐ |
| 시크릿은 어떻게 주입되나? | `AI_INTERNAL_SECRET`, `.env` 주입, 콜백용(`AI_CALLBACK_SECRET`)과 별도 값 권장 | ☐ |
| 범위 바인딩은 어떻게 보존되나? | body 자체가 서명 대상이라 위조 시 서명 검증 실패로 자동 보존 | ☐ |
| phase-2(JWT) 전환 조건은 무엇인가? | §9.4 그대로: 호스트 분리·다중 소비자·감사 규제 발생 시 | ☐ |

**3. 잔여 위험 서술 초안**

| 위험 | 평가 | 대응 |
|---|---|---|
| 시크릿 유출 시 60초 내 재사용(replay) 가능 | 제한적 잔여 위험 | TLS 전제, 내부망 전용 endpoint, 짧은 신선도 창으로 노출 시간 제한 |
| 단일 공유 시크릿이라 회전 시 양측 동시 배포 필요 | 운영 절차 이슈 | 회전 절차는 phase-2 전환 전까지 수동 배포 문서로 관리(후속 작업) |
| `issuedAtMs`가 미래로 조작/오차 나면 `now - issuedAtMs`가 음수가 되어 신선도 검증을 무의미하게 통과시킴 | §9 본문엔 없는 구현 갭(리뷰로 발견) | 미래 허용치를 5초로 제한해 구현에서 방어. ADR 문면에 없는 내용이라 여기 명시 |

**4. replay 세션 시간축 변환 제안** (ARCHITECTURE §9-9 대응)

- 라이브: LiveKit 트랙 타임스탬프를 세션 시작 시각 기준 상대 ms로 변환
- replay: 재생 위치(`currentTime`)를 동일한 세션 시작 시각 기준 상대 ms로 변환
- 두 경로 모두 동일한 "세션 상대 ms" 단위로 정규화해 캡션·자료 조회 쿼리에 사용 — RAG 근거 조회가 라이브/리플레이 어느 쪽에서 호출되든 동일한 시간 기준을 쓰게 됨

**5. FE 계약 드리프트 해결 제안** (ARCHITECTURE §9-11 대응)

- `POST /lessons/{id}/ai/questions:stream` 경로를 CONTRACT.md에 **경로만 우선 등록**(현재 FE가 이미 참조 중인 값과 일치시켜 드리프트 방지) — 요청/응답 필드 계약은 §9 승인 확정 후 채운다.

### 결정 확정 (2026-07-28)

- §9(HMAC) 채택 여부 — **확정됨**. ai-api 쪽 구현·테스트를 완료해 `!154`로 제출.
- `canola/0023` 자체 문서의 상태 줄 갱신은 유채은 소유 파일이라 이 저장소에서 대신 하지 않음 — 본인 몫으로 남김.

### 후속 작업

- `docs/CONTRACT.md`(루트, 공유 계약)로의 승격은 **아직 하지 않음** — `ai/ai-api/CONTRACT.md`에 이미 명시된 승격 조건("Spring proxy 구현과 양쪽 계약 테스트가 준비되면 common MR에서 공유 계약으로 승격")이 아직 안 채워짐(Spring 쪽 서명 발급기 미구현). 인증 "방식 결정"과 "공유 계약 승격"은 다른 단계.
- 위 테스트 전략·체크리스트를 `canola/0023`에 §9.5/§9.6으로 반영하는 것은 유채은·송정기 본인 몫(팀원 소유 파일이므로 이 저장소에서 대신 수정하지 않음)
- Spring 쪽 서명 발급기·SSE 프록시 구현 후 MR-C(compose 배선·E2E), MR-D(FE 연동) 순서로 진행
