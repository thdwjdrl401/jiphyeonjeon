# ADR-0081: 강의 노트 window를 60초로 넓히고 draft 모델을 gpt-5-mini로 올림

- **상태**: 구현됨
- **일자**: 2026-08-05
- **관련**: [canola/ADR-0034](0034-near-realtime-accumulative-lecture-notes.md)(원 설계 — window·모델
  초기값을 이 ADR이 대체한다)

## 배경

운영에서 강의 노트 GMS 호출이 지나치게 잦다는 문제 제기로 파이프라인 전체를 검토했다
(`app/lecture_notes/` 전 모듈 + 어댑터). 호출 빈도는 증상이었고 원인은 두 개였다.

**원인 1 — 판단 단위가 너무 작다.** ADR-0034의 초기값(목표 25초, 강제 40초/400자)은 강의의
한 호흡이다. 이 조각마다 "새 주제인가/갱신인가/버릴 것인가"를 묻는데, 개념 하나가 3~6개 창에
흩어져 도착하므로 매 창이 "의미가 끝나지 않은 발화"에 가깝다. 경계 판단에 필요한 맥락이 창
안에 없다.

**원인 2 — 실패 재시도가 호출을 증폭한다.** `validate_draft_update`는 활성 topic의 기존 item이
결과에 그대로 보존됐는지 검사한다(identity = `(type, label 없으면 content)`). 실패하면 재작성
1회, 그래도 실패하면 window 전체가 실패하고 **같은 batch를 다음 caption 도착 때 다시 호출**한다.
즉 보존 실패율이 높을수록 호출 수가 곱으로 늘어난다.

보존 실패의 원인을 프롬프트로 의심했다. 프롬프트가 `UPDATE_CURRENT` 사유로 "기존 표현을 더
자연스럽게 정리할 수 있는 경우"를 명시하고 "같은 사실을 합치는 경우" 삭제를 허용하는데, label
없는 item은 content가 곧 identity라 **다듬거나 합치는 순간 검증이 실패**한다. 모델이 프롬프트를
잘 따를수록 실패하는 모순이었다.

## 실측 (2026-08-05, 실제 GMS·실제 어댑터·동일 fixture)

프롬프트 가설을 검증하려고 2×2로 갈랐다. fixture는 활성 topic에 label 없는 근사 중복 item을
둔, 다듬고 싶어지는 형태다. 어댑터를 그대로 호출해 재작성 1회까지 포함한 최종 결과를 셌다.

| 보존 검증 통과 | gpt-5-nano / minimal | gpt-5-mini / minimal |
|---|---:|---:|
| 기존 프롬프트 | 0/3 | 3/3 |
| 프롬프트 수정 후 | 1/3 | 3/3 |

- `gpt-5-nano`는 `reasoning_effort`를 `low`로 올려도 1/3이었다. **effort 문제가 아니다.**
- `gpt-4.1`도 3/3이었다.
- 지연: nano avg 4.6s(2.5~6.2), **mini avg 3.3s(3.1~3.5)**. mini가 더 빠르고 편차도 작다 —
  nano의 느림은 재작성 왕복 때문이다.

**결론: 지배 요인은 프롬프트가 아니라 모델 체급이었다.** 프롬프트 수정은 방향이 옳지만
(검증기와 모순되는 지시를 없앤다) nano를 구제하지 못한다.

## 결정

1. **window를 넓힌다**: 목표 25→60초, 강제 40→90초, 최소 15→45초, 문자 80/400→200/1,500.
2. **상한 90초는 임의값이 아니라 스키마 제약이다.** `LectureNoteDraftUpdateResult`는 한 호출에
   `newTopic`을 **하나만** 표현할 수 있다. 창이 길어져 주제 전환이 두 번 들어오면 한쪽이 조용히
   유실된다. 2~3분 안은 이 위험 때문에 기각했다.
3. **draft 모델 기본값을 `gpt-5-nano` → `gpt-5-mini`로 올린다.** 위 실측 근거.
4. **프롬프트를 검증기에 맞춘다**: "자연스럽게 정리" 사유와 "합치기" 허용을 제거하고, 기존
   item은 `type·label·content`를 글자 그대로 복사하게 한다. 표현 정리·중복 병합은 **종료 정제
   단계의 몫**으로 역할을 나눈다(정제 프롬프트에 이미 병합 지시가 있다). 재작성 프롬프트의
   "사실을 유지"도 재서술을 허용하는 표현이라 "글자 그대로 복사"로 바꾼다.
5. **IGNORE를 무손실화한다.** IGNORE된 window의 자막을 버리지 않고 다음 호출 입력 앞에 이월한다.
   상한 4,000자, 소비되면 비운다. checkpoint에 `deferredText`(version 1 optional)로 남겨
   재시작에도 살아남게 한다.

## 근거

- **호출 수**: 창 25→60초로 약 1/2.4. 보존 실패 재시도가 사라지면서 추가로 줄어든다. nano
  1/3 → mini 3/3이므로 성공 1회당 호출이 ~3회에서 ~1회가 된다. **두 효과가 곱해져 체감
  감소폭은 창 배율보다 크다.**
- **비용**: mini는 토큰 단가가 nano보다 높지만 호출 수가 위와 같이 줄고, 실패 시 낭비되던
  호출(결과를 버리는 호출)이 사라진다. 단가 대비 총비용은 실측으로 확인할 것(아래 후속).
- **지연**: 노트 갱신 주기가 25초 → 60~90초가 된다. 실시간 노트의 UX 요구가 분 단위라는
  전제 위에서 수용했다. 이 전제가 틀리면 되돌려야 하는 결정이다.
- **IGNORE 이월**: 기존 동작은 "미완결이라 버림"인데 프롬프트 의도는 "미완결이라 미룸"이었다.
  이월분을 자를 때 뒤를 남기는 이유는, 계속 IGNORE되는 상황에서 완결에 가까운 최근 발화가
  잘리면 이월의 목적이 사라지기 때문이다.

## 하지 않은 것

- **`newTopics` 배열 확장**: 창을 2~3분까지 넓히려면 필요하다. 스키마·reducer·검증기가 함께
  바뀌는 이 구조 최대 변경이라 이번 범위에서 뺐다. 90초 상한은 그 전까지의 안전선이다.
- **delta 출력 전환**: 스냅샷 재출력이 토큰 지배 항이지만, patch 병합 모호성을 다시 들여오는
  변경이라 비용이 실제 문제로 확인된 뒤에 판단한다.
- **12-item 캡으로 인한 주제 분할(용량 분할)과 의미 분할의 구분**: `START_NEW`에 사유를 실어
  정제 단계가 구별하게 하는 안이 있으나 이번엔 넣지 않았다.

## 검증

- ai-api **416 passed**, ruff check·format, `uv build` 통과.
- 신규 테스트 4건(IGNORE 이월): 다음 호출로 이어짐 / 소비 후 비워짐 / 상한 안에서 최근 발화
  보존 / 재시작 후에도 이어짐.
- `test_lecture_note_windowing.py`는 flush 로직을 검증하는 파일이므로 경계를 파일 안에서
  고정하도록 바꿨다. 정책 값이 바뀔 때 무관한 테스트가 깨지지 않게 하기 위함이며, 정책 값
  자체는 `test_deployment_config.py`가 compose 기본값으로 지킨다.

## 후속

1. **실측 비교**: 실제 세션 자막 1개를 dev에 재생해 변경 전후로 GMS 호출 수·`model_failed`
   횟수·IGNORE 비율·topic 수·최종 정제본의 사실 누락(원 자막 대조 표본 10곳)을 비교한다.
2. **비용 확인**: mini 전환 후 실제 과금이 줄었는지 확인. 늘었다면 window를 더 넓히는 쪽
   (=`newTopics` 확장 선행)을 검토한다.
3. **`newTopics` 확장** 설계 — 별도 ADR.
