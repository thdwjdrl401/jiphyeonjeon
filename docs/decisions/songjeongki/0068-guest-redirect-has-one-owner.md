# ADR-0068: 로그인하지 않은 사람을 어디로 보낼지는 한 곳이 정한다

> 관련 결정: [ADR-0031 계정·프로필 보안](0031-account-profile-security.md)

- **상태**: 채택 — 구현됨
- **일자**: 2026-08-03
- **적용 범위**: `AuthContext.guestReason`, `GuestRedirect`, `RequireRoleRoute`,
  `RequireAdminRoute`, `GlobalHeader`, `AccountWithdrawModal`

## 한 줄 결정

보호 경로에서 로그인하지 않은 사람을 내보내는 목적지는 **`GuestRedirect` 한 곳**이 정하고,
갈림길은 **"왜 게스트가 되었는가"** 하나다.

## 맥락

### 1. 같은 결정이 네 군데에 흩어져 서로 다른 곳을 가리켰다

```text
GlobalHeader           await logout(); navigate('/')          홈
AccountWithdrawModal   await logout(); navigate('/')          홈
RequireRoleRoute       Navigate('/login?returnTo=…')          로그인 화면
RequireAdminRoute      Navigate('/login?returnTo=…')          로그인 화면
```

로그아웃하면 **네 곳이 동시에 움직인다.** 화면이 옮기려는 곳과 가드가 옮기려는 곳이 다르므로,
어느 쪽이 마지막에 그리느냐로 결과가 갈린다.

### 2. 그래서 회원 탈퇴 목적지가 실행마다 달랐다

기존 테스트는 자주 이기던 `/login`을 고정해 두고 있었고, 다른 작업으로 실행 순서가 바뀌자
간헐적으로 깨졌다. **기다림의 문제가 아니었다** — 15초를 줘도 같았다.

실측한 순서는 이랬다.

```text
115.7ms  replaceState → /                              (모달)
128.5ms  replaceState → /login?returnTo=%2Fstudent%2Fprofile   (가드)
```

가드는 인증이 사라진 순간 **아직 보호 경로에 서 있는 채로** 이동을 예약한다. 화면이 먼저 옮겨도
그 예약이 나중에 덮는다.

### 3. 순서로는 못 이긴다

`navigate`를 먼저 부르고, `flushSync`로 즉시 반영하고, 목 서비스가 뮤테이션 도중에 로그아웃하던
것까지 고쳐 봤지만 결과는 같았다. 가드의 `<Navigate>`는 **렌더 시점에 목적지를 확정하고 효과에서
실행**하므로, 그 사이 우리가 무엇을 하든 예약은 살아 있다.

**목적지가 서로 다른 것이 문제였지 순서가 문제가 아니었다.**

## 결정

### 1. 게스트가 된 경위를 인증 계층이 말한다

```ts
export type GuestReason = 'never-signed-in' | 'signed-out'
```

`status`만으로는 두 경우가 구분되지 않는다. 가드가 이것을 각자 추측하면(예: "여기서 로그인 상태였던
적이 있는가"를 ref로 기억) 가드마다 같은 추측이 복제되고, 추측이므로 언젠가 어긋난다.

`logout()`이 **경위와 상태를 같은 블록에서** 바꾼다. 사이에 `await`가 끼면 게스트가 된 렌더와 경위가
갱신된 렌더가 갈라져, 가드가 한 번은 '만료'로 읽는다.

`login()`은 경위를 되돌린다 — 지난번에 스스로 나갔다고 해서 이번 세션이 끊겼을 때까지 랜딩페이지로
보내면 안 된다.

### 2. 목적지는 `GuestRedirect` 하나가 정한다

| 경위 | 목적지 | 왜 |
|---|---|---|
| `never-signed-in` | `/login?returnTo=…` | 주소 직접 열기·만료. 보던 곳으로 돌아가고 싶다 |
| `signed-out` | `/`(랜딩페이지) | 스스로 나갔다. 방금 나온 화면을 다시 권할 이유가 없다 |

탈퇴한 사람에게 로그인 화면을 들이미는 것은 특히 이상하다 — **돌아갈 계정이 없다.**

랜딩페이지는 로그인 여부로 되돌리지 않으므로 로그아웃 직전·직후 어느 쪽에서도 안전하다.

### 3. 화면은 목적지를 정하지 않는다

`AccountWithdrawModal`과 `GlobalHeader`에서 `navigate`를 걷어냈다. 로그아웃하면 보호 경로 밖이 되고
가드가 내려놓는다.

공개 화면에서 로그아웃하면 **보던 자리에 그대로 남는다.** 읽던 것을 빼앗을 이유가 없고, 그 자리에는
가드가 없으므로 다툴 상대도 없다.

## 채택하지 않은 대안

### 1. 가드가 "로그인한 적 있는가"를 ref로 기억한다

한 줄이면 되고 실제로 통과한다. 그러나 **가드마다 같은 추측이 복제되고**, 추측이라 언젠가 어긋난다
(예: 가드가 리마운트되면 기억이 사라진다). 경위는 인증 상태의 일부지 화면의 기억이 아니다.

### 2. 화면이 먼저 옮기고 `flushSync`로 확정한다

실제로 시도했고 실패했다(§맥락 3). 가드의 예약은 그대로 살아 있다.

### 3. 로그아웃 시 전체 새로고침(`location.replace('/')`)

SPA를 통째로 내려 확실히 정리된다 — 삭제된 계정의 캐시·소켓이 남지 않는다. 그러나 로그아웃마다 앱을
다시 받게 되고, jsdom에 구현이 없어 테스트에서 검증할 수 없다.

### 4. 가드를 없애고 라우터 로더에서 판정한다

data router로 옮기면 이동이 렌더 밖에서 정해져 경합 자체가 사라진다. 그러나 라우팅 방식 전환은 이
문제의 범위를 한참 넘고, 지금 구조에서도 소유자를 하나로 모으면 해결된다.

## 결과와 한계

### 장점

- 로그아웃·탈퇴 목적지가 **하나**다. 실행 순서와 무관하다.
- 규칙이 한 파일에 있어 바꾸려면 한 곳만 고치면 된다.
- 세션 만료의 `returnTo`는 그대로 살아 있다 — 두 경우를 구분했기 때문이다.

### 한계

- `guestReason`은 메모리에만 있다. 새로고침하면 `never-signed-in`으로 돌아가는데, 새로고침 뒤에는
  어차피 세션이 없는 상태이므로 로그인 화면이 맞다.
- 401 응답으로 세션이 끊기는 경로는 아직 이 모델을 거치지 않는다(`status`가 자연히 guest가 되며
  `never-signed-in`으로 읽힌다 — 만료로 다뤄지므로 의도와 같다).
- 공개 화면에서 로그아웃하면 그 자리에 남는다. 그 화면이 로그인 사용자용 내용을 보이고 있었다면
  각자 비워야 한다(현재 공개 화면들은 그렇게 하고 있다).

## 검증

- `guestRedirect.test.tsx` — 세션 없음 → `/login?returnTo=…`, 스스로 로그아웃 → `/`,
  회원 탈퇴 → `/`(같은 목적지), 다시 로그인하면 만료 취급으로 복귀.
- 전체 스위트 6회 연속 통과(88파일 747테스트)로 간헐 실패가 사라졌음을 확인.
