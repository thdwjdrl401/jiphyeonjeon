# ADR-0070: 강의 노트는 서버가 준 Markdown을 그대로 그린다

> 관련 결정: [ADR-0061 강의 노트 read model은 생산자와 무관하다](0061-lecture-note-read-model-is-producer-agnostic.md) ·
> [공유 계약 §3-4a 강의 노트](../../CONTRACT.md)

- **상태**: 채택 — 구현됨
- **일자**: 2026-08-03
- **적용 범위**: `LectureNotePanel`, `NoteMarkdown`, `NoteMarkdownBody`, `react-markdown`·`remark-gfm`

## 한 줄 결정

노트 본문은 화면이 `topics[].keyPoints`를 목록으로 조립하지 않고, 서버가 준 **`markdown` 필드를
그대로** 그린다. 계약이 금지한 raw HTML·이미지·링크는 **렌더러에서 막는다.**

## 맥락

### 1. 화면이 목록 모양을 강제하고 있었다

```tsx
<h3>{topic.title}</h3>
<ul>{topic.keyPoints.map((point) => <li key={point}>{point}</li>)}</ul>
```

계약(§3-4a)은 `markdownFragment`에 **heading, unordered list, bold, inline code**를 허용한다. 그런데
화면이 목록 모양을 직접 만들고 요점을 글자 그대로 넣으므로, 굵게나 인라인 코드가 오면
`**이렇게**` 별표째 보인다. read model에 `markdown` 필드가 이미 있는데 쓰지 않고 있었다.

### 2. 지금 데이터로는 차이가 없다

결정 전에 운영 데이터를 전수 조사했다.

```text
core.live_lecture_note  13건
  굵게 0 · 인라인 코드 0 · h3 이상 0 · 중첩 목록 0 · 번호 목록 0
  구조화 필드 안의 인라인 문법 0
core.live_ai_answer      9건
  markdown 문법 0건
```

지금 오는 것은 `## 제목` + `- 불릿`뿐이고, 이는 기존 구조화 렌더링과 **결과가 같다.** 즉 이 변경은
오늘 화면을 바꾸지 않는다. 계약이 허용하는 문법이 실제로 오기 시작할 때를 위한 것이다.

### 3. 계약은 구조화 쪽을 정본이라고 말한다

> 구조화 `topicAction/topicTitle/keyPoints`가 의미상 정본이며 `markdownFragment`는 동일 값에서
> 결정론적으로 만든 파생 표현이다. 둘이 불일치하면 계약 위반이다.

그래서 파생 표현을 그리는 것은 **계약이 지켜진다는 전제 위에** 선다. 이 전제가 깨지면 화면이 틀린
쪽을 보여 준다(§한계).

## 결정

### 1. 본문은 `markdown`, 개수는 `topics`

머리말의 "N개 주제"는 구조화 필드에서 센다. 둘은 같은 값에서 나온 두 표현이므로 어긋나지 않는
것이 계약이고, 개수는 Markdown을 파싱해 세는 것보다 구조화 필드에서 읽는 편이 정확하다.

**빈 판정은 본문으로 한다.** `topics`만 보면, 구조화 필드는 왔는데 Markdown이 빈 어긋난 상태에서
"3개 주제"라는 머리말 아래 아무것도 없는 화면이 나온다.

### 2. 계약이 금지한 것을 렌더러가 막는다

| 막는 것 | 방법 | 왜 |
|---|---|---|
| raw HTML | `rehype-raw`를 넣지 않는다(기본 동작) | `<img onerror>`·`<script>`가 섞여 와도 글자로 남는다 |
| 이미지 | `disallowedElements={['img']}` | 계약에 없다. 외부 요청이 노트에서 나가면 안 된다 |
| 링크 | `disallowedElements={['a']}` + `unwrapDisallowed` | 모델이 지어낸 주소가 클릭 가능한 링크로 남으면 그것만으로 피싱 표면이다. **글자는 남긴다** — 링크를 걷어냈다고 문장에 구멍이 나면 안 된다 |

`remark-gfm`은 계약을 넓히려는 것이 아니라, 표·취소선처럼 계약 밖 문법이 섞여 와도 원문이 그대로
노출되지 않게 하려는 것이다.

### 3. 렌더러는 지연 로드한다

`AppRouter`가 페이지를 직접 import해 **라우트가 코드 분할돼 있지 않다.** 여기서 바로 import하면
react-markdown·remark-gfm이 로그인 화면 번들에까지 들어간다. 플레이어·판서가 이미 쓰는 방식대로
별도 청크로 뗀다.

```text
NoteMarkdownBody-*.js   156.99 kB │ gzip: 47.54 kB   ← 노트를 여는 사람만 받는다
```

## 채택하지 않은 대안

### 1. 구조는 그대로 두고 인라인 문법만 렌더한다

`keyPoints`는 계약상 **단일 행** 1~300자라 블록 구조가 들어올 수 없다. 그러니 굵게·인라인 코드만
처리하는 40줄짜리 렌더러로 충분하고, 의존성이 늘지 않으며 구조화 정본을 그대로 지킨다.

채택하지 않은 이유는 **미래 문법을 자동으로 따라가지 못하기 때문**이다(2026-08-03 사용자 결정).
계약이 넓어질 때마다 우리 파서를 고쳐야 하고, 그 사이 원문이 노출된다.

### 2. 서버가 HTML로 내려준다

화면이 가장 단순해진다. 그러나 표현을 서버가 정하게 되어 화면마다 다른 표현(예: 다시보기에서
접기)을 줄 수 없고, HTML을 신뢰해야 하므로 지금 렌더러가 막는 것들을 서버가 다시 막아야 한다.

### 3. `dangerouslySetInnerHTML` + sanitizer

번들이 가볍다. 그러나 sanitize 설정이 곧 보안 경계가 되어, 설정 한 줄이 잘못되면 조용히 열린다.
react-markdown은 **기본이 안전한 쪽**이다(raw HTML을 켜야 그린다).

## 결과와 한계

### 장점

- 계약이 허용하는 문법이 오는 순간 화면이 따라간다. 우리 쪽은 이미 준비돼 있다.
- 금지 항목을 렌더러 한 곳에서 막고, 테스트가 그것을 지킨다.
- 메인 번들이 커지지 않는다.

### 한계

- **오늘 화면은 달라지지 않는다**(§맥락 2). 지금 데이터에는 인라인 문법이 없다.
- 계약이 깨져 `markdown`과 `topics`가 어긋나면 **화면은 `markdown` 쪽을 보여 준다.** 개수만 구조화
  필드에서 오므로 그때는 머리말과 본문이 어긋나 보인다 — 계약 위반을 화면이 숨기지 않는다는 뜻이기도 하다.
- 노트가 아주 길면(계약 상한 262,144자) 매 갱신마다 전체를 다시 파싱한다. 지금 최대 430자라
  체감되지 않는다. 느려지면 `markdown` 값으로 메모이즈하면 된다.
- 표·취소선 등 GFM 문법은 계약 밖이라 스타일만 최소로 뒀다.

## 검증

- `lectureNoteMarkdown.test.tsx` — 제목·목록을 구조로 그림, 굵게·인라인 코드 살림,
  **raw HTML 미렌더**, **링크·이미지 제거하되 글자 유지**, 본문이 비면 빈 상태, 개수는 구조화 필드.
- `lectureNotePanel.test.tsx` — 빈 상태·REFINED·미수신 상태(픽스처가 본문과 구조화 필드를 함께 맞춘다).
- 대비는 브라우저 `getComputedStyle` 실측 — 본문·제목·굵게·코드·인용·로딩 문구 모두 5.31:1 이상.
- `vite build`로 별도 청크 분리 확인.
