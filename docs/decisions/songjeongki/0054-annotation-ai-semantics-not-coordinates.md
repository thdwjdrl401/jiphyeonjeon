# ADR-0054: 판서 AI는 **의미만** 모델에게 묻고 좌표는 우리가 계산한다

> 📍 하네스 개요: [../../harness/README.md](../../harness/README.md) · 아키텍처: [../../ARCHITECTURE.md](../../ARCHITECTURE.md) · 계약: [../../CONTRACT.md](../../CONTRACT.md)

- **상태**: 채택 (설계 확정, 구현 전)
- **일자**: 2026-07-31
- **관련**: [0051](0051-instructor-annotation-excalidraw.md)(판서 = Excalidraw 문서, 이 ADR이 후속 ②③을 구체화), [0047](0047-live-ai-answer-sse-proxy.md)(라이브 AI 답변 프록시 — 인가·릴레이 패턴을 따른다), [0032](0032-media-playback-hls-only.md)(수강생은 합성만 본다), CONTRACT §3-6b·§3-6d·**§3-6e**
- **오너 경계**: BE·FE(송정기) — 이 기능은 Spring이 GMS를 직접 부르므로 **AI 팀 의존이 없다**(결정 7)

## 맥락 (Context)

ADR-0051이 판서를 **Excalidraw 요소 배열**로 두기로 하면서 후속을 두 개 남겼다 — ② 손그림 정리, ③ 수식 → 그래프. 둘 다 "강사가 대충 그린 것을 AI가 정리해 준다"는 같은 모양이고, 그때는 **GMS 게이트웨이가 멀티모달을 통과시키는지 미검증**이라 착수하지 않았다.

이제 그 게이트를 열고 실제 판서 데이터로 재 봤다. 실측 결과가 설계를 한 방향으로 강하게 밀었다. 이 ADR은 그 결과를 결정으로 고정한다.

전제로 깔린 사실 두 가지가 중요하다.

- **판서 문서는 이미 정확한 벡터다.** `freedraw` 요소가 `points: [[x,y], ...]`를 들고 있고, 좌표계는 1920x1080 논리 프레임이다(§3-6b). 우리는 강사가 그린 위치를 **한 픽셀도 추측하지 않고** 알고 있다.
- **판서의 writer는 강사 하나다.** revision 채번이 그 전제 위에 서 있고, 그것이 깨지면 수신 측의 유실 감지가 무의미해진다(§3-6b).

## 결정 (Decision)

### 1. 의미는 모델에게, 좌표는 우리가

모델에게 **"무엇인가"** 만 묻는다. **"어디인가"** 는 묻지 않는다 — 우리가 이미 정확히 알고 있고, 물으면 틀린다(아래 실측).

### 2. 다이어그램은 **mermaid**를 중간 표현으로 쓴다

모델은 `flowchart LR / A[요청] --> B[인증]` 같은 **좌표가 없는 정의**를 낸다. 배치는 `@excalidraw/mermaid-to-excalidraw`(이미 설치된 전이 의존성, v2.2.2)가 dagre로 계산하고, `convertToExcalidrawElements()`가 **편집 가능한 Excalidraw 요소**로 만든다. 모델이 픽셀을 추정할 자리가 원천적으로 없다.

### 3. 수식은 **LaTeX**를 중간 표현으로 쓴다

같은 이유다. 모델은 `y = ax^2 + bx + c`만 내고, 그것을 어디에 어떤 크기로 놓을지는 원본 획의 bbox에서 우리가 정한다.

### 4. 도형 정리(사각형·원·직선)는 **AI를 쓰지 않는다**

닫힌 폴리라인이 사각형인지 원인지는 인식이 아니라 **기하 계산**이다. RDP 단순화 + 도형 피팅으로 결정론적으로 나온다. 왕복이 없어 즉시 반응하고, 비용이 0이며, 같은 획에 늘 같은 답을 준다. ADR-0051이 이미 "AI 불필요"로 적어 둔 판단을 유지한다.

### 5. AI 결과는 **강사 클라이언트가 주입한다** — 서버가 publish하지 않는다

모델이 낸 것은 **제안**이고, 그것을 문서에 넣는 주체는 강사의 Excalidraw 씬이다. 그 뒤는 기존 경로를 그대로 탄다: `onChange` → diff → 데이터 채널 publish → 영속화 → Egress. 단일 writer가 유지되므로 revision 규약, z-order, 복원, 녹화가 전부 공짜로 따라온다.

### 6. **항상 확인받고 적용한다**

모델이 낸 `confidence`를 신뢰 근거로 쓰지 않는다. 실측에서 **틀린 라벨에 1.0을 줬다.** "확신도가 낮을 때만 확인받는다"는 성립하지 않는다.

### 7. GMS 호출은 **Spring이 직접 한다** — ai-api를 거치지 않는다

판서 해석에는 검색도 임베딩도 자막 컨텍스트도 없다. 이미지와 프롬프트를 GMS에 넘기고 툴콜 결과를 검증해 돌려주는 것이 전부다. ai-api를 거치면 홉과 HMAC 서명이 하나씩 늘 뿐 **파이썬이 할 도메인 일이 없다**.

**옮겨야 할 조건을 함께 못박는다.** 판서 해석이 강의 자료(RAG)나 자막 컨텍스트를 필요로 하게 되면 — 예: "이 다이어그램을 강의 자료의 용어로 라벨링" — 그때는 ai-api로 옮긴다. 검색이 들어오는 순간 그쪽이 맞는 자리다.

**이 결정은 되돌리기 싸다.** FE ↔ Spring 계약(§3-6e)은 어느 쪽이든 동일하므로, 나중에 내부 구현만 ai-api 호출로 바꾸면 되고 프론트는 손대지 않는다.

## 근거 (Rationale)

### 실측 — 모델은 의미를 읽고, 좌표를 틀린다

전부 **저장된 실제 판서**(세션 `964a793c`)를 op에서 복원해 잰 값이다. 모델은 `gpt-4.1`(GMS 게이트웨이), 온도 0.

**좌표를 물었을 때** — 같은 사각형을 두 방법으로 잰 값이다. 이미지 좌표(px).

| | 좌변 | 우변 | 상단 | 하단 |
|---|---|---|---|---|
| 획의 점에서 계산 (정답) | 324 | 1330 | 85 | 494 |
| 모델에게 질문 | 420 | 1400 | 110 | 540 |
| 오차 | **+96** | +70 | +25 | +46 |

그림 크기의 2~13%다. "손그림을 도형으로 정리"에 쓰면 정리된 도형이 눈에 띄게 튄다. 그런데 **그 좌표는 우리가 이미 정확히 갖고 있다.**

**의미를 물었을 때** — 3회 반복, 전부 동일.

| 대상 | 질문 | 결과 |
|---|---|---|
| 손글씨 수식 | LaTeX로 | `y = ax^2 + bx + c` — **정확**, 3/3 동일 |
| 손그림 다이어그램 | mermaid로 | 노드 3 · 화살표 2 · 방향 LR — **정확**, 3/3 동일 |
| 위 다이어그램의 한글 라벨 | — | 3개 중 2개 정확. `요청`을 `유정`으로 오독 |

**이것이 결정의 전부다.** 위상과 수식 내용은 신뢰할 수 있고, 위치는 신뢰할 수 없다. 그래서 좌표가 없는 중간 표현(mermaid·LaTeX)을 거친다.

### 왜 이미지를 보내는가 — 벡터가 더 정확한데도

판서 문서가 벡터인데 굳이 래스터화해 보내는 이유는, **필기 인식이 지각(perception) 문제**이기 때문이다. `[[0,0],[2,3],[5,7], ...]` 500쌍을 보고 `∫x²dx`를 읽어내는 것은 온라인 필기 인식이라는 별도 분야이고, `gpt-4.1`은 렌더된 이미지로 학습됐지 좌표 시퀀스로 학습되지 않았다. SVG path로 바꿔도 같다 — 모델이 SVG를 머릿속으로 렌더하지는 못한다.

그래서 **읽는 데만 이미지를 쓴다.** 벡터는 우리가 계속 들고 있되 <b>보내지 않는다</b> — 서버는 좌표를 쓰지 않고,
배치는 클라이언트가 원본 획의 `points`에서 직접 계산한다. 모델에게는 이미지와 함께 <b>강사가 고른 요소 `id`</b>만
넘긴다. 이미지만으로는 어느 요소를 지울지 "왼쪽 위 그거"라고밖에 지정하지 못하는데, `id`가 그 자리를 대신한다.

정리하면 이렇다. **좌표는 브라우저 안에서만 돈다.** 네트워크를 건너가는 것은 "무엇으로 읽혔는가"뿐이다.

### 왜 대상은 강사가 고르는가

모델에게 "어느 요소를 바꿀지" 맞히게 하지 않는다. 강사가 Excalidraw에서 선택한 요소 `id` 목록을 스코프로 넘긴다. 훨씬 안정적이고 의도도 분명하며, 선택이 곧 "이걸 지우고 저걸 넣어라"의 범위가 된다.

### 왜 raw Excalidraw JSON을 모델에게 뱉게 하지 않는가

요소 하나에 `seed`, `versionNonce`, `index`(fractional index), `roundness`, `boundElements` 같은 필드가 붙는다. 모델이 이것들을 맞게 채울 이유가 없고, 틀리면 씬이 깨지거나 z-order가 어긋난다(§3-6b가 이미 겪은 문제다). 좁은 스키마만 받고 **우리가 Excalidraw 요소로 변환**한다.

### mermaid 변환은 브라우저에서만 돈다

`parseMermaidToExcalidraw`는 mermaid가 글자 폭을 실측해 배치하므로 SVG `getBBox`가 필요하다. jsdom에서는 `text.getBBox is not a function`으로 실패한다(실측). 서버(Node)에서 돌리려면 헤드리스 브라우저가 필요하다.

**그런데 우리가 원하던 자리가 원래 브라우저다** — 결정 5에 따라 주입 주체가 강사 클라이언트이므로, 변환도 거기서 하는 것이 자연스럽다.

## 대안 (Alternatives)

**모델에게 좌표를 받는다.** 가장 단순하지만 실측 오차가 최대 96px이다. 정리된 도형이 원본에서 튀어 "정리"가 아니라 "이동"이 된다. 기각.

**스트로크 좌표를 모델에게 준다(온라인 필기 인식).** 데이터는 이미 있고(획 순서·점 순서, 타임스탬프는 없음) 이론적으로는 오프라인보다 유리하다. 그러나 범용 LLM은 이 형식을 읽지 못하고, 전용 온라인 인식 모델은 공개된 학습 가중치가 드물다. **전용 HMER 모델**(pix2tex·CoMER 등)을 내부 GPU 런타임에 올리는 선택지는 남겨 둔다 — 비용 0에 100ms급이고 우리에게 이미 `bge-runtime`이라는 같은 패턴이 있다. 다만 지금은 GMS 비전이 수식을 3/3 맞혔으므로 **새 배포 대상을 늘릴 근거가 없다.**

**서버가 데이터 채널에 직접 publish한다.** revision 채번의 단일 writer 전제가 깨진다. 번호가 충돌하면 수신 측이 정상 op를 "이미 본 op"로 버리는데, **강사 화면에는 그려지므로 드러나지 않는다.** 이 프로젝트에서 같은 모양의 버그를 이미 여러 번 겪었다. 기각.

**ai-api를 거친다.** 일관성("모든 LLM 호출은 ai-api")은 얻지만, 검색·임베딩이 없는 호출에 홉과 HMAC 서명이 하나씩 는다. 결정 7에 옮겨야 할 조건을 명시해 두었고, FE 계약이 동일하므로 되돌리기 싸다.

**도형 정리도 AI로 한다.** 왕복 1~3초, 호출당 비용, 같은 획에 다른 답. 기하 계산은 즉시·무료·결정론적이다. 기각.

## 영향·후속 (Consequences)

- **GMS API 키를 Spring도 갖게 된다.** 지금은 ai-api만 갖고 있다(`AI_API_GMS_API_KEY`). 같은 호스트의 같은 시크릿 파일(`/etc/liveclass/.env.prod`)에서 오므로 배포 경계는 늘지 않지만, **키를 가진 서비스가 둘이 된다**는 사실은 남는다.
- **브라우저는 GMS를 직접 부르지 않는다.** 키가 클라이언트에 노출된다. 반드시 Spring을 거친다.
- 인가는 **소유 강사만**이다(`LiveAccessGuard.requireOwner`). 판서를 고치는 행위이므로 §3-6d의 쓰기 게이트와 같다.
- 한글 라벨 오독이 남는다. **확인 UI가 기능의 일부**이지 부가가 아니다(결정 6).
- 후속으로 열린 것: 인식 결과를 다시보기 앵커(`session_ms`)와 묶어 "강사가 이 수식을 설명한 순간"으로 이동, 그리고 판서 텍스트를 RAG 컨텍스트로 넣기. 둘 다 좌표가 필요 없는 용도라 이 ADR의 제약을 받지 않는다.
- 계약은 [CONTRACT §3-6e](../../CONTRACT.md)에 적는다.
