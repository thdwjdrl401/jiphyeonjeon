# ADR-0127: 발송 워커를 별도 노드로 떼고, 늘어나는 노드에서는 주기 작업을 돌리지 않는다

- **상태**: 채택 — 코드·배포 구성 반영, 운영 전개는 미실시
- **일자**: 2026-08-18
- **관련**: [0073](0073-notification-fanout-architecture.md)(팬아웃 설계),
  [0122](0122-the-commit-wakes-the-relay.md)(릴레이 깨우기),
  [0123](0123-notification-partition-and-content.md)(알림 파티션),
  [0124](0124-push-delivery-queue-and-progress.md)(푸시 전용 큐)
- **적용 범위**: `docker-compose.prod.yml`, `AssetSchedulingConfig`,
  `NotificationFanoutWorker`·`PushDeliveryWorker`의 리스너 기동 조건, `application.yml`

## 한 줄 결정

발송을 별도 노드로 떼어 그 노드만 늘린다. 늘어나는 노드는 주기 작업과 Redis 스트림 소비를 켜지
않는다 — 이 앱의 주기 작업 대부분이 여러 대에서 동시에 도는 것을 전제로 쓰이지 않았기 때문이다.

## 왜

측정하니 팬아웃과 발송의 병목이 정반대였다. lazy(i7-6700HQ 4물리코어)에서 수강생 100만 명,
구독 1,097,488건 기준이다.

| 구간 | 앱 CPU | pg CPU | 워커 2배로 늘렸을 때 |
|---|---|---|---|
| 팬아웃 | 39% | 90% | 1.45배 (3대에서는 오히려 감소) |
| 발송 | 82% | 21% | 1.79배 |

팬아웃은 DB가 막는다. 워커를 늘려도 같은 Postgres를 두드리므로 2대에서 멈춘다. 발송은 건당
암호화(코어당 2,796건/s가 상한)와 기기 수만큼의 HTTPS라 앱 CPU가 막고, 공유 자원을 21%밖에 안 써서
노드를 늘린 만큼 늘어난다.

두 일이 한 프로세스에 있으면 서로 CPU를 훔친다. 같은 머신에서 동시에 돌렸을 때 발송이 1,636건/s,
구간을 갈라 돌렸을 때 2,654건/s였다. 그리고 늘리고 싶은 쪽만 늘릴 수가 없다.

## 어떻게

같은 산출물을 스위치 넷만 바꿔 배포한다.

| | web·팬아웃 | 발송 전용 |
|---|---|---|
| `notification.fanout.listener-enabled` | true | **false** |
| `notification.push.listener-enabled` | **false** | true |
| `liveclass.scheduling.enabled` | true | **false** |
| `caption` / `lecture-note` consumer | true | **false** |

기본값은 전부 켜짐이라 한 대로 돌리던 동작은 그대로다. 나누는 것은 배포의 선택이다.

발송 노드를 늘리는 것은 한 줄이다.

```
docker compose -f docker-compose.prod.yml up -d --scale backend-push=3
```

## 주기 작업을 통째로 끄는 이유

낭비가 아니라 정확성 때문이다. 노드를 늘리기 전에 확인한 결과, 이 앱의 `@Scheduled` 잡 중 여러
대에서 동시에 돌아도 안전하다고 **문서에 적혀 있는 것은 둘뿐**이었다 — `AssetReaper`(전이가
PENDING→FAILED 뿐이라 멱등)와 `AnnotationHighlightDescribeWorker`(아웃박스 UNIQUE가 재발행을 무시).

나머지는 확인되지 않았고, 그중 하나는 반대라고 스스로 적어 두고 있다.

> **단일 인스턴스 전제다.** 여러 대로 늘리면 같은 행을 두 인스턴스가 집어 아웃박스에 두 줄이
> 들어갈 수 있다. — `LiveStartingSoonScheduler`

여덟 개 잡을 각각 감사하고 필요한 곳에 잠금을 넣는 것이 정공법이지만, 지금 필요한 것은 발송
확장이고 발송 노드는 그 잡들을 하나도 필요로 하지 않는다. **늘어나는 노드에서는 주기 작업을 아예
돌리지 않는다**는 규칙이 감사보다 싸고, 무엇보다 확실하다.

이 앱에서 `@EnableScheduling`은 `AssetSchedulingConfig` 한 곳뿐이라 스위치도 하나면 된다. 빈을
지우는 것이 아니라 스케줄 등록만 끄므로 주입 관계는 그대로고, 다른 코드가 잡을 직접 부르는
경로는 살아 있다. `SchedulingActivationTest`가 스위치가 실제로 먹는지와 설정 빈이 남는지를
확인한다 — 후자는 바깥 클래스에 조건을 걸었다가 `AssetReaperProperties`까지 사라져 기동이
실패했던 실수를 막는다.

Redis 스트림 소비자(자막·강의노트)는 consumer 이름이 고정이라 두 노드가 같은 이름으로 붙으면
서로의 pending을 건드린다. 발송 노드는 자막·노트와 무관하므로 아예 붙지 않는다.

`container_name`도 뺐다. 이름이 박혀 있으면 복제본을 만들 수 없고, 그것이 이 앱이 구조적으로 한
대였던 이유 중 하나였다. nginx는 서비스명으로 찾으므로 이름이 없어도 닿는다.

## 이 결정이 풀지 않는 것

**팬아웃은 여전히 한 대다.** 워커를 늘려도 안 빨라지는 것이 측정으로 확인됐으므로 늘릴 이유가 없고,
100만 명 팬아웃이 22.8초(체인 2개·조각 5,000명, 앱 1코어·pg 2코어·브로커 1코어)라 1분 예산 안에
들어온다. 더 필요해지면 그때는 워커가 아니라 DB 쪽(코어·쓰기량·샤딩)을 봐야 한다.

**공급자 한도는 우리가 못 정한다.** 100만 명을 1분에 보내려면 분당 108만 건인데 FCM의 프로젝트 기본
한도는 분당 60만 건이다. Web Push(VAPID) 경로가 그 한도에 걸리는지는 문서에 없어 확인하지 못했다.
서버를 늘려 낼 수 있는 속도와 실제로 받아 주는 속도는 별개이며, 429 처리가 이론이 아니라 반드시
지나가는 경로라는 뜻이다(현재 429 후 재시도 기한이 끝난 기기가 "시도 완료"로 기록돼 영구 유실되는
경로가 있다 — 별건으로 고친다).

**여러 대가 안전한지 감사하지 않았다.** 위의 여덟 개 잡은 여전히 미확인이다. 팬아웃 노드를 둘 이상으로
늘리려면 그때 감사가 필요하다. 지금은 주기 작업을 도는 노드가 하나뿐이라 문제가 되지 않는다.
