# ADR-0119: 아무도 없는 라이브는 스스로 끝난다

> 📍 하네스 개요: [../../harness/README.md](../../harness/README.md) · 판단 정책: [../../harness/POLICY.md](../../harness/POLICY.md)

- **상태**: 채택
- **일자**: 2026-08-10
- **관련**: Sub Ⅲ · [ADR-0034](0034-egress-completion-webhook.md)(egress webhook) · [ADR-0078](0078-livekit-ports-off-the-blocked-range.md)(방 유예값) · choinhoo/0003(종료 오케스트레이션)

## 맥락 (Context)

강사가 **종료를 누르지 않고 창을 닫으면** 세션이 `LIVE`인 채로 영원히 남는다. 코드 경로를 따라가 보면
끝낼 사람이 아무도 없다.

- `ENDING`/`ENDED`로 바꾸는 곳은 `LiveEndTransitions` 하나이고, 그것을 부르는 것은
  `LiveEndOrchestrator` 하나이며, 그것을 부르는 것은 **종료 API 하나뿐**이다.
- LiveKit webhook은 `egress_ended`만 다룬다. `room_finished`는 파싱 전에 걸러진다.
- 시작 쪽에는 `LiveStartReconciler`가 있는데 **종료 쪽에는 대응물이 없다.**

남는 것은 유령 세션이다. 수강생 화면은 계속 진행 중으로 보이고, 운영 콘솔의 진행 목록에 쌓이며,
그 방과 Egress가 전역 슬롯을 문다. 녹화만은 정상으로 끝난다 — 방이 닫히면 egress도 끝나고
`egress_ended`가 오기 때문이다. **녹화는 완결되는데 세션만 방치되는** 어긋난 상태다.

## 결정 (Decision)

시스템이 끝내는 경로를 만든다. **두 갈래를 함께** 둔다.

1. **`room_finished` webhook** — LiveKit이 방을 닫았다는 것은 아무도 남지 않았다는 뜻이다.
   그 방의 세션이 진행 계열이면 `ENDED`로 확정한다. video 모듈이 받아 `live.api.LiveRoomLifecycle`
   포트로 넘긴다.
2. **`LiveEndReconciler`** — 주기적으로(60초) 진행 계열 세션의 방을 보고, **비어 있는 채로
   유예가 지나면** 종료한다.

둘 다 필요하다. webhook은 빠르고 정확하지만 **강사만 나가고 학생이 남으면 방이 안 닫혀 오지
않는다.** 재조정기는 느리지만 그 경우를 포함해 전부 본다.

사람이 부르는 종료와 **경로를 갈라 둔다**(`beginBySystem`/`completeBySystem`). `requesterId` 자리에
`instructorId`를 넣어 소유권 검사를 우회하는 방식이면 검사가 형식만 남고, 어느 종료가 시스템이 한
일인지 로그에서 구분되지 않는다.

## 근거 (Rationale)

**왜 방이 비었다는 관측 하나로 끊지 않나.** 강사가 새로고침하거나 네트워크가 튀면 수십 초 동안
방이 빈다. 그래서 *비어 있기 시작한 시각*을 기억해 두고 유예가 지나야 끝낸다. 그 기억은 메모리에만
두는데, 재시작하면 타이머가 처음부터 도는 오차는 **안전한 쪽**이다 — 늦게 끝낼지언정 살아 있는
강의를 끊지 않는다.

**유예의 하한은 우리가 고르는 값이 아니다.** 이걸 짜다가 발견했는데,
`livekit.room-departure-timeout-seconds`가 이미 **10분**으로 설정돼 있다(`livekit.yaml`이 아니라
백엔드가 방을 만들 때 넣는다). 그 10분은 "와이파이 전환처럼 수십 초 끊기는 일이 흔하다"는 이유로
LiveKit 기본값 20초에서 **일부러 올린** 값이고, 그동안 방은 비어 있다 — 돌아올 강사를 기다리는
중이라서다.

그보다 먼저 세션을 끊으면 **그 결정을 무효로 만든다.** 강사가 8분 만에 돌아왔는데 세션이 이미
`ENDED`면 방을 10분 열어 둔 의미가 없다. 그래서 `empty-grace` 기본값을 12분으로 두고,
설정이 이탈 유예보다 짧으면 **기동 시 끌어올리고 경고를 남긴다**. 값 하나가 다른 값의 전제를
조용히 깨뜨리지 못하게 코드로 막았다.

**시스템 경로는 외부 제어 실패에 다르게 반응한다.** 사람이 부르는 종료는 Room 삭제가 실패하면
예외를 올려 강사가 다시 누르게 하지만, 여기는 다시 누를 사람이 없다. 게다가 이 경로가 열리는 조건
자체가 *방이 이미 없거나 비어 있다*는 것이라 실패의 대부분은 "지울 게 없다"다. 로그만 남기고
`ENDED`까지 간다 — 여기서 멈추면 세션이 `ENDING`에 갇혀 문제가 그대로 남는다.

## 대안 (Alternatives)

| 대안 | 장점 | 단점 |
|---|---|---|
| **webhook + 재조정기 (선택)** | 빠른 경로와 빠짐없는 경로를 둘 다 가짐 | 코드가 둘, 유예값 조율이 필요 |
| `room_finished` webhook만 | 간단, 정확, 즉시 | **강사만 이탈하면 영영 안 옴** — 가장 흔한 시나리오를 못 잡는다 |
| 재조정기만 | 모든 경우를 덮음 | 방이 이미 닫힌 뒤에도 최대 1주기 늦음. 즉시성이 없다 |
| `participant_left`로 강사 이탈 감지 | 가장 빠름 | 순단마다 신호가 온다. 재접속 판정을 우리가 다시 만들어야 하는데, 그건 이미 LiveKit의 이탈 유예가 하는 일이다 |
| 손으로 정리(현행) | 코드 0 | 운영자가 계속 봐야 한다. 실제로 방치되고 있었다 |

## 영향·후속 (Consequences)

- **실질적인 종료 시점은 재조정기가 정한다.** 이탈 유예 10분 → `room_finished`는 그 뒤에 오는데,
  재조정기 유예가 12분이라 둘이 비슷하게 붙는다. 방이 닫히면 webhook이 먼저 오고, 학생이 남아
  방이 안 닫히면 재조정기가 12분에 끝낸다.
- **단일 인스턴스 전제**가 하나 더 늘었다. 여러 대로 늘리면 `emptySince` 기억이 인스턴스마다
  따로 놀고 같은 세션을 여럿이 집는다. 종료 자체는 행 잠금과 상태 검사가 막지만 헛일이 는다.
- `EgressWebhookEvent`가 egress 전용이 아니게 됐다. 이름은 그대로 두되 javadoc에 두 이벤트를
  받는다고 적었다 — 이름을 바꾸면 이 MR의 diff가 본질과 무관하게 커진다.
- **아직 운영에서 재현해 보지 않았다.** 프로덕션에 시작된 라이브 세션이 없어(로그 0건) 이 경로가
  실제로 어떻게 도는지 본 적이 없다. 첫 라이브 때 `시스템이 라이브 세션을 종료함` 로그를 확인한다.
- `STARTING`은 건드리지 않는다. 시작 게이트에 lease와 재조정이 따로 있어(`LiveStartReconciler`)
  두 루프가 같은 세션을 반대로 밀면 안 된다. 시작에서 멈춘 세션은 그쪽 몫이다.
