# ADR-0027: 프론트 mock→실 API 전환은 서비스 단위 점진 교체로 한다 (기능별 플래그 없이)

> 📍 하네스 개요: [../../harness/README.md](../../harness/README.md) · 판단 정책: [../../harness/POLICY.md](../../harness/POLICY.md)

- **상태**: 일부 대체 — 직접 demo 호출 허용과 선택 규칙은 [ADR-0014](../yoongwanghyeok/0014-operation-level-hybrid-api-routing.md) 적용
- **일자**: 2026-07-22
- **관련**: Sub Ⅱ / CP0 · [ADR-0026](0026-catalog-viewer-context.md)

## 맥락 (Context)

프론트는 `VITE_USE_MOCK_API` 하나로 mock/실 API를 고르는데, `shared/api/client.ts`의 요청
인터셉터가 **mock 모드에서는 모든 네트워크 요청을 예외로 막고 있었다.**

그래서 실 API로 옮긴 서비스가 몇 개 있어도, 플래그를 켜 둔 동안에는 그 서비스마저 백엔드에 닿지 못했다.
전환하려면 모든 화면을 한 번에 옮겨야 하는 **전부 아니면 전무** 스위치였고, 남은 화면이 많은 상태에서는
켤 수 없었다.

"기능별 플래그로 쪼개자"는 안이 먼저 나왔지만, 확인해 보니 전제가 틀려 있었다. mock 전용 화면들은
`features/demo/*`를 **직접 import**하고 플래그를 참조하지 않는다. 즉 플래그를 꺼도 그 화면들은 깨지지
않고 계속 demo 데이터를 그린다. 실제로 막고 있던 건 인터셉터 하나였다.

## 결정 (Decision)

- 네트워크 차단을 **테스트 모드에서만** 건다(`runtime.ts`의 `isNetworkBlocked`). dev에서는 mock 플래그와
  무관하게, 실 API 경로가 있는 서비스는 백엔드로 나간다.
- 전환은 서비스 단위로 한다. `requestByDataSource({ mock, http })`에서 mock 갈래를 지우며 옮기고,
  전부 옮기면 `dataSource.ts`를 삭제한다. **기능별 플래그는 만들지 않는다.**

## 근거 (Rationale)

- 진행도가 코드에 그대로 드러난다 — 남은 mock 갈래 수 = 남은 일. 별도 플래그 목록을 따로 관리하며
  코드와 어긋나게 두지 않는다.
- 테스트에서 차단을 유지하는 이유는 반대다. 테스트는 결정적이어야 하고, 선택 경계를 우회한 요청이
  실제로 나가면 조용히 느려지거나 CI에서만 실패한다. 그건 계속 막는 게 맞다.
- 플래그를 늘리면 조합 수만큼 상태가 생기고, 대부분은 아무도 실행해 보지 않은 조합이 된다.

## 대안 (Alternatives)

| 대안 | 장점 | 단점 |
|---|---|---|
| (선택) 차단은 테스트만, 서비스 단위 교체 | 변경 최소, 진행도가 코드에 드러남 | 전환 중에는 한 화면 안에 실데이터와 demo가 섞여 보일 수 있음 |
| 기능별 mock 플래그 | 화면 단위로 통제 | 플래그·조합 폭증, 코드와 플래그 목록이 어긋남 |
| 한 번에 전면 전환 | 상태가 단순 | 미구현 API(다시보기·자막·진도)에 막혀 착수 자체가 불가 |
| MSW로 전면 대체 | mock/실 API 경계가 네트워크로 통일 | 지금 단계에선 도입 비용이 전환 이득보다 큼 |

## 영향·후속 (Consequences)

- 전환 중에는 화면에 따라 실데이터와 demo 데이터가 섞인다. 의도된 중간 상태이며, 남은 화면은
  아래 순서로 옮긴다: 내 커리큘럼 → 커리큘럼 관리 → 레슨 → 라이브 → 다시보기.
- mock 갈래를 지운 서비스의 테스트는 HTTP 레벨 목(MSW 등)으로 옮겨야 한다. 그 시점에 MSW 도입을
  다시 판단한다.
- `.env`·`.env.example` 주석을 새 의미(옮긴 서비스만 http)로 갱신했다.
