# ADR-0083: 학생 진행률이 늘 0%였던 이유 — 진도를 보내는 쪽이 없었다

> 📍 하네스 개요: [../../harness/README.md](../../harness/README.md) · 아키텍처: [../../ARCHITECTURE.md](../../ARCHITECTURE.md) · 계약: [../../CONTRACT.md](../../CONTRACT.md)

- **상태**: 채택
- **일자**: 2026-08-05
- **관련**: [0033](0033-learning-progress-wiring.md)(진도 API·카탈로그 progress), [0063](0063-watch-heatmap-buckets.md)(칸 기준 진도 계산), [0024](0024-orphan-module-scaffolding.md)(learning 골격)
- **오너 경계**: FE — 진도 전송 배선 / BE — 목차 레슨별 learning 채우기

## 맥락

학생 화면의 수강 진행률이 움직이지 않았다. 커리큘럼 카드도, 목차의 완료 표시도, 다시보기의
"학습 진행률 n%"도 전부 0이었다.

찾아보니 **고장난 곳이 없었다.** 양쪽 끝이 다 있었다.

| | 상태 |
|---|---|
| `PUT /api/lessons/{id}/progress` | 구현됨 — 계약 테스트 8건([0033](0033-learning-progress-wiring.md)) |
| 커리큘럼 진도 집계(`CatalogService`) | 구현됨 — 완료 레슨 수 기준 |
| 진행률을 그리는 화면 4곳 | 구현됨 |
| **그 API를 호출하는 코드** | **없음** |

`frontend/src` 전체에서 `/progress`로 나가는 PUT이 0건이었다. `learning_progress` 테이블에
행이 한 번도 생기지 않았고, 집계는 빈 테이블을 정확하게 읽어 0%를 냈다.

**중간 조각도 이미 있었다.** [0063](0063-watch-heatmap-buckets.md)이 "진도는 칸 데이터에서
파생된다"고 정하면서 `bucketProgressPercent(state, durationMs)`를 만들어 두었고, 단위 테스트도
6건 붙어 있다. 그런데 **아무도 호출하지 않는다.** 칸을 세고 보고하는 훅도 있고, 그 칸으로
진도율을 내는 함수도 있고, 받을 엔드포인트도 있는데, 셋을 잇는 한 줄이 없었다.

두 ADR의 후속 항목이 각각 절반씩 남은 결과다.

- [0033](0033-learning-progress-wiring.md): "`learning-context`·`progress`는 아직 화면에서 쓰지 않아 어댑터 미배선 — 화면이 생기면 그때 연결한다."
  → 화면이 생겼고 **읽는 쪽(`learning-context`)만** 연결됐다.
- [0063](0063-watch-heatmap-buckets.md): "화면이 아직 없다. 서버만 섰고 클라이언트 집계·전송은 후속이다."
  → 집계·전송이 붙었지만 **재시청 그래프까지만**이고 진도는 빠졌다.

## 결정

### 1. 진도는 칸을 보내는 그 주기에 함께 보낸다

새 훅도 새 타이머도 만들지 않는다. `useWatchTracking`의 flush(15초 · `pagehide` ·
`visibilitychange` · 언마운트)에서 `bucketProgressPercent`를 불러 같이 보낸다.

진도율이 칸에서 파생되는 값이므로 따로 셀 것이 없고, 타이머를 하나 더 두면 두 값이 서로 다른
시점을 가리키게 된다.

**계산은 재생 위치 비율이 아니라 본 칸 수다**([0063](0063-watch-heatmap-buckets.md)) — 재생바를
끝으로 끌었다고 완료가 되어서는 안 된다.

### 2. 강의 길이를 모르면 진도를 보내지 않는다

`durationMs`가 null이면(진행 중인 라이브, 또는 녹화 완료 webhook 전) 칸만 보낸다. 전체 칸 수를
모르는 채로 낸 비율은 "지금까지 나온 것 중 몇 %"라 늘 100%에 가깝고, **듣고만 있어도 완료가
찍힌다.**

**라이브로 들은 시간이 사라지지는 않는다.** 라이브 중에도 칸은 그대로 서버에 쌓이고, 나중에
다시보기를 열면 그 누적을 물려받아 진도로 환산된다.

### 3. 진도 실패가 칸 보고를 되돌리지 않는다

둘은 다른 엔드포인트다. 진도가 실패했다고 칸을 다시 보내면 **재시청 횟수만 부풀 뿐** 진도가
살아나지 않는다. 진도는 다음 주기에 더 큰 값으로 다시 나간다 — 본 칸 수는 줄지 않으므로 한 번
놓쳐도 따라잡는다.

### 4. 녹화강의 재생 화면에도 같은 훅을 붙인다

`RecordedLessonPlaybackPage`에는 시청 추적이 아예 없었다. 그런데 **게시된 RECORDED 레슨은
커리큘럼 진도의 분모에 들어간다**(`CatalogService.computeEnrolledProgress`). 세지 않으면 그
강의만 영원히 미완료로 남아 **커리큘럼 전체 진행률을 끌어내린다.**

### 5. 목차 레슨별 `learning`을 채운다

`CatalogService`가 `CatalogOutlineLesson`의 마지막 인자를 `null`로 넘기고 있었다. 커리큘럼
`progress`는 "몇 강을 끝냈나"만 말하므로, 목차에서 **어느** 강의를 끝냈는지는 이 필드가 있어야
보인다. 진행률 막대는 움직이는데 목차의 완료 표시는 비어 있는 상태였다.

같은 조회 결과(`findProgressByLesson`)로 둘 다 채운다 — **쿼리는 늘지 않는다.**

진도 기록이 없는 레슨은 **null 그대로** 둔다. 0%로 채우면 "안 본 강의"와 "보다 만 강의"가
화면에서 같아진다.

## 함께 고친 것 — seed 시점의 칸이 빠지고 있었다

테스트를 쓰다 걸렸다. 칸을 세는 효과는 `positionMs`가 바뀔 때만 도는데, 서버 누적을 받아오는
동안 위치가 그대로였으면 seed 뒤에 다시 돌지 않는다. 그래서 **seed 시점에 있던 칸이 통째로
빠졌다** — 0:00에서 시작하는 재생에서는 늘 첫 칸이었다.

재시청 그래프에서는 눈에 띄지 않는 오차지만, 진도에서는 다르다. **한 칸이 비면 끝까지 봐도
100%에 닿지 않는다.** 짧은 강의일수록 크다(10분 강의면 한 칸이 1.7%p).

seed 직후 현재 위치로 한 번 전진시키는 것으로 고쳤다.

## 고려한 대안

| 대안 | 판단 |
|---|---|
| 서버가 칸에서 진도를 계산 | 전체 칸 수를 알려면 강의 길이가 필요하고 그건 video 모듈에 있다 — learning이 새 의존을 갖는다([0063](0063-watch-heatmap-buckets.md) §3이 이미 기각) |
| 진도 전용 훅·타이머를 새로 | 같은 데이터를 두 번 세고 두 값이 서로 다른 시점을 가리킨다 |
| 재생 위치 비율(`position / duration`) | 스킵 한 번으로 완료가 찍힌다([0063](0063-watch-heatmap-buckets.md) §2가 이미 기각) |
| 라이브에서도 진도 전송 | 진행 중에는 전체 길이를 모른다. 지금까지 나온 길이로 나누면 듣고만 있어도 100% |
| 목차 learning을 위해 조회 추가 | 커리큘럼 progress가 같은 조회를 이미 한다 — 결과를 나눠 쓰면 된다 |

## 결과와 한계

### 검증

- `useWatchTracking.test.tsx` **6건** — 길이를 알면 진도를 보냄(칸 기준 30%이지 위치 기준 20%가
  아님) · 길이를 모르면 안 보냄 · **seed 시점 칸 포함** · 안 바뀌면 재전송 안 함 · 진도 실패가
  칸을 되돌리지 않음 · 꺼져 있으면 요청 없음
- `LearningContractTest` **+2건** — 목차 레슨이 내 학습 상태를 실음(안 본 강의는 null) ·
  비수강자에게는 안 보임
- **돌연변이 확인 2회**: 진도 전송을 지우면 FE 3건이, `withLearning`을 지우면 BE 1건이 깨진다.
- 프론트 1,037건 통과 · typecheck·lint 통과

### 한계

- **라이브만 듣고 다시보기를 한 번도 열지 않으면 진도가 잡히지 않는다.** 칸은 쌓이지만 길이를
  알 방법이 그 화면에 없다. 서버가 환산하려면 §고려한 대안의 첫 줄로 돌아가야 한다.
- 배속 재생·건너뛰며 훑기를 구분하지 않는다([0063](0063-watch-heatmap-buckets.md)에서 그대로
  물려받는 한계). "재생됐다"만 센다.
- 완료 임계 90%는 [0033](0033-learning-progress-wiring.md) 그대로다. 칸 기준으로 바뀌었으니
  체감이 달라질 수 있는데, 실사용 값을 보고 판단한다.
- 이미 강의를 들은 사용자의 지난 진도는 **소급되지 않는다.** 칸 기록이 남아 있는 레슨은 다음에
  열 때 그 누적으로 환산되지만, 칸도 없던 시기의 시청은 복구할 수 없다.
