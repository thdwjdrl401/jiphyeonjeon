# ADR-0078: LiveKit을 막힌 포트 대역 밖으로 옮긴다 — 미디어 3478/udp, 시그널링 443

> 📍 하네스 개요: [../../harness/README.md](../../harness/README.md) · 아키텍처: [../../ARCHITECTURE.md](../../ARCHITECTURE.md) · 계약: [../../CONTRACT.md](../../CONTRACT.md)

- **상태**: 채택
- **일자**: 2026-08-05
- **관련**: [0032](0032-media-playback-hls-only.md)(HLS 재생 토폴로지), [0034](0034-egress-completion-webhook.md)(Egress 완료 웹훅),
  `infra/livekit/README.md`
- **오너 경계**: 인프라(송정기) — 포트·nginx·방화벽 / FE — 없음(접속 주소를 토큰 응답으로 받는다) / BE — 환경변수 한 줄

## 맥락

특정 네트워크에서 라이브 강의 입장이 통째로 실패했다. 핫스팟으로 바꾸면 즉시 정상이라 서버 문제가
아닌 것은 분명했지만, **무엇이 막히는지** 모르는 채로는 우회할 수 없었다.

실측했다. 문제의 망에서 우리 서버로 보내고, 서버에서 `tcpdump`로 도착 여부를 셌다 — 클라이언트 쪽
추측이 아니라 도착 사실을 본 것이다.

**TCP**

| | 포트 |
|---|---|
| 통과 | 22 · 443 · 4000 · 4001 · 5433 · 8988~8991 · 9090 |
| 무응답(drop) | **7443 · 7881** |

**UDP** — 12회씩 보내고 서버 도착 수를 셈

| | 포트 |
|---|---|
| 12/12 도착 | **3478 · 19302 · 50000** |
| 0/12 도착 | **7882 · 7881 · 443 · 123 · 8882 · 10000** |

**왕복** — 서버에 에코를 띄우고 측정

```
udp/3478    14/14 응답   평균 10ms (6~25ms)
udp/50000   13/14 응답   평균  8ms (6~12ms)
```

TCP와 UDP가 **같은 패턴**이다. 이 망은 WebRTC를 막는 것이 아니라 **7000~7999 대역을 막는다.**
오히려 STUN 표준 포트(3478)는 열어 두었다. 하필 LiveKit 기본값이 전부 그 대역 안에 있었다 —
7443(시그널링)·7882(UDP 미디어)·7881(ICE-TCP)·7880(내부).

처음에는 공개 STUN 네 곳이 무응답인 것만 보고 "UDP 전면 차단"으로 판단했다. **틀렸다.** 표본이 두
포트뿐이라 "WebRTC 포트만 막힘"과 "UDP 전체 차단"을 구분하지 못했다. 그 판단대로 갔으면 ICE-TCP
릴레이를 도입해 **필요 없는 화질 저하**를 떠안을 뻔했다.

## 결정

### 1. UDP 미디어를 3478로 옮긴다

`rtc.udp_port: 7882 → 3478`.

3478을 고른 이유는 실측에서 왕복이 확인됐고(14/14, 10ms), **STUN 표준 포트**라 WebRTC를 허용하는
망이라면 열려 있을 가능성이 가장 높기 때문이다. 50000도 통과했지만 임의 포트라 다른 망에서의 보장이
없다.

**AWS 보안그룹 작업이 필요 없다.** 위 UDP 패킷이 EC2 NIC까지 도달했는데, 보안그룹은 NIC 앞단에서
거른다 — 도달했다는 사실 자체가 3478/udp 인바운드 허용의 증거다. 서버 쪽은 `ufw allow 3478/udp` 한
줄이면 된다.

### 2. 시그널링을 443의 `/livekit` 경로로 옮긴다

앱 nginx에 `location /livekit/`를 두고 LiveKit 7880으로 프록시한다. **새 포트를 열지 않는다.**

443을 고른 이유는 HTTPS라 어떤 망에서도 열려 있고, 이 서버의 STOMP WebSocket(`/api/ws`)이 문제의
망에서 이미 동작하는 것을 확인했기 때문이다. 8988~8991도 통과했지만 그건 이 망의 사정일 뿐, 다음
망에서도 그러리라는 근거가 없다.

경로 끝의 슬래시(`proxy_pass http://...:7880/`)가 `/livekit` 접두사를 떼어 낸다 — LiveKit이
`/rtc`·`/rtc/validate`로 라우팅하므로 이게 없으면 404다.

### 3. 7443 리스너는 그대로 둔다

지우지 않는다. 되는 망에서는 한 홉 짧고, 무엇보다 **문제가 생기면 `LIVEKIT_URL` 한 줄로 되돌릴 수
있다.** 미디어 스택 nginx는 건드리지 않는다.

### 4. 브라우저용 주소만 바꾼다. 서버 API 주소는 그대로 둔다

`LIVEKIT_URL`만 `wss://jiphyeonjeon.thdwjdrl.com/livekit`로 바꾸고, `LIVEKIT_API_URL`은
`https://jiphyeonjeon.thdwjdrl.com:7443` 그대로 둔다.

막힌 것은 **브라우저가 있는 망**이지 서버가 아니다. 백엔드는 EC2 안에서 나가므로 7443이 멀쩡하다.
바꿀 이유가 없는 것을 함께 바꾸면 문제가 생겼을 때 어느 쪽 때문인지 못 가린다.

### 5. LiveKit에 붙는 것이 브라우저만은 아니다 — 전부 확인했다

| 소비자 | 어떻게 붙나 | 이 결정의 영향 |
|---|---|---|
| 브라우저(강사·수강생) | `LIVEKIT_URL`(토큰 응답에 실림) | **바뀐다** — 시그널링 `/livekit`, 미디어 3478/udp |
| 백엔드(방 제어·Egress 시작) | `LIVEKIT_API_URL` = `https://…:7443` | 그대로. EC2 안에서 나가므로 7443이 멀쩡하다 |
| Egress(녹화) | `egress.yaml` `ws_url: ws://localhost:7880` | 그대로. co-located라 공개 포트를 타지 않는다 |
| Egress 합성 페이지 | LiveKit이 `?url=`에 **자기 `ws_url`**을 붙여 연다 | 그대로. 우리 `livekit.url`이 아니다 |
| STT 에이전트(AI팀 로컬) | SSH 터널 → `wss://localhost:7443` + **relay-only TURN** | **7443 유지가 전제다**(아래) |
| coturn | `127.0.0.1:3478/tcp`, `no-udp` | 충돌 없음(아래) |
| 미디어 스택 nginx | 7443 → `127.0.0.1:7880` | 그대로 |

**7443을 남기는 두 번째 이유가 여기 있다.** STT 에이전트는 EC2가 아니라 AI팀 로컬에서 돌고
`-L 7443:localhost:7443` 터널로 시그널링에 붙는다(`ai/realtime-agent/scripts/start_ec2_tunnels.sh`).
7443을 걷어내면 자막이 통째로 죽는다.

**EC2에는 coturn이 이미 돌고 있다.** 진단 중에 발견했다 — `listening-ip=127.0.0.1`,
`listening-port=3478`, **`no-udp`**, `relay-ip=172.26.6.162`, relay 범위 49160~49200.
STT 에이전트가 `turn:127.0.0.1:3478?transport=tcp`로 relay-only ICE를 쓰기 위한 것이다
(SSH 터널은 TCP만 나르므로 미디어를 TURN over TCP로 우회시킨다).

LiveKit의 UDP 3478과 **충돌하지 않는다.** coturn은 TCP만, 그것도 루프백에만 붙는다. 진단용
에코 서버가 coturn이 떠 있는 상태에서 `0.0.0.0:3478/udp`에 바인딩하는 데 성공한 것이 실증이다.
coturn의 피어 제한은 IP 단위(`denied-peer-ip`)이고 포트 단위 규칙은 없다.

다만 에이전트 미디어가 coturn relay → LiveKit 후보(`172.26.6.162:3478/udp`)로 흐르게 되므로,
**AI팀이 자막 파이프라인을 한 번 확인해야 한다.** 여기서 turnutils로 재보려 했으나 대조군
(피어 포트 50000)도 같은 결과라 하네스가 동작하지 않은 것으로 판단했다 — 3478이 특별히
거부된다는 증거는 없지만, 릴레이가 실제로 도는지도 증명하지 못했다. 문제가 생기면
`udp_port`를 50000으로 바꾸면 된다(그쪽도 왕복 13/14로 확인해 뒀다).

### 6. ICE-TCP(7881)는 옮기지 않는다

막힌 대역에 있지만 그대로 둔다. UDP가 뚫린 이상 이 망의 해법이 아니고, TCP 쪽은 3478/50000을
**실측하지 않았다.** 재지 않은 값으로 옮기는 것은 추측을 하나 더 얹는 일이다.

### 7. 적용 순서를 못 지키면 전체 미디어가 죽는다

**레포의 `infra/livekit/livekit.yaml`은 템플릿이다.** 실제로 뜨는 것은 호스트의
`/etc/liveclass/livekit/livekit.yaml`(실 시크릿)이고 compose가 그것을 마운트한다. CI의
`deploy-livekit`은 `docker compose up -d`만 하므로 **포트 변경은 배포로 적용되지 않는다.**
사람이 호스트 파일의 `udp_port` 한 줄을 고치고 LiveKit을 재시작해야 한다.

순서가 중요하다.

1. `ufw allow 3478/udp` — **먼저.** 이걸 빼고 재시작하면 3478이 막혀 있어 되던 망까지 미디어가 죽는다.
2. `ufw allow from 172.16.0.0/12 to any port 7880 proto tcp` — 앱 nginx가 시그널링을 넘길 통로.
   브리지 대역을 넓게 잡은 것은 도커 네트워크를 다시 만들면 서브넷이 바뀌기 때문이다.
3. 앱 스택 배포(nginx `/livekit` + `LIVEKIT_URL`).
4. 호스트 `livekit.yaml`의 `udp_port` 수정 → LiveKit 재시작(**진행 중 라이브 세션이 끊긴다**).

3까지만 해도 안전하다 — 되는 망은 그대로고, 막힌 망은 시그널링만 붙고 미디어가 안 될 뿐
(지금은 아예 못 붙으므로 나빠지지 않는다). 4가 마지막인 이유다.

`7882/udp` 허용은 남겨 둔다. 되돌릴 때 방화벽을 다시 만지지 않아도 되게.

## 고려한 대안

**ICE-TCP 릴레이로 전환.** 첫 오진("UDP 전면 차단")을 따랐다면 이것이 답이었다. head-of-line
blocking 때문에 지연·끊김이 UDP보다 눈에 띄게 나빠진다 — 강의 송출에서는 체감되는 손해다. 재보니
필요 없었다.

**내장 TURN(+TLS)을 443에 붙이기.** 가장 범용적인 해법이지만 앱 nginx가 443을 쓰고 있어 충돌한다.
`ssl_preread`로 SNI 분기를 하려 해도 **도메인이 하나뿐이라 SNI가 같아** 갈라낼 수 없다. ALPN에
기대야 하는데 브라우저 TURNS는 ALPN을 싣지 않아 취약하다. 근본 제약은 DNS 콘솔 권한이 없어
서브도메인을 만들 수 없는 것이다.

**시그널링을 8988~8991 같은 통과 포트로 옮기기.** 이 망에서는 되지만 다음 망에서의 근거가 없다.
443은 그 질문 자체가 성립하지 않는다.

**미디어 스택 nginx(7443)를 443으로 합치기.** 앱 nginx와 포트가 겹친다. 경로로 나누면 될 일을
스택 구조를 바꿔서 풀 이유가 없다.

## 결과

- 7000번대를 막는 망에서 라이브 강의가 **UDP 그대로** 동작한다. 화질 저하가 없다.
- 새로 여는 포트는 `3478/udp` 하나뿐이고, 보안그룹은 이미 허용 중이라 ufw 한 줄이다.
- FE 코드 변경이 없다 — 접속 주소는 토큰 응답(`livekitUrl`)으로 받는다.
- 롤백이 환경변수 한 줄이다(`LIVEKIT_URL`을 `wss://…:7443`으로 되돌리면 즉시 원복).
- 앱 nginx가 미디어 스택에 의존하게 된다. 다만 `/livekit`이 죽어도 앱의 나머지 경로는 영향이 없고,
  그 반대도 같다.
- **AI팀 확인이 필요하다.** STT 에이전트의 미디어가 coturn relay를 타고 LiveKit의 새 후보 포트로
  흐른다. 시그널링(7443)은 그대로라 붙기는 붙는다.

## 검증

측정은 전부 문제의 망에서, 도착 여부는 서버 `tcpdump`로 확인했다(위 표).

배포 후 확인할 것:

- 문제의 망에서 `wss://jiphyeonjeon.thdwjdrl.com/livekit` 시그널링 연결
- 같은 망에서 강의 입장 → 영상·음성 송수신
- ICE 후보에 `3478/udp`가 실리고 실제로 선택되는지(`chrome://webrtc-internals`)
- 되는 망(핫스팟)에서 회귀 없음
- Egress 녹화가 계속 동작(`ws://localhost:7880` 직결이라 무관해야 한다)
- **STT 자막이 계속 동작**(AI팀 로컬 에이전트 → 터널 7443 + coturn relay)
