# ADR-0116: 진도는 뒤로 가지 않는다

> 관련 결정: [songjeongki/ADR-0033 학습 진도 배선](0033-learning-progress-wiring.md) ·
> [songjeongki/ADR-0063 시청 구간 칸](0063-watch-heatmap-buckets.md)

- **상태**: 채택
- **일자**: 2026-08-10
- **적용 범위**: `useWatchTracking`의 서버 누적 반영 · `LearningService.updateProgress`

## 맥락

강사가 물었다 — "실시간으로 다 들었는데 왜 진행도가 100%가 아니냐". 화면에는 **4%**가 떠 있었다.

운영 데이터가 사고를 그대로 보여 줬다.

```
녹화 길이 244초 = 전체 25칸

칸 0        횟수 2   16:54:00      ← 이 한 줄만 나중에 다시 찍혔다
칸 3~24     횟수 1   16:53:54      ← 나머지 22칸은 한 번에
칸 1, 2     없음

learning_progress   진도 4% · 마지막위치 0 · 16:54
```

**23칸을 봤으니 92%가 나왔어야 한다.** 4%는 정확히 `1/25`이고, 마지막 위치가 0이다 — 진도를 보낸
그 순간 클라이언트가 알고 있던 칸이 **하나뿐**이었다는 뜻이다.

### 왜 하나뿐이었나 — 캐시에 남은 빈 응답

`useWatchTracking`은 서버에 쌓인 내 누적을 받아 그것으로 시작한다. 그런데 그 반영이 **첫 응답으로
잠겨** 있었다.

```ts
useEffect(() => {
  if (!mine.data || seededRef.current) return
  seededRef.current = true                    // 첫 데이터로 잠근다
  stateRef.current = advanceWatchBuckets(seedWatchBuckets(mine.data), positionRef.current)
}, [mine.data])
```

순서가 이렇게 흘렀다.

1. **라이브 입장** — 아직 아무것도 보내지 않았으므로 조회 결과가 **빈 목록**. 캐시에 남는다
   (`staleTime: 30_000`).
2. **라이브 시청** — 칸 0~24가 쌓이고 종료 직전 한 번에 서버로 나간다.
3. **다시보기 화면** — 같은 `lessonId`라 캐시의 그 **빈 목록이 즉시** 반환된다.
4. 그 빈 값으로 **잠긴다.** 뒤늦게 도착한 진짜 23칸은 무시된다.
5. 위치 0에서 칸 하나 세고 보고 → **4%**.

빈 배열은 `!mine.data`에 걸리지 않는다(빈 객체도 truthy). "아직 못 받음"과 "받아 보니 없음"이
구분되지 않은 채, 잠금이 그 첫 값에 걸렸다.

### 그리고 서버가 그 값을 그대로 받았다

`updateProgress`에는 순서역전 방어가 있고 주석은 "진도 후퇴 방지"라고 적혀 있었다. 그런데 그 가드는
`clientUpdatedAt`이 **저장값보다 뒤일 때만 반영**하는 것이라, **늦게 도착한 옛 보고**를 막을 뿐이다.
방금 만들어진 보고가 낮은 값을 들고 오면 그대로 덮는다. 이번이 정확히 그 경우였다.

## 결정

### 1. 서버 누적은 잠그지 말고 합친다 (FE)

`mergeWatchBuckets(state, serverCounts)` — 칸마다 **큰 쪽**을 남긴다.

- 낡은 빈 응답이 와도 지금까지 센 칸이 지워지지 않는다.
- 서버가 더 많이 알고 있으면(다른 기기에서 본 회차) 물려받는다.
- 값이 누적 절대값이라 **몇 번을 합쳐도 결과가 같다.**
- `lastBucket`은 건드리지 않는다 — "지금 재생 중인 칸"이라 서버가 알 바가 아니다.

### 2. 진도는 내려가지 않는다 (BE)

`updateProgress`가 저장값과 새 값 중 **큰 쪽**을 남긴다.

FE를 고쳤으니 이건 안전망이다. 그런데 안전망이 필요하다 — 클라이언트가 어떤 이유로든 빈 상태에서
시작할 수 있고(캐시·새로고침·다른 기기), 그때마다 사람이 들인 시간이 깎이면 안 된다.

`lastPositionMs`는 **최대값이 아니다.** "지금 어디를 보고 있나"라 마지막 값이 맞고, 이어보기가 그
값을 쓴다.

**대가를 안다.** 자료를 다시 올려 길이가 **늘어나면** 같은 칸 수의 비율이 낮아지는데, 그때도 옛 값이
남아 과대평가된다. 진도가 사라지는 쪽이 강사·학생 모두에게 더 나쁘다고 보고 이쪽을 택했다. 되돌리려면
재업로드 시점에 명시적으로 초기화하는 편이 맞다.

## 결과

- 라이브에서 쌓은 칸을 다시보기 화면이 그대로 물려받는다.
- 진도가 클라이언트 사정으로 깎이지 않는다.
- 완료 표시(sticky)는 예전부터 유지됐고, 이제 진도율도 같이 지킨다.

## 검증

- `watchBuckets.test.ts` **+5건** — 낡은 빈 응답이 센 칸을 지우지 않는지 · 서버가 더 알면 물려받는지 ·
  같은 칸은 큰 쪽이 남는지 · 재생 중인 칸을 서버가 건드리지 않는지 · 더할 것이 없으면 상태를 그대로 두는지.
- `useWatchTracking.test.tsx` **+1건** — 빈 응답이 **먼저 반영된 뒤** 진짜 누적이 도착해도 물려받는지.
  이 테스트는 처음에 **헛돌았다**: `wrapper`가 렌더마다 새 `QueryClient`를 만들어 캐시가 이어지지
  않았고, 응답 순서도 제어되지 않아 진짜 데이터가 첫 응답으로 도착했다. 클라이언트를 테스트당 하나로
  고정하고 첫 응답을 손으로 resolve하도록 고친 뒤에야 잠금을 잡아냈다.
- `LearningContractTest.progress_never_goes_backwards` — 60% 뒤 4% 보고가 무시되고, 80% 보고는
  반영되는지. 기존 `progress_over_threshold_is_completed_and_sticky`는 "10%로 내려간다"를 고정하고
  있어 **함께 갱신**했다(그 값이 이번에 바꾸는 동작이다).
- **돌연변이 확인**: 잠금을 되돌리면 훅 테스트가 `20%`로 깨진다.
- 백엔드 **767건** · 프런트 **1,344건** 통과.

## 남은 일

**라이브만 듣고 다시보기를 안 열면 진도가 0으로 남는다.** 진도율 계산이 브라우저에서만 일어나고,
계산에 필요한 전체 길이는 녹화가 끝나야 생기기 때문이다(`bucketProgressPercent`는 길이를 모르면
null을 돌려준다). 녹화 완료 시점에 **서버가 쌓인 칸으로 환산**하는 것이 다음 수순이고, 녹화가 아예
없는 강의를 어떻게 다룰지는 그때 함께 정해야 한다.
