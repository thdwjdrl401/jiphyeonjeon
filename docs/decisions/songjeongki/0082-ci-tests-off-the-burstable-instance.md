# ADR-0082: CI 테스트를 운영 EC2에서 전부 뺀다 — t2.xlarge의 지속 CPU는 0.9 vCPU다

> 📍 하네스 개요: [../../harness/README.md](../../harness/README.md) · 아키텍처: [../../ARCHITECTURE.md](../../ARCHITECTURE.md) · 계약: [../../CONTRACT.md](../../CONTRACT.md)

- **상태**: 채택
- **일자**: 2026-08-05
- **관련**: [0038](0038-ci-test-gate-testcontainers.md)(CI가 계약 테스트를 실제로 돌린다), [0069](0069-number-collisions-close-the-merge-window.md)(이번에 같이 옮긴 `check-collisions` 잡의 근거),
  `infra/ci/lazy-runner/README.md`, `infra/livekit/remote-egress/README.md`(같은 이유로 부하를 뗀 사례)
- **오너 경계**: 인프라(송정기) — 러너 배치·동시 실행 / FE — `vite.config.ts`의 포크 수 한 줄 / BE — 없음

## 맥락

CI가 느리고 자주 깨졌다. 처음에는 테스트가 무거워서라고 보고 테스트를 정리했다 — 실제로 한
클래스가 백엔드 시간의 70%를 먹고 있었고 그것을 고쳤다(189초 → 67초). 그런데도 파이프라인은
9분대에 머물렀고, **같은 잡의 실행 시간이 4초에서 1,050초까지 253배 흔들렸다.**

그 편차를 "러너가 바쁘다"로 설명해 왔는데, 근거가 없었다. 그래서 하루치 `sar`를 봤다.

```
14:20         user 52%     steal  0.3%   idle 40%
14:30~14:50   user 81~87%  steal  0.1%   idle  3%   ← CI가 CPU를 꽉 채워 태움
15:00         user 39%     steal 53.6%   idle  2%   ← 여기서 무언가 꺾인다
15:00~19:20   user 24~30%  steal 44~63%             ← 4시간 반 내내
19:30         user  7%     steal  0.9%   idle 89%   ← 부하 그치자 정상
```

`steal`은 하이퍼바이저가 CPU를 가져간 시간이다. 오전 내내 0.2~0.6%였다가 15:00에 53.6%로
뛰었고, 그 뒤로 네 시간 반 동안 절반이 사라졌다.

인스턴스 타입을 확인했다. **`t2.xlarge`** — 버스터블이다. 지속 가능한 성능이 4 vCPU의 22.5%,
즉 **0.9 vCPU**다. 그 이상은 크레딧으로 빌려 쓰고, 크레딧이 바닥나면 baseline으로 조인다.
스로틀 구간의 `user ≈ 25%`가 정확히 그 baseline이다.

증거를 하나 더 맞춰 봤다. **같은** 프론트 스위트(120파일·1004건)를 두 시각에 돌린 기록이다.

```
14:03 (크레딧 있음)   103초
19:10 (스로틀 중)     307초
```

테스트는 한 줄도 늘지 않았다. "253배 편차"는 테스트가 무거워서가 아니라 **박스가 절반이
되었다 돌아왔다** 한 것이다.

### 이것은 CI만의 문제가 아니다

같은 호스트에 라이브 강의 서비스가 있다. 크레딧이 바닥난 네 시간 반 동안 **운영도 같이
반쪽이었다.** CI를 빠르게 하는 문제 이전에, CI가 서비스 품질을 깎고 있었다.

### 예산으로 보면

```
지속 예산        3,240 vCPU초/시간
운영 상시 소비     -1,008          (유휴 시 user 7% × 4 vCPU)
CI 몫             2,232 vCPU초/시간

파이프라인 1회      578 vCPU초  →  시간당 3.9회가 한계
피크 실측        4,400~7,000 vCPU초/시간  →  3.1배 초과
```

시간당 네 번이 한계인 예산을 그 세 배로 쓰고 있었다. 잡을 조금 가볍게 해서 메울 격차가 아니다.

## 결정

**`test-*` 여섯 개와 `check-collisions`를 전용 러너(`lazy-test`, 8코어)로 전부 옮긴다.**
EC2에는 `build`와 `deploy` 계열만 남긴다 — 그쪽은 shell executor로 그 호스트에서 제자리
배포하고 시크릿(`/etc/liveclass/.env.prod`)도 거기에만 있어 옮길 수 없다.

함께 정하는 것 셋.

**① `build`는 테스트를 기다리지 않는다**(`needs: []`). 어떤 테스트의 아티팩트도 쓰지 않는데
스테이지 순서만으로 뒤에 서 있었다. 파이프라인 169584는 실작업 389초가 598초가 됐고 그중
207초는 EC2 단일 슬롯 앞의 순수 대기였다. 테스트가 깨져도 이 잡은 돈다 — 둘은 독립된
게이트이고, 어느 하나라도 빨간불이면 머지는 막힌다(`only_allow_merge_if_pipeline_succeeds`).

**② 프론트 포크를 2에서 4로 올린다.** 8코어 전용 러너 실측:

```
forks 2 → 107초    forks 4 → 73초    forks 6 → 64초    forks 8 → 63초
```

4를 넘으면 얻는 것이 급격히 줄고(코어 포화), 대신 같은 호스트의 녹화에 남길 여유가 사라진다.

**③ 러너 동시 실행을 올린다**(EC2 1→2, lazy 2→3). 지금까지 3초짜리 `check-collisions`가
대기 중앙값 99초, 22초짜리 `test-bge-runtime`이 대기 중앙값 749초였다 — 전부 단일 슬롯 뒤에
줄을 선 시간이다.

동시 실행을 켜면 드러날 자리 두 곳을 같이 막았다. `test-frontend`의 `node_modules` 볼륨과
`build`의 compose 프로젝트 이름이 고정이라, 서로 다른 MR이 겹치면 한쪽이 다른 쪽이 쓰는
중인 것을 지우거나 덮는다. 지금까지 안 터진 것은 러너가 `concurrent = 1`이라 **우연히**
직렬이었기 때문이다. 둘 다 `$CI_CONCURRENT_ID`로 슬롯마다 갈랐다.

## 대안과 기각 이유

**T2 Unlimited를 켠다** — 한 번의 설정으로 스로틀이 사라진다. 기각하지는 않았고 보류다.
baseline 초과분이 vCPU시간당 과금되는데, 지금 초과가 3배라 비용을 예측하기 어렵다. 테스트를
걷어내면 남는 부하가 baseline 안에 들어올 가능성이 높으므로 **먼저 옮기고 그 뒤의 steal을
보고 판단한다.** 이 판단이 필요해지면 그때 별도 ADR로 남긴다.

**인스턴스 타입을 비버스터블로 바꾼다** — 근본적이지만 재기동이 필요해 운영 중단이 생기고,
비용도 늘어난다. 위와 같은 이유로 실측 뒤로 미룬다.

**테스트를 더 가볍게 만든다** — 이미 했고, 더 깎을 군살이 없다. 백엔드 107클래스 중 82개가
1초 미만이고 지배적인 클래스가 없다. 프론트는 120파일이 합쳐 110 CPU초다. `@Disabled`·
`test.skip`·`.only`는 0건이다. 3배 초과를 메울 여지가 아니다.

**테스트를 줄이거나 건너뛴다** — 계약 테스트는 [ADR-0038](0038-ci-test-gate-testcontainers.md)이
"실제로 돌린다"고 정한 게이트다. 느리다는 이유로 게이트를 내리는 것은 문제를 다른 곳으로
옮기는 것이다.

## 결과

옮기기 전에 각 잡의 스크립트를 그 호스트에서 그대로 돌려 전부 통과하는 것을 확인했다
(bge 38초 · realtime-agent 108초 · ai-worker 97초 · ai-api 31초 · backend 172초 ·
frontend 73초). 실측 기준 가장 흔한 MR(`build + test-frontend`, 전체의 43%)은
563초에서 80~120초가 된다.

## 남는 위험

- **lazy는 코어가 아니라 메모리가 상한이다.** 8코어지만 RAM이 7.6GB뿐이고, 같은 호스트에서
  원격 Egress도 돈다(녹화 1건 약 2GB). 동시 3잡이 약 5.5GB라 녹화와 겹치면 거의 꽉 찬다.
  `concurrent`를 4로 올리려면 그 전에 잡별 메모리 상한을 걸어야 한다.
- **CI와 녹화 사이에 CPU 격리가 없다.** Egress는 가용 CPU를 보고 새 녹화를 받을지 정하므로,
  무거운 CI가 도는 중에는 녹화 시작이 거절될 수 있다. 아직 겪지 않았고 실측치도 없다.
- **가정용 회선을 탄다.** 끊기면 테스트가 전부 멈춘다. 태그를 되돌리면 즉시 EC2로 돌아가지만,
  EC2는 위의 크레딧 한계를 그대로 안고 있으므로 **임시 대피지이지 원상복구가 아니다.**
- 프론트 스위트에 재현되지 않은 플레이키가 하나 남아 있다(`InstructorLiveMediaProvider`의
  발행 실패 테스트). 부하를 걸고 단독 10회는 모두 통과해 원인을 확정하지 못했다.
