## 맥락

[0029]에서 FE HTTP 어댑터가 부르는 경로를 컨트롤러 매핑과 대조했고, 그중 둘(`GET /lessons/{id}`·`PUT /me/display-name`)은 서버에 구현했다. 남은 **14개는 CP1~CP5 범위**라 지금 만들 수 없는데, 프론트가 그 경로를 그대로 호출하고 있어서 세 가지 문제가 있었다.

1. **404가 장애와 구분되지 않는다.** 화면에는 "불러오지 못했습니다"만 뜬다. 사용자도 개발자도 "서버가 죽었나"와 "아직 안 만든 기능인가"를 구별할 수 없다.
2. **저장이 절반만 반영된다.** `saveCurriculumManagement`는 커리큘럼 정보 → 섹션 → 순서 → 새 섹션 → **자료** 순으로 다섯 번 쓴다. 마지막 자료 호출만 없는 경로라, 앞의 네 번이 커밋된 뒤 404가 난다. 화면엔 "저장 실패"가 뜨는데 서버 데이터는 바뀐 상태고 롤백할 방법이 없다. `saveLesson`의 자료 첨부도 같은 모양이다.
3. **부가 조회 하나가 화면 전체를 막는다.** 자막·학습 요약·질문 하이라이트가 진입 게이트에 섞여 있어, 목록이나 세션을 정상으로 불러왔는데도 페이지가 통째로 오류 화면이 됐다.

작업 중 하나가 더 드러났다. 라이브 강의실의 레슨 조회는 세션 결과에 의존해(`enabled`) 세션이 실패하면 **비활성인 채 영원히 `isPending`으로 남는다.** 게이트가 로딩을 먼저 검사해서, 세션이 죽으면 오류 화면에 닿지 못하고 로딩 화면에 갇혔다.

## 결정

### 1. 없는 경로는 호출하지 않고 501 + `API_NOT_IMPLEMENTED`로 표시한다

`shared/api/notImplemented.ts`에 모은다. 어느 경로인지 메시지에 남기고, 화면이 분기할 수 있게 `isNotImplemented(error)`를 함께 제공한다.

```ts
async getReplayCaptions(lessonId) {
  return notImplemented(`GET /lessons/${lessonId}/captions`)
}
```

**목 데이터를 흉내 내어 돌려주지 않는다.** 그러면 화면은 정상으로 보이는데 값이 가짜라 "구현됐다"는 착각을 만든다. [0028]에서 백엔드가 근거 없는 `materialAttentionCount`를 0으로 채우는 대신 필드를 아예 빼기로 한 것과 같은 판단이다.

기존에 `httpProfileService`가 쓰던 `PROFILE_HTTP_ADAPTER_UNAVAILABLE`도 이 공용 코드로 합친다 — 화면이 feature마다 다른 코드를 알 필요가 없다.

### 2. 실패가 확정된 저장은 **첫 쓰기 전에** 막는다

`materials`가 비어 있지 않으면 어떤 요청도 보내기 전에 던진다. 자료를 건드리지 않은 저장은 그대로 통과한다.

부분 쓰기를 감수하고 순서를 바꾸거나 보상 트랜잭션을 넣는 대안도 있었지만, 지금 필요한 것은 "막힐 저장은 **아무것도** 바꾸지 않는다"는 성질 하나뿐이다. 자료 API가 생기면 이 가드만 지우면 된다.

### 3. 진입 게이트에는 그 화면의 정체성만 둔다

| 화면 | 필수 (없으면 화면이 성립 안 됨) | 부가 (실패해도 화면은 뜬다) |
|---|---|---|
| 라이브 강의실 | 세션, 레슨 | 채팅, 자막, 질문 하이라이트 |
| 다시보기 | 레슨 | 게시본 자막, 채팅 |
| 내 커리큘럼 | 목록 | 학습 요약 |

내 커리큘럼은 목록 오류와 요약 오류를 갈라 표시하고, 요약이 미구현이면 "아직 준비 중"으로 안내한다(`isNotImplemented`).

### 4. 게이트는 **실패를 로딩보다 먼저** 검사한다

```ts
if (sessionQuery.isError || lessonQuery.isError) return <PageState title="…못했습니다" />
if (!session || !lesson) return <PageState title="…불러오는 중입니다" />
```

의존 쿼리(`enabled: Boolean(sessionQuery.data?.lessonId)`)는 선행 쿼리가 실패하면 비활성인 채 `isPending`으로 남는다. 로딩을 먼저 보면 그 상태에 영원히 갇힌다.

## 근거

- 미구현과 장애를 코드로 가르면 화면 문구뿐 아니라 **재시도 여부**도 다르게 다룰 수 있다. 없는 경로를 재시도하는 것은 의미가 없다.
- 부분 쓰기는 사용자가 복구할 수 없는 종류의 실패다. "실패했다"는 안내가 사실과 다르면(일부는 저장됨) 다음 행동을 잘못 고르게 된다.
- 진입 게이트를 좁히면 **서버가 하나씩 생길 때마다 화면이 단계적으로 살아난다.** 전부 갖춰질 때까지 못 여는 상태를 피한다.

## 대안

| 대안 | 장점 | 단점 |
|---|---|---|
| **명시적 501 (선택)** | 미구현/장애 구분, 남은 경로가 코드에서 보임, 네트워크 낭비 없음 | 화면이 501을 다룰 자리를 만들어야 함 |
| 목 데이터를 http 어댑터에서 반환 | 화면이 완성돼 보임 | 가짜 값이 "구현됨"으로 읽힘 — 데모에서 사실과 다른 수치를 보이게 됨 |
| 호출을 그대로 두고 404를 화면에서 해석 | 코드 변경 최소 | 404는 "경로 없음"과 "리소스 없음"이 섞임. 부분 쓰기도 그대로 |
| 조용히 빈 배열 반환 | 화면이 안 깨짐 | 실패가 사라져 아무도 모른다. 가장 나쁜 선택 |

## 영향·후속

- **검증**: `tsc --noEmit` 통과, `eslint --max-warnings 0` 통과, vitest **17 files / 139건 통과**(기존 113 + 신규 26).
  - `notImplemented.test.ts` 17건 — 헬퍼 계약 + 미구현 15개 경로가 네트워크로 나가지 않는지
  - `partialWriteGuard.test.ts` 4건 — 자료가 붙으면 요청 0건, 자료가 없으면 정상 저장
  - `AuxiliaryQueryDegradation.test.tsx` 5건 — 부가 조회가 실패해도 화면이 열리는지, 필수가 실패하면 오류를 내는지
- **테스트 작성 중 발견**: `PageState`는 heading이 아니라 `<strong>`으로 그린다. `getByRole('heading')`으로 찾는 단정은 늘 못 찾아서 **부정 단정이 헛통과**한다. 이 문서의 테스트는 텍스트로 찾는다.
- **서버가 생기면**: `notImplemented(...)` 한 줄을 실제 `apiClient` 호출로 바꾸면 된다. 응답 정규화(`captionAdapter` 등)는 그대로 두었다.
- **남은 것**: 라이브·다시보기 화면의 개별 패널에서 "준비 중"을 알리는 UI는 내 커리큘럼에만 넣었다. 나머지 패널은 빈 목록으로 조용히 뜬다 — 어떤 문구를 어디에 넣을지는 화면 설계라 `frontend/` 오너와 함께 정하는 것이 맞다.
- **여전히 미구현**: 자료 업로드(ADR-0023 MATERIAL 3중 게이트, CP3), 라이브 자막(CP2), AI 질의·퀴즈·검수(CP3~CP5), 학습 요약(learning 배선, [0024]).
