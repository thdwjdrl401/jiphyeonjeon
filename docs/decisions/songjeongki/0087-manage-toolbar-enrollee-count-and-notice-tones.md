# ADR-0087: 관리 요약의 수강생 수, 그리고 "알림이 알림처럼 보이지 않는" 세 가지

> 📍 하네스 개요: [../../harness/README.md](../../harness/README.md) · 아키텍처: [../../ARCHITECTURE.md](../../ARCHITECTURE.md) · 계약: [../../CONTRACT.md](../../CONTRACT.md)

- **상태**: 채택
- **일자**: 2026-08-06
- **관련**: [0021](../yoongwanghyeok/0021-modern-ink-monotone-curation-ui.md)(모노톤 전환 — §8이 이 문서의 근거), [0042](0042-curriculum-material-attach-and-embedding-scope.md)(관리 화면 자동 저장), [0076](0076-enrollment-notification-action-axis-settlement.md)(수강 상태 축)
- **오너 경계**: BE — `enrolleeCount` 응답 / FE — 저장 실패 알림 위치 · 알림 톤 CSS

## 맥락

강사 관리 화면의 요약 툴바에서 **수강생 수가 늘 `--`**였다. 화면 코드는 멀쩡했다 —
`{storedCurriculum.enrolleeCount ?? '--'}`. **서버 응답에 그 필드가 아예 없었다.** 백엔드 전체에
`enrolleeCount`라는 이름이 한 번도 나오지 않는다. 목 데이터에는 값이 있어서 개발 화면에서는
정상으로 보였고, 운영에서만 `--`였다.

그 김에 "알림이 흐름에 끼어들어 화면을 흔드는 곳"을 훑었다. 훑다가 더 큰 것이 나왔다.

## 결정

### 1. `enrolleeCount`는 `CurriculumResponse`를 돌려주는 모든 응답에 싣는다

관리 조회만이 아니라 **생성·PATCH·게시**에도 넣는다. 화면이 자동 저장 응답으로 상태를
갈아끼우므로, 조회에만 있으면 **저장할 때마다 숫자가 사라졌다 다시 나타난다.**

**ACTIVE만 센다.** 승인 대기 중인 신청까지 세면 강사가 실제 수강 인원을 잘못 읽는다. 이미 있는
`EnrollmentDirectory.countsByStatus`(집계 쿼리 1회, 행을 적재하지 않음)를 쓴다.

### 2. 자동 저장 실패는 흐름에서 빼고 토스트로 옮긴다

요약 툴바 위에 `inline-notice`를 끼워 넣고 있었다. 실제 브라우저에서 재 봤다.

```
툴바 top: 223.05px → 282.15px   (아래 전체가 59.09px 내려감)
```

자동 저장은 편집 중(디바운스 1초)에 도는 것이라, 이 59px이 **글을 쓰고 있는 손 밑에서** 튄다.

- **자동으로 닫지 않는다**(`duration: 0`). "새로고침한 뒤 다시 시도해 주세요" 같은 **복구 방법이
  담긴 문장**이라 3.2초 뒤에 사라지면 읽지 못한 사람이 생긴다. 대신 저장이 다시 성공하면 우리가
  치운다 — 그래서 `toast.show`가 **id를 돌려주도록** 했다(닫으려면 부른 쪽이 id를 쥐어야 한다).
- **같은 문구는 쌓지 않는다.** 서버가 계속 죽어 있으면 편집할 때마다 한 장씩 늘어난다.
- 헤더의 `autosave-status` 칩("저장 실패")은 그대로 둔다 — 토스트를 닫아도 남는 지속 신호다.

### 3. inline-notice·toast의 톤을 되살린다 ← 훑다가 나온 진짜 문제

`design-system.css`가 `main.tsx`에서 **맨 뒤에** 로드되는데, 거기서 `.inline-notice`와 `.toast`의
**base**를 다시 선언했다. 같은 특이도라 나중에 온 쪽이 이긴다 — `workspace.css`·`toast.css`의
톤 규칙이 전부 덮였다. 실제 브라우저에서 잰 계산값이다.

| | 고치기 전 | 고친 뒤 |
|---|---|---|
| `inline-notice--info` | `rgb(238,236,232)` | 그대로 · 인장 없음 |
| `inline-notice--success` | `rgb(238,236,232)` | `rgb(232,239,235)` · 초록 인장(채움) |
| `inline-notice--warning` | `rgb(238,236,232)` | 중립 바탕 · **빈 인장** |
| `inline-notice--danger` | `rgb(238,236,232)` | `rgb(245,231,228)` · 인주 인장(채움) |
| `toast--success` / `--danger` | 둘 다 `rgb(36,35,32)` | 먹에 각 색을 섞은 바탕 + 같은 인장 |

**네 톤이 전부 같은 회색이었다.** 저장 실패가 안내문과 구분되지 않았고, 토스트는 성공과 실패가
똑같은 먹색 상자였다(살아남은 차이는 1px 테두리 색뿐이라 사실상 구분되지 않는다).

[ADR-0021](../yoongwanghyeok/0021-modern-ink-monotone-curation-ui.md) §8이 못박은 지점이다 —
*"의미 있는 상태색은 모노톤 전환 뒤에도 식별 가능해야 한다."* 같은 파일의 `.status-pill--*`는
톤을 다시 세워 두었으니, 이 둘만 빠진 **누락**으로 본다.

### 표식은 인장(印章)이다

색은 새로 만들지 않는다. 그런데 **이 팔레트의 유채색은 인주와 먹빛 초록 둘뿐**이라(나머지 토큰은
모노톤 전환에서 회색으로 remap됐다) 색만으로는 셋을 가를 수 없다. 그래서 **바탕**(무엇)과
**인장**(어떤 상태)을 두 축으로 쓴다.

인장은 브랜드 마크의 인주 사각형과 같은 도형이다(`.brand-mark rect`) — 이 제품이 이미 쓰고 있는
어휘라 새 기호를 들이지 않는다. `::before`로 그리므로 **컴포넌트 JSX는 손대지 않는다.**

| 톤 | 바탕 | 인장 |
|---|---|---|
| info | 중립 | 없음 — 상태가 아니라 안내다 |
| success | 먹빛 초록 | 초록, 채움 |
| warning | 중립 | 인주, **비어 있음** — 아직 찍히지 않은 도장 |
| danger | 인주 | 인주, 채움 |

warning과 danger는 인주색을 함께 쓰지만 **두 축이 동시에 다르다**(바탕 중립/붉음, 인장 빔/채움).
한 축만 다르면 흘려볼 수 있어도 둘이 같이 움직이면 눈에 걸린다.

토스트는 먹색 칩이라는 성격을 유지하되 그 색을 먹에 조금 섞어 바탕에 깐다. 인주·먹빛 초록을
그대로 얹으면 먹 위에서 탁해지므로 **흰색을 섞어 밝힌 값**을 쓴다 — 새 색이 아니라 같은 토큰을
옅게 푼 것이고, `color-mix`로 적어 두어 토큰이 바뀌면 따라 움직인다(이 파일이 이미 쓰는 방식이다).

## 고려한 대안

| 대안 | 판단 |
|---|---|
| 저장 실패 자리를 미리 비워 두기(레이아웃 시프트만 제거) | 늘 비어 있는 59px이 생긴다. 오류는 드문 일이라 그 대가가 반대다 |
| 저장 실패를 기본 지속(3.2초) 토스트로 | 복구 방법이 담긴 문장이라 읽기 전에 사라진다 |
| 헤더 "저장 실패" 칩만 남기고 문구를 버리기 | 구조 충돌과 자료 동기화 실패는 대응이 다르다 — 이유를 잃으면 강사가 할 수 있는 게 없다 |
| CSS import 순서를 바꿔 톤 규칙을 뒤로 | 파일 하나를 옮기면 그 파일의 <b>다른 모든 재정의</b>가 같이 움직인다. 눈에 안 띄는 회귀가 넓게 퍼진다 |
| 톤마다 새 색 토큰 추가 | 모노톤 전환의 취지에 어긋난다. 팔레트에 이미 있는 값으로 충분하다 |
| **왼쪽에 톤 색 세로선** | 처음 쓴 방법이고 되물렀다. 이 제품의 어휘가 아니라 <b>어디서나 보는 기본형</b>이고, 브랜드가 이미 인장이라는 자기 기호를 갖고 있다. 세로선은 상자를 장식할 뿐 상태를 말하지 않는다 |
| 톤마다 아이콘(⚠·✕·✓) | 모노톤·명조 위에서 이질적이고, 텍스트 크기를 따라 흔들린다. 인장은 도형이라 크기·정렬이 고정된다 |
| `enrolleeCount`를 목록 API(`InstructorCurriculumListItem`)에도 | 목록은 커리큘럼마다 집계 쿼리가 붙어 N+1이 된다. 필요해지면 배치 포트(`countActiveByCurriculums`)로 따로 한다 |

## 함께 본 것 — 고치지 않은 것들

흐름에 끼어드는 알림을 전부 훑었고, **나머지는 그대로 두는 것이 맞다고 판단했다.**

- **폼 필드 오류**(로그인·가입·비밀번호 재설정): 입력 바로 아래가 제자리다. 토스트로 옮기면 어느
  칸이 틀렸는지 사라진다.
- **조회 실패 안내**(내 커리큘럼·운영 콘솔·수강생 로스터): 실패가 <b>지속 상태</b>다. 목록이 있어야
  할 자리에 이유가 있는 편이 맞고, 토스트는 사라져서 빈 화면만 남는다.
- **업로드·탈퇴 모달의 제출 오류**: 누른 버튼 바로 위다. 모달은 스크롤되므로 잘리지도 않는다.
- **라이브/다시보기 화면의 띠**: 뷰포트 높이에 맞춘 세로 flex라 위험한 자리인데, `.media-page--live`
  아래의 띠들은 이미 `flex: 0 0 auto`로 고정돼 있고 CSS에 그 이유가 주석으로 남아 있다.
- **`GlobalHeader`의 로그아웃 실패**: `position: absolute`라 흐름을 건드리지 않는다.

## 결과와 한계

### 검증

- `CatalogViewerContextContractTest` **+1건** — 0 → 신청만(여전히 0) → 승인(1) → PATCH 응답에도 1.
  **돌연변이 확인**: 집계를 `0L`로 바꾸면 깨진다.
- `CurriculumWorkspace.test.tsx` **+3건** — 요약 툴바가 수강생 수를 그림 · 저장 실패가 알림 영역
  안에서 나오고 요약 툴바의 문서 위치가 그대로임 · 같은 실패가 토스트를 겹쳐 쌓지 않음
- 프론트 **1,053건** 통과 / 백엔드 전체 통과 / typecheck·lint 통과
- 톤 회귀는 **실제 브라우저에서 계산값으로** 확인했다(위 표). jsdom은 import한 CSS를 적용하지
  않아 자동 테스트로 고정할 수 없다 — 이 한 줄이 이 문서에 표를 남긴 이유다.

### 한계

- **톤 회귀를 막는 자동 테스트가 없다.** 같은 사고(나중에 로드되는 파일이 base를 덮음)가 다시
  나면 또 사람이 발견해야 한다. 시각 회귀 도구를 붙이기 전까지는 이 문서가 유일한 방어다.
- 목록 API에는 `enrolleeCount`를 넣지 않았다(위 표 참조). 카드에 수강생 수를 띄우려면 배치
  집계부터 해야 한다.
- `.curriculum-manage__toolbar`의 `z-index: 12`와 960px 미디어 쿼리의 `position: static` 재설정은
  **죽은 코드**다(base에 `position: sticky`가 없다). `.curriculum-manage__publish-column`의
  `top: 146px`도 툴바가 붙어 있던 시절의 값이라 지금은 헤더(71px)보다 75px 낮게 뜬다. 이번
  변경과 무관해 손대지 않았고, 레이아웃을 다시 볼 때 함께 정리할 후보로 남긴다.
