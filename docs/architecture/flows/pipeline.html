팬아웃 워커 안 — 넓은 팬아웃

메시지에는 조건이 실리지 않는다. type 하나로 수신자 규칙이 정해지고, 명단은 앱을 통과하지 않는다.

이 그림이 기존 문서와 다르게 그려진 곳

코드를 다시 읽으며 확인한 것들이다. 그림은 코드를 따랐다.

  1. STOMP와 Web Push는 분기하지 않는다. "탭이 열렸으면 STOMP, 닫혔으면 Push"로 읽히지만 서버는 둘 다 무조건 보낸다 — WsNotificationBroadcaster.java:105의 pushSender.send(...)에는 조건이 없다. STOMP 쪽에만 있는 접속자 검사(:111)는 라우팅이 아니라 100만 번의 헛 호출을 줄이는 최적화다. 진짜 중복 억제는 브라우저 서비스워커의 client.focused(push-worker.js:30)에 있다.
  2. 푸시에는 딥링크가 없다. 호출부가 url=null을 넘겨(:105) 모든 푸시 클릭이 /notifications로 간다. STOMP 경로의 클릭은 서버에 대상을 재판정해 정확한 화면으로 가는데, 이 비대칭은 문서에 없다.
  3. ENROLLMENT_CANCELED는 알림이 아니다. 팬아웃 큐를 타지만 알림 행을 만들지 않는 정리 신호다 — 대기 중이던 신청 알림의 처리 축을 EXPIRED로 닫고 끝난다(NotificationFanoutWorker.java:117-121). 종류 검사보다 먼저 처리하는 이유는 isKnown이 false라 그대로 두면 DLQ로 가기 때문이다.
  4. LESSON_PUBLISHED는 발행 지점이 없다. 타입 상수와 화면 문구는 있지만 서버가 이 종류를 만들지 않는다 — 레슨에는 초안이 없고 공개 여부는 커리큘럼이 정하기 때문이다.
  5. 조각 크기와 폴링 주기는 application.yml에 없다. notification.fanout.slice-size(1000)와 live-starting-soon.poll-ms(30초)는 @Value 기본값으로만 존재해서, 운영에서 튜닝하려면 키를 먼저 추가해야 한다.

메시지 필드 이름

설계 문서(ADR-0073 §5)의 예시는 limit이지만 코드 정본은 sliceLimit이다(NotificationFanoutCommand.java:41). 이 문서는 코드를 따랐다.
