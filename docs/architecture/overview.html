제품

업로드 강의가 아니라, 라이브의 부산물로 만들어지는 강의

콘텐츠는 전부 라이브와 그 녹화에서 나온다. 강사가 따로 올리는 건 강의자료(PPTX)뿐이다. 이 한 줄이 아키텍처 전체를 결정한다 — 라이브 없이는 다시보기도 없고, 그래서 라이브 미디어가 가장 먼저 서야 하는 토대다.

LIVE

실시간 자막과 용어

강사 오디오가 STT를 거쳐 자막이 되고, 확정된 구간에는 용어 설명과 자료 근거가 따라붙는다.

ASK

자료 근거 RAG

강의자료와 자막을 근거로만 답한다. 근거가 없으면 지어내지 않고 INSUFFICIENT_EVIDENCE를 반환한다.

REPLAY

다시보기 = 완성본

라이브 때 만든 산출물을 그대로 재생한다. 이미 교정이 끝난 뒤라 처음부터 전체 기능이 나온다.

01
원칙

여섯 개의 분리 원칙

구현이 흔들릴 때 되돌아오는 기준선이다. 모든 설계 논쟁은 이 여섯 줄로 판정한다.

  1. React는 Spring으로만 요청한다. Python AI는 외부에 노출되지 않는다 — 권한·정책·비용을 Spring이 검증한다.
  2. core(Spring) / ai(Python) 스키마 공동수정 금지. 한 클러스터, 소유 기준은 그 행을 실제로 쓰는 서비스(write-owner)다.
  3. 긴 작업은 큐 잡으로. HTTP 요청 안에서 처리하지 않는다. Redis는 durable 큐로 쓰지 않는다.
  4. 미디어 바이트는 Spring을 통과하지 않는다. 라이브는 WebRTC 직결, 자료 업로드는 presigned로 클라이언트가 스토리지에 직접 PUT 한다.
  5. AI 결과는 후보다. 원본은 보존하고 강사 게시본을 학생에게 노출한다. 예외 — 라이브 자막. 실시간 자막은 검수 없이 즉시 나간다. 그게 실시간의 본질이다. 검수는 사후 교정이고 승인 게이트는 두지 않는다.
  6. AI 장애가 코어를 막지 않는다. 라이브 영상·채팅·수강·다시보기는 AI와 무관하게 살아 있다.

03
모듈

경계를 규율이 아니라 빌드 실패로 지킨다

Spring Modulith로 모듈 경계를 코드에 새겼다. 다른 모듈의 domain·repository를 직접 부를 수 없고, 접근은 <module>.api 공개면으로만 가능하다. 순환은 금지고, 위반은 리뷰어가 아니라 CI가 잡는다.

포트는 필요한 모듈만 만든다. 10개 모듈 중 .api를 가진 건 6개이고, curriculum은 유입 참조가 없어 포트가 아예 없다. 기계적으로 다 파면 비용만 남는다.

이 게이트가 실제로 잡은 것
  • video → live.config아무도 의도하지 않은 결합이 드러났다. LiveKitServerAccess seam으로 정리.
  • CatalogService서비스가 web DTO를 알던 계층 역전. 서비스 레벨 record + web 팩토리로 분리.
  • live → curriculum순환이 막히자 live_session.curriculum_id를 비정규화했다. 결과적으로 조인 없이 수강을 검사하는 더 빠른 구조가 됐다.

세 번 다 확장성 이야기가 아니다. 전부 지금 당장의 코드 품질이다. 나중에 특정 모듈을 별도 서비스로 떼어낼 수 있다는 건 공짜로 딸려오는 선택지이지, 이 구조를 고른 이유가 아니다.

04
시간축

지평선 — 라이브와 확정본 사이의 거리

이 제품의 모든 데이터는 세션 상대 밀리초라는 하나의 좌표 위에 놓인다. 자막도, HLS 세그먼트도, 다시보기 싱크도 같은 축을 쓴다. 그 축 위에서 지금과 확정된 지점 사이의 간격이 지평선이다.

인프라는 쓰는 시점에 배선한다

RabbitMQ는 dev 인프라에 이미 서 있지만 Spring 배선과 prod 투입은 CP3에서 한다. CP2의 자막 경로는 Redis Streams로 충분하고, 실제 배치 잡은 CP3에서 처음 생긴다. 단일 노드에 컨테이너를 하나라도 늦게 얹는 게 낫다.

06
결정

착수를 막는 결정 네 가지

미구현 영역을 점검하며 나온 것들이다. 답이 나와야 CP2·CP3에 손을 댈 수 있다.

지평선을 몇 초로 둘 것인가

CP2 차단

제품 설명의 핵심 단어인데 정의가 없다. 프론트의 자막 렌더링 정책과 백엔드의 영속 시점이 여기에 달려 있다.

제안 partial은 즉시 회색으로, final은 확정 렌더, 교정·용어·근거는 t − N초 뒤 재전송. N은 STT bake-off 결과로 정하고 설정값으로 뺀다.

자료를 레슨에 붙이는 API가 없다

CP3 차단

presigned 업로드는 되지만 업로드한 자료를 레슨에 연결하는 경로가 없다. RAG ingestion의 입력이 비어 있는 상태다. 로드맵 의존성 그래프에도 빠져 있던 선행조건이다.

제안 CP3 착수 전 백엔드 작업으로 명시하고 의존성 그래프에 반영한다.

자막이 유실되면 정본은 어디에 있나

CP2 차단

원칙 3은 Redis를 durable 큐로 쓰지 않는다고 했는데, 자막이 Redis Streams를 지난다. Redis가 재시작하면 그 구간의 정본이 없다.

제안 자막 fast-path는 의도적으로 유실을 허용하고, 빈 구간은 CP4 녹화본 2-pass 재처리로 복구한다. 그러면 Redis는 여전히 fast-path이고 정본 복구 경로는 녹화가 된다.

EC2 한 대로 CP3까지 갈 수 있나

CP2 차단

노드 전체가 4vCPU/15GB인데 Egress 단독 권장 사양만 4vCPU/4GB다. 여기에 realtime-agent·ai-api·ai-worker가 더 붙는다.

전제를 명시한다 STT·임베딩·LLM은 전부 외부 API · Egress는 데모 세션에만 기동 · 동시 라이브 세션 1~2개. 이 전제가 깨지면 노드를 분리한다.

07
배포

한 대의 EC2, 두 개의 독립 스택

앱 스택은 nginx가 TLS를 종단하고 SPA와 /api를 같은 오리진에서 서빙한다 — 쿠키 세션이 CORS 없이 동작한다. 미디어 스택은 SFU가 UDP 포트를 직접 잡아야 해서 network_mode: host로 도커 NAT를 우회한다.

도메인이 하나뿐이고 DNS 콘솔 권한이 없어, 미디어 시그널링은 서브도메인 대신 같은 도메인의 별도 TLS 포트로 분리했다. 인증서는 앱 스택이 단독으로 발급·갱신하고 미디어 nginx는 볼륨으로 읽기만 한다.
